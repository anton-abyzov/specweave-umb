[medium] Retry of a saved blocked-path clone bypasses the new safety rule

Where: `/Users/antonabyzov/.specwithcode/m4/worktrees/specwithcode/fix-folder-copy-origin-leftovers/apps/server/src/fleet/folderTransfer/destinationService.ts:691-692`, `/Users/antonabyzov/.specwithcode/m4/worktrees/specwithcode/fix-folder-copy-origin-leftovers/apps/server/src/fleet/folderTransfer/destinationService.ts:1245-1256`, `/Users/antonabyzov/.specwithcode/m4/worktrees/specwithcode/fix-folder-copy-origin-leftovers/apps/server/src/fleet/folderTransfer/apply.ts:429-431`.

Why: A pre-update failed Apply can retain a clone step for an occupied non-repository folder and its synced `cloned` intent. Retry reads that saved plan directly; it never passes through the new blocked-row replacement rule. If `.git` is absent and the origin becomes readable, Apply clones alongside the original files and attaches `.git`. Undo then moves the whole folder, including the original destination-only files, into `undone-clones` instead of restoring their original location. The reproduction used an occupied `svc` folder with `notes.txt`, a local bare origin, and the legacy `cloned` intent. It confirmed that the current planner would select `replace`, while replay of the saved `clone` selected the unsafe clone path. Apply and Undo returned no problems, and `notes.txt` disappeared from the destination after Undo.

Fix: Before replaying saved clone steps, identify legacy clones whose paths already contained destination files and refuse unsafe Retry with an explicit recovery path, or migrate their plan, staging and journal safely. Do not simply change `clone` to `replace`: old staging omits Git data and clean tracked files, and the existing `cloned` intent still affects Undo. Add an upgrade/restart regression covering this persisted state.
