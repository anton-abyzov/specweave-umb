# Copilot turns end with the answer, not with their background command, and the queue says why it waits

## Problem

On M5, messages typed into a GitHub Copilot thread often sit in the queue behind a turn that shows "No new events for 4m" and "Can't steer now". Evidence and timelines: `reports/root-cause.md`.

1. **Copilot holds the turn open.** Copilot CLI 1.0.114 does not answer `session/prompt` while a shell it started in the background (`mode: "async"`) is alive. The app treats that prompt as the turn. In "GTA 6 livestream kit" on November 20, 2026, turn 30 wrote its answer after 17 seconds and stayed running for 13 minutes 39 seconds until Stop; turns 26 and 28 were silent for 461 s and 611 s the same way. Two typed messages waited 701 s and 632 s for that turn and were then held by Stop. Across M5, Copilot left a background command running in 4 turns, and all 4 stayed open until the command ended or Stop was pressed.
2. **A Copilot thread can never be steered.** ACP has no mid-turn message, and interrupt-and-restart was switched off for Copilot in 1146 because cancelling a prompt stops its background agents. Every message to a busy Copilot thread queues. On M5 (567 runs, November 16 to 20), 11 of 78 typed Copilot messages waited over 30 seconds, against 2 of 94 on Claude and Codex.
3. **The screen reads as a temporary stall.** "Can't steer now" is permanent on Copilot, each row still shows a disabled "Steer now", and "No new events" is in the warning colour while the provider waits on a command it could name.
4. **Stop makes it worse.** Stop is the only way out, and it holds the queue until Resume, although the turn had already answered.
5. **After Stop the queue never starts.** Same thread, 1:43 to 2:00 PM. Copilot's wait covers every background command alive in the session, not only the turn's own: turn 35 started none and still hung after its answer, because a watcher started in turn 34 was alive. Stop does not end the watcher. Resume first sends "Continue where you left off." as a new turn, and a typed message also starts ahead of the older queued ones (`apps/web/src/components/ChatView.tsx:12248-12301`, `Orchestrator.ts:6830`). Each of those turns hung again, so three typed messages stayed queued for 19, 18 and 8 minutes or more through two Stops.

## Scope

In: the Copilot ACP adapter tracks the background commands a turn started; a turn that has answered and only waits on them gives way to a queued message; Stop on such a turn does not hold the queue; Steer now on Copilot by interrupt-and-restart when no background agent is running (if the probe allows it); the queue header and live row say what is true.

In also: Resume starts the queued messages themselves; a typed message sent to a stopped thread keeps its place behind older queued messages (D-05). Out: mid-turn delivery inside a running Claude or Codex command (a steered message is read when the command returns); prompt text telling agents how to run watchers (the standing rule is to enforce in code); other ACP agents; the 45-minute silent-run watchdog.

## Acceptance Criteria

- [ ] AC-01: A recorded probe of Copilot CLI 1.0.114 in `--acp` mode answers, in `reports/copilot-acp-probe.md`: (a) whether a second `session/prompt` is accepted while one is open; (b) whether `session/cancel` on a prompt that only waits on a background command leaves that command running and its output readable by shell id in the next prompt, with the stop reason returned; (c) whether Copilot sends any update when a background command ends while no prompt is open; (d) how a Copilot background agent appears in session updates, and whether it survives the same cancel; (e) whether any update marks the end of the model's step while the prompt stays open.
- [ ] AC-02: The server knows which background commands are running in a Copilot session, whichever turn started them, including after Stop and across turns, from the tool results (`<command started in background with shellId: X>`, `<shellId: X completed ...>`, `<command with id: X stopped>`), and publishes them on the thread.
- [ ] AC-03: A Copilot turn gives way to the queue when all of these hold: Copilot has sent `assistant.idle` for the foreground agent (the adapter opts in to that event), no tool call, request or background agent is open, a background command is still running in the session (started by this turn or an earlier one), and a message is waiting in the queue. The turn ends as completed, the background command keeps running, and the first queued message starts within 2 seconds of the later of the two (the idle event, the message arriving). With an empty queue the turn stays open and Copilot reports the command's result itself, as today.
- [ ] AC-04: When a background command ends while no prompt is open, Copilot's own report (the tool update and the text it streams by itself) is shown in the thread as its own completed turn, not dropped and not merged into another turn. If a turn is running, it is shown after that turn.
- [ ] AC-05: Stop on a turn that has written its answer and only waits on a background command ends it without holding the queue. Stop on a turn that is still working holds the queue as today.
- [ ] AC-06: On a Copilot thread with no background agent running, Steer now is enabled on a typed message: it cancels the current step and starts the message at once in the same session, and the queue order behind it is kept. A background agent is one started by a tool call with `mode: "background"` whose `agentId` has not gone idle. With one running it stays disabled and says "A background agent is running. Steering would stop it." Messages are never steered into a Copilot turn automatically.
- [ ] AC-07: Where a provider cannot steer this turn for a lasting reason, the queue header shows the reason in words ("Sends when this turn ends · GitHub Copilot can't take a message mid-turn") instead of "Can't steer now", and the rows show no Steer now button. A temporary reason (turn starting, saving its checkpoint) keeps the disabled button and its tooltip.
- [ ] AC-08: While a running turn is quiet and a background command is running in its session, the live row says "Waiting on a background command (X) · 4m" in the normal colour. "No new events" stays for a quiet turn with nothing known to be running.
- [ ] AC-09: On M5 with the released build, in a Copilot thread that starts a 5-minute background command and answers, a message typed after the answer starts within 5 seconds, and the command is still running. Screenshots and the run rows are in `reports/`.
- [ ] AC-10: Resume on a stopped thread whose queue holds a message a person typed starts the oldest queued message at once and sends no "Continue where you left off." turn. With no typed message queued, Resume continues the stopped turn as today.
- [ ] AC-11: A message typed into an idle thread whose queue is held releases the hold and joins the queue at the end, so the oldest queued message starts first. Run now on a row still starts that row first.
- [ ] AC-12: Replaying this thread's sequence in a server test (answer, live background command, three typed messages, Stop, Resume, a second turn that answers while the command is alive) delivers all three messages in order within 5 seconds of each idle event, with no second Stop.

## Approach

1. Probe (T-01, done): `reports/copilot-acp-probe.md`. Copilot reports the end of the answer with an `assistant.idle` event while the prompt stays open; a cancel, or a new prompt, ends a prompt that only waits and leaves the shell running; the wait is per session; when the shell ends with no prompt open Copilot streams its own report unprompted; a cancel stops a background agent. Not yet tested: a new prompt sent while the model is still working.
2. `apps/server/src/orchestration-v2/Adapters/copilotBackgroundCommands.ts` (new): parse the three tool-result forms into `started`, `ended`, `stopped` per shell id. Wired through the existing flavor hooks (`extractBackgroundTaskId`, `extractBackgroundTaskCompletion`) in `AcpRegistryAdapterV2.ts`, so the adapter's `BackgroundWork` report carries them. `AcpAdapterV2.ts` is 8,683 lines; new logic goes in the new file.
3. Ending the turn: the Copilot flavor opts in to `assistant.idle` and `session.idle` at `initialize` and handles `github.com/copilot/sessionEvent`. A new flavor option, `settlePromptWaitingOnBackgroundCommands`, is read where the adapter already settles prompts with background work. Updates that arrive with no prompt open open a provider-started turn (AC-04). The orchestrator asks the adapter to give way when a queued run exists; when the conditions of AC-03 hold, the adapter sends `session/cancel`, takes the prompt's stop reason as a normal end, and finalizes the run as completed. An optional wake (AC-04) reuses `backgroundWorkNotification`.
4. `apps/server/src/orchestration-v2/Orchestrator.ts`: a stop request for a run whose adapter reports "answered, waiting on background" completes it instead of holding the queue.
5. `CommandPolicy.ts`: Copilot's interrupt-and-restart stays off as a capability. A per-turn check allows a person's promote-to-steer when the active run has no open subagent item. `resolveMessageDispatchIntent` is unchanged, so sends still queue.
6. `packages/client-runtime/src/state/threadWorkflows.ts`: `steerUnavailableReason` returns a kind (`temporary` or `lasting`) with the words; the workflow state carries the turn's running background commands. `QueuedRunsControl.tsx` and `MessagesTimeline.tsx` render AC-07 and AC-08. New phrases go in all eight `apps/web/src/i18n/phrases/*.ts` files.
7. Queue order after Stop (AC-10, AC-11): in `ChatView.tsx` Resume calls `resumeThreadQueue` alone when the held queue has a person's message; in `Orchestrator.ts` a person's `message.dispatch` that releases a person-held queue is queued behind it instead of starting, and `startNextQueuedRun` runs after the release. AC-03 must key on the session's background commands kept across runs, so the store from step 2 lives on the provider session, not the run.

Rejected: ending the turn on a timer with an empty queue (it would drop Copilot's own report when the command ends, and the app may have no signal to replace it); telling Copilot in its instructions to detach watchers (prose the app cannot enforce, and the agent followed Copilot's own tool advice); switching interrupt-and-restart back on for every Copilot turn (stops background agents, the reason it was turned off in 1146); a shorter silent-run watchdog (would also end turns that are really working).

Risks: after `assistant.idle` Copilot can start more work by itself when a background command ends; giving way then cancels a pending prompt that is about to wake, so the adapter treats a `turn_start` after idle as work again. The parsing depends on Copilot's result wording and event names; an unrecognized form leaves today's behaviour.

## Decisions

### Asked
- D-01 May the app end a Copilot turn that has answered and only waits on a background command, as soon as a message is waiting? → Yes, automatically (user, November 20, 2026). The command keeps running; the agent's own report of its result may be lost unless the probe finds a signal.
- D-02 May Steer now be offered on Copilot as a manual press when no background agent is running? → Yes, manual only (user, November 20, 2026). It discards the step in progress and partly reverses 1146.
- D-05 After Stop, should Resume start the queued messages directly, and should a newly typed message wait behind the older queued ones? → Yes to both (user, November 20, 2026). Run now on a row still starts that row first.
### Defaulted (change any before sw-do)
- D-03 Stop on a turn that has already answered and only waits on a background command does not hold the queue.
- D-04 No quiet timer: the probe found Copilot's `assistant.idle` event, which marks the end of the answer. With an empty queue the turn stays open so Copilot can report the result itself.
