# Named accounts per provider: add, sign in and switch without the terminal

## Problem

Anton, November 18, 2026: "on one single machine (for example, I have two free accounts of ChatGPT), by the way, we should do the same for Claude. I want to switch from one account to another ... Maybe we need a skill so that it knows what to do to switch the subscription without a person, for example, opening a terminal, typing `/login`, and then going into the browser and confirming this. The same could be used inside of the terminal for Codex or for Claude."

What the terms decide. One person may hold several accounts with either vendor, but the two do not document the same thing. Anthropic documents it for Claude Code: "give each account its own configuration directory". OpenAI documents it for ChatGPT on the web and mobile only ("stay signed in to up to 2 separate ChatGPT accounts at a time ... Only one account is active at a time"; "You can have more than 2 ChatGPT accounts") and says nothing about several ChatGPT accounts signed in to Codex on one machine or used at the same moment, which is what this increment builds for Codex. OpenAI forbids "circumvent any rate limits or restrictions" and says "You cannot bypass a limit"; rotating two free ChatGPT accounts so Codex keeps running, which is the example in the request, is that case, and no setting or consent makes it compliant. Anthropic bars "automated or non-human" access to its consumer service, so a person approves on the vendor's page. This increment therefore builds holding accounts, signing in without the terminal and switching by hand. Automatic takeover at a limit is increment 1400 and waits for Anton's decision.

Anton accepted this plan on November 18, 2026 and added: the right provider logo wherever a provider is named; the Chrome profile shown the way Google shows it, by name and email, since he has sixteen profiles and six start with "Anton"; one machine at a time; and an easy way from here to all subscriptions and limits. Those are AC-01, AC-02 and AC-15. Limits and renewal dates for every provider are increment 1411. Takeover: he chose option A (increment 1400). Who approves on the vendor's page is still under discussion (D-02); this increment builds with the person approving.

What each sign-in costs after this increment: the first sign-in of an account takes one approval on the vendor's page, in the right Chrome profile, with no terminal. Every later switch between signed-in accounts takes no sign-in at all.

Most of the machinery exists. What is wrong today:

1. **Codex still needs the terminal.** A Codex instance that uses the Codex CLI's own login has no sign-in in the app; the status line says to run `codex login` (`apps/server/src/provider/CodexProvider.ts:773`). The only in-app path is "managed" Codex, where the app is the OAuth client and holds the ChatGPT tokens (`apps/server/src/provider/CodexManagedRuntime.ts:18`).
2. **Sign-in opens in the wrong Chrome profile.** Sign-in links go to the default browser (`apps/web/src/components/settings/ClaudeSignIn.tsx:108-118`, `apps/web/src/components/settings/ProviderAuthenticationSection.tsx:170`). With two accounts the default profile is signed in to the wrong one. The desktop shell can open a link in a chosen profile (`apps/web/src/browser/externalBrowsers.ts:76-87`); no sign-in uses it.
3. **Nothing says which account an instance should hold.** An account is a display name (`packages/contracts/src/providerInstance.ts:126`). If the wrong account signs in, the instance quietly runs under it.
4. **No single list.** A second Claude account and a second Codex account are two different dialogs behind "Add instance", and no view shows a provider's accounts with who is signed in, the Chrome profile and what is left.
5. **Agents cannot help.** No tool or skill lets an agent see the accounts or ask for a sign-in.
6. **The terminal has no helper.** Using account B outside the app means remembering `CLAUDE_CONFIG_DIR=~/.claude-work claude` or the right `CODEX_HOME`.

## Scope

In, for Claude and Codex, on the machine that runs them, with the desktop app on that machine:

- An Accounts list per provider in Settings > Providers and one Add account dialog for both.
- An expected email and a Chrome profile per account; sign-in opens in that profile and a wrong or unconfirmed account is held.
- Codex sign-in and sign-out through the Codex CLI's own login, with no terminal and no managed mode, on a Codex version that has the sign-in call (H2).
- Cancel, timeout, failure, sign-out and remove.
- Two agent tools and a skill; `specweave-studio accounts` for the terminal; a docs page.

Out:

- Automatic takeover between accounts of one vendor at a limit, and the same-account guard for it: increment 1400. Today's takeover is unchanged by this increment, except that a held account is never a target.
- Any click, typing, script or debugger on a vendor's sign-in page; reading Chrome profile storage or cookies. In this increment the person approves there; the automatic press Anton chose in D-02 is increment 1413.
- Reading, copying or storing a CLI's token; `claude setup-token`; Codex access tokens; token pooling proxies.
- Creating accounts at a vendor.
- The rotation and prompt-cache policy of 1055, usage views (1082, 1340, 1375), model tracks and provider order (1339), extension pairing (1394).
- Managed Codex, API-key, Console and cloud-billed instances: listed and labelled, otherwise unchanged.
- Existing code that reads login files: increment 1401.
- Other providers (Cursor, Grok, Copilot, Muse).
- A remote machine, a browser client or the mobile app: today's flows stay; nothing there starts a sign-in for these accounts.
- Stopping a person or an agent with a shell from running `claude auth login` or `codex login` themselves. A local shell acts with the person's own authority.

## Approach

**An account is a provider instance with an `account` block.** `packages/contracts/src/providerInstance.ts` gains `account: { expectedEmail, browserProfile? }`, where `browserProfile` is `ExternalBrowserTarget` (`packages/contracts/src/externalBrowser.ts:51`). `ProviderInstanceRegistry.ts` passes it through the driver create input (`apps/server/src/provider/ProviderDriver.ts`).

**Identity is computed where it is read.** `ServerProviderAuth` (`packages/contracts/src/server.ts:66`) gains `accountKey`, `accountKeyObservedAt` and `planClass` (`free`, `personal`, `organisation`, `unknown`). Each driver sets them in the probe that already reads the account, with that probe's time:

- Claude: from the `email` and `organization` the SDK reports at initialization (`apps/server/src/provider/ClaudeProvider.ts:543-556`); `planClass` from `subscriptionType`.
- Codex: from the account id the driver already hashes into `quotaPoolId` (`apps/server/src/provider/codexUsageLimits.ts:215-219`); `planClass` from `planType` (`apps/server/src/provider/CodexProvider.ts:116`).

The key is `<provider>:acct:sha256:<hex>` and leaves the plan out, unlike `claudeSubscriptionKey` (`apps/server/src/provider/subscriptionIdentity.ts:28-37`), so a plan change is not a new account. No email or id means no key and no "Same account" line. The mapping lives in new `accountIdentity.ts`. For Codex the id arrives with the rate-limits read (`apps/server/src/provider/CodexProvider.ts:583-587`), so the key and its time are absent when that read fails. Both probes rerun on the provider health refresh (five minutes by default, `packages/contracts/src/settings.ts:1535`), but that refresh runs only while some client is watching provider status (`apps/server/src/provider/makeManagedServerProvider.ts:420-427`, `apps/server/src/background/BackgroundPolicy.ts:74-76`). With nobody watching, the key is as old as the last probe; T-02 tests both cases, and 1400 rereads at decision time.

**The stamper compares and holds.** `withInstanceIdentity` (`apps/server/src/provider/Drivers/instanceIdentity.ts:13`) receives the `account` block and the draft, which already carries `auth.email` (`ServerProviderDraft`, `apps/server/src/provider/providerSnapshot.ts:105`). It stamps an `account` view on the snapshot: `emailCheck` (`match`, `mismatch`, `unconfirmed`, `unset`), the profile and `hold` (`wrong_account`, `unconfirmed`, or absent).

**A hold reuses the signed-out gates.** The held account's CLI is signed in and would run, so nothing may rely on it failing. The stamper publishes a held snapshot with `auth.status: "unauthenticated"`; the row reads `account.hold` for its wording. That one change is seen by every gate of both shapes at this commit: `!== "authenticated"` (`packages/shared/src/providerFallback.ts:230`, `apps/server/src/orchestration-v2/ProviderFallbackWorker.ts:1343`, `packages/shared/src/fallbackOptions.ts:142`, `packages/shared/src/coordinatorDefault.ts:39`) and `=== "unauthenticated"` (`apps/server/src/scheduledTasks/ScheduledTaskProviderRoute.ts:177`, `packages/shared/src/modelLanes.ts:335`, `packages/shared/src/modelTrackRules.ts:53`, `packages/shared/src/providerFallback.ts:693`). A message sent straight to a thread has no such gate, so new `apps/server/src/provider/accountHold.ts` holds one refusal that `apps/server/src/orchestration-v2/ProviderTurnStartService.ts` calls before it opens a session. That layer has no source of provider snapshots today (`ProviderTurnStartService.ts:241-256`), so T-03 adds `ProviderRegistry` (the one the fallback worker reads, `apps/server/src/orchestration-v2/ProviderFallbackWorker.ts:674`) to its requirements and provides it in `apps/server/src/orchestration-v2/runtimeLayer.ts:252`; the file is 1,955 lines, so the logic stays in `accountHold.ts`. "Ready but signed out" is a new combination: the sign-in panel treats it as not done and offers sign-in again (`apps/web/src/components/settings/ClaudeSignIn.tsx:88`), and the capacity view answers with a generic sign-in message (`apps/server/src/studio/Capacity.ts:606-610`). Both read `account.hold` first (T-03, T-07). Other surfaces that react to "signed out" (notices, limit return) now also react to a hold; T-03 lists them and the row's wording wins.

**Codex.** New `apps/server/src/provider/CodexAccountHome.ts` derives the login home for a new account with no home set (`<state>/providers/codex/<instanceId>/login`), the way `CodexManagedHome.ts:13-18` does for managed ones, prepares it as a shadow home (`CodexHomeLayout.ts:51-71`) before any use, and removes it per AC-07. `config.toml` is shared with the default home (`CodexHomeLayout.ts:398-404`; `:34` lists what stays private), so the credential store setting is the person's own: in `file` mode the login is that home's `auth.json`; in `keyring` or `auto` mode a credential-store entry keyed to that home's path (`codex-rs/login/src/auth/storage.rs`, `compute_store_key`); in `ephemeral` mode it dies with the process, which AC-03's second-process check catches. The existing file watcher (`CodexDriver.ts:353`) sees only the first, so after every flow, on Recheck and on the health refresh the app asks the CLI (`account/read`).

New `apps/server/src/provider/CodexCliLogin.ts`: a short-lived `codex app-server` for that home, built like the probe client with no protocol logger (`CodexProvider.ts:466-474`); `account/login/start` (already in the generated protocol, `packages/effect-codex-app-server/src/_generated/schema.gen.ts:53308`), the browser interaction, the completion notice, `account/read`; `account/login/cancel` on cancel; `account/logout` for sign-out. There is no fallback to `codex login`: it opens the default browser itself and cannot be pointed at a profile (`codex-rs/cli/src/login.rs`, saved text `:240-264`). On a Codex version without the call the row says "Update Codex to sign in here" and today's terminal hint stays. `codex login` also writes its own `codex-login.log` under the home (`login.rs:55-88`), which is why AC-14 searches that folder. The Codex CLI clears the current login before a new one (`login.rs:154-160`), hence AC-06's notice. The auth binding key is the account's login home, so `stopSessions` (`ProviderAuthService.ts:293-298`) stops that account's sessions only.

**Claude.** `ClaudeCliLogin.ts` adds `--email` and always suppresses the CLI's own browser when a profile is bound (`noBrowserProgram`, `ClaudeCliLogin.ts:209-218`). Its link matcher accepts any host today (`ClaudeCliLogin.ts:67-81`); it gains the host list.

**Opening the profile.** `ProviderAuthInteraction` type `browser` (`packages/contracts/src/providerSetup.ts:46-53`) gains an optional `target`. The client that owns the flow opens it with `openUrlInExternalBrowser(url, target)`. No launcher file, no new channel into the server, no Chrome extension relay (1394 found it accepts any local client).

**The profile's name and email.** The desktop app already reads both from Chrome's `Local State` (`apps/desktop/src/preview/BrowserImport/Sources.ts:352-362`, `user_name`) and carries the email as `account` on `ExternalBrowserProfile` (`packages/contracts/src/externalBrowser.ts`), so nothing new is read. It is a file of profile names beside the profiles, not a profile's storage or cookies. Agent tools return the profile's name only.

**Full Disk Access is not needed and nothing here is gated on it.** Chrome's profile list, `~/.claude-<name>` and the server's state folder are outside the folders macOS protects, and the logins themselves are never read with or without it (1386 decided what Full Disk Access is for).

**One flow at a time.** A machine-wide single-flight in `ProviderAuthService.ts`, since two pending vendor pages cannot be told apart.

**Agents: the client that presses "Sign in" owns the flow.** Sign-in state is filtered by owner: any other session gets the link and the interaction blanked (`apps/server/src/provider/ProviderAuthFlow.ts:515-530`), and the owner is the session that called `providerAuthStart` (`apps/server/src/ws.ts:2602`). A tool handler has no session, so the server never starts an agent-requested flow. The tool calls `OrchestratorMcpService.requestAccess` (`apps/server/src/mcp/OrchestratorMcpService.ts:3380`) directly, not `ensureAccess`, so no stored grant is consulted (`apps/server/src/access/accessGate.ts:141-171`), with a new subject kind `providerAccountSignIn` (`packages/contracts/src/accessRequest.ts:9`). A subject of that kind carries the account's `providerInstanceId`, which the start call needs (`packages/contracts/src/providerSetup.ts:112-118`) and today's subject lacks (`accessRequest.ts:20-33`). Its only positive answer is a new `{ type: "proceed" }` with no scope; `allow` with a scope (`accessRequest.ts:43-49`) is refused for this kind, and `proceed` for every other. For that kind `AccessRequests.answer` writes no grant (`apps/server/src/access/AccessRequests.ts:253-256`). The glyph switch in `packages/client-runtime/src/accessRequest.ts:66-78` is exhaustive and gains the kind. And `AccessRequestCard.tsx` renders new `AccountSignInCard.tsx` in place of the three scope buttons. On "Sign in" the desktop client (`window.desktopBridge` present, the card's environment is its own machine) calls `startProviderAuth` as Settings does (`apps/web/src/components/settings/ClaudeSignIn.tsx:66`), which makes it the owner, then answers the card with `proceed` and shows the same sign-in panel on the card. The tool handler then watches that instance's flow as a non-owner, which carries no link, until it ends or 10 minutes pass. A client that answers the card without starting a flow only makes the tool time out. Agents cannot click in SpecWithCode itself (`accessGate.ts:26-31`), so a tool-only agent cannot answer its own card. A caller that is an external MCP client has no thread to hold a card (`apps/server/src/mcp/McpInvocationContext.ts:63-78`) and is refused.

**Terminal.** One endpoint, `POST /api/studio/provider-accounts`, in the `studio` group (`packages/contracts/src/environmentHttp.ts:1082`; that file is 1,635 lines, so the schemas go in new `packages/contracts/src/providerAccountsHttp.ts` and one `.add` is added). Its handler is new `apps/server/src/provider/accountsHttp.ts`, registered from `apps/server/src/studio/http.ts:63` under the operate scope with the same origin check as that group's other changes (`studio/http.ts:28-47`), because it prepares a home and returns paths. A request with a bearer token and no `Origin` passes that check (`apps/server/src/auth/requestOrigin.ts:14-18`), and the local CLI's credential holds the administrative scopes (`apps/server/src/auth/LocalCliCredential.ts:59`); T-09 tests the CLI's own request against it. It returns each account's ids, name, state, plan, the environment variable name and the home path, and prepares a Codex account home before answering. The CLI reaches it the way other commands reach the running service (`apps/server/src/cli/liveService.ts:1-15`). The answer holds paths and no login material.

**Delivery.** Three stacked pull requests in the app repository: server (T-01 to T-05), interface and docs (T-07), tools and CLI (T-08, T-09). T-08 and T-09 touch disjoint files and can run in parallel after T-05. The skill (T-10) lands in vskill after the release that has the tools.

**Rejected.**

| Alternative | Why not |
|---|---|
| A script, agent or debugger approves on the vendor's page | Anthropic's Consumer Terms bar "automated or non-human" access; passkeys, 2FA and robot checks need the person anyway. |
| Read Chrome's profile storage or cookies to skip the vendor's page | Takes the person's vendor session; the same clause, and it reads another program's secrets. |
| Keep a long-lived token per account | Anthropic: developers "may not collect, store, or intermediate" them. |
| Copy `auth.json` or credential-store entries between homes | Reads the CLI's token store. |
| A `BROWSER` launcher that forwards the link to the server | A new local channel that could be made to open any link in the person's profile. T-06 only measures a launcher that starts Chrome directly. |
| The link through the Chrome extension relay | Unauthenticated loopback clients (1394). |
| The server starts the flow after an Allow on the standard access card | An Allow there is a grant for 30 days or for the machine, so later sign-ins would run unasked, and no client would own the flow to open the link or take Claude's code. |
| A sign-in command in `specweave-studio accounts` | It would add a second way in with no card; the terminal already has the CLIs' own login commands. |
| "Use first" button or a "First for <provider>" label | Under 1339 the provider is chosen per model family and `defaultModelProviders` is only a tie-break (`packages/contracts/src/settings.ts:1656`, 1339 spec line 88), so no single setting means "first". |

**Threats and answers.**

| Threat | Answer |
|---|---|
| Someone else completes the sign-in first (the link is on Chrome's command line, which other OS users can list; it is also in the profile's history) | The CLI accepts only a callback carrying its own `state` (T-04 tests a wrong one is refused). An account that signs in with another email is held (AC-05). The link is single use and the flow ends in at most 10 minutes. |
| A link or code reaches a log, transcript or disk | Per-sink tests (AC-10) for what the app writes; AC-14 searches the real logs for what the CLIs write. |
| A tool-only agent is talked into a sign-in | A card every time, pressed by a person in the desktop app, with the consequences on it; one flow at a time; no tool changes the account in use. |
| An agent with a shell signs an account in or out | Not prevented, and not claimed. A shell can run `codex login` or `claude auth login` with the person's authority, with or without this increment. The skill tells agents not to; the hold catches a wrong account afterwards. |
| A hostile page during sign-in | Only hosts on the list are opened; the app never types or clicks there. |
| A sign-in replaces a working login or stops work | AC-06's notice, cancel and timeout; the binding stops that account's sessions only. |
| The wrong account, silently | Required expected email, `--email` hint, the hold on a mismatch or an unreadable identity. |

**Risks.** `account/login/start` at the oldest supported Codex version is unverified until T-04; without it that version keeps the terminal. Real sign-ins cannot run in CI. `ProviderInstanceCard.tsx` is 1,189 lines, so the list is new files. OpenAI has not said whether several ChatGPT accounts may be signed in to Codex on one machine and used at once; AC-08 does that. Running a vendor's CLI inside a product has its own terms (terms report, "Beyond this increment"); that is a product question for Anton and counsel, not introduced here.

- D-04 The Chrome profile is a browser profile opened by the desktop app, not a paired extension profile.
- D-05 The expected email is required for a new account. A mismatch, or a signed-in CLI that reports no email, holds the account.
- D-06 Agents can list accounts and ask for a sign-in; a person presses "Sign in" on a card each time. Agents cannot change the account in use. The terminal command starts no sign-in. None of this limits what a shell can do.

- D-09 Removing an account keeps a Claude directory and any home path the person set.

- D-12 A held account is published as signed out, with the reason beside it, so the existing gates apply.
- D-13 No Full Disk Access gate: nothing in this increment reads a protected folder. Anton raised it on November 18, 2026 ("only, I believe, when we have full disk access"); say so if a gate is wanted anyway.
