## [high] The final queue boundary still fails open

`apps/server/src/orchestration-v2/ThreadManagementService.ts:602-622,654-665` maps `queue` to `queue_after_active` and distinguishes `queued` from `started`. The receiver discards that distinction and marks the row delivered. No timing race is necessary: a usage-limit stop can leave no active run, so the receiver's idle check passes, but the orchestrator explicitly queues automatic notifications behind that stop (`apps/server/src/orchestration-v2/Orchestrator.ts:6459-6477,6583-6589`). On recovery the queue consumer checks the destination, not the sender's live authority (`apps/server/src/orchestration-v2/Orchestrator.ts:1917-1952`). A revoked sender's text can therefore start a new turn. Keep the row in the receiver until dispatch can start atomically, or carry its authority binding to queue consumption and check it there. A legitimately running turn need not be interrupted.

## [high] The request can create the policy before checking for it

`apps/server/src/handoff/handoffRoute.ts:165-171` authenticates the credential, then calls `grants.forClient`. That lookup settles the policy and inserts a default record when the authenticated coordinator has none (`apps/server/src/fleet/WorkGrants.ts:424-436,448-463,482-495,517-524`). The default for this path allows all accounts and at least linked projects (`apps/server/src/fleet/workGrantPolicy.ts:103-107`). Even `grants.policies` calls a read that initializes a missing file with legacy all-project/all-account policies for live coordinators (`apps/server/src/fleet/WorkGrants.ts:343-367,763`). The later missing-row refusal at `apps/server/src/project/CoordinatorMessageReceiver.ts:331-346` cannot distinguish a pre-existing policy from one created by this request. This is not an anonymous pairing bypass. Use a lookup that neither settles nor initializes authority, at admission and delivery.

## [high] The admitting credential and capability are snapshots

`apps/server/src/auth/EnvironmentAuth.ts:1614-1624` returns the authenticated session ID and derives access from operate scope. That session can be revoked independently of the peer work policy (`apps/server/src/auth/EnvironmentAuth.ts:1342-1346`). The route passes only an `operate` boolean (`apps/server/src/handoff/handoffRoute.ts:311-321`). The row saves it, the advertised capabilities and a policy timestamp pair; flush reuses those values. An actionable message can pass after its session is revoked even when dispatch starts immediately. The capability check likewise proves what the sender advertised at admission, not what it advertises at delivery. Bind the row to a verifiable approval instance and validate it at consumption; do not describe the stored capability list as a fresh negotiation.

## [medium] Rejoining does not invalidate traffic from the previous membership

`apps/server/src/project/LinkedPeerRoute.ts:138-150` matches the peer environment and logical project. Unlink removes a member without changing the surviving copy's logical project ID; rejoin records a new `linkId` and generation (`apps/server/src/project/ProjectLink.ts:674-683,781-792,842-851`). If both changes happen before flush and the grant is unchanged, the old row passes under the new membership. Compare the membership identities that admitted the row, not just machine and project IDs.

## [medium] Step and reference membership is checked only on arrival

Admission checks the step and each machine-bound ref. Before framing an ordinary message, flush checks local thread ownership again, but `placeRefs` accepts non-thread refs unchanged and the frame uses the original step (`apps/server/src/project/CoordinatorMessageReceiver.ts:195-201,375-397,430-447,735-746`). If a third machine leaves while sender and receiver remain members, a step or read instruction naming that machine still reaches the agent. This establishes an out-of-project instruction, not a successful file transfer or disclosure. Apply the current member set to steps and machine-bound refs before framing.
