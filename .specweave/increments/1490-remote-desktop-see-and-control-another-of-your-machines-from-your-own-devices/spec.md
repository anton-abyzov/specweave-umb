# 1490 Remote desktop: see and control another of your machines from your own devices

This increment holds the whole plan (`plan.md`) and builds slice 1: view another Mac's screen, view-only. Control, WebRTC, TURN, the phone, Windows and Linux are later increments, listed in `plan.md`.

Access change. Anton approved building it on November 25, 2026. Nothing here is on by default and nothing gives an agent the screen.

## Problem

On November 25, 2026 Anton asked: "is there some kind of a remote control where I could technically go ahead and see and control, through the UI, what is exactly happening on my machine? Maybe clicking some buttons, like logging in to the server in Google Chrome, leveraging my Touch ID." Then: "add passkey QR, and plan full remote desktop, go ahead and implement it with security in mind."

Today the owner can reach another of their machines only through threads, the terminal and files. To see what is on its screen they need macOS Screen Sharing, a third-party tool, or a trip to the desk. 1488 covers one Chrome tab for a website sign-in. Nothing shows the whole screen.

What the code has today (app at `origin/main` `61f3e8baa`):

1. **Capture is one still per request.** Computer use runs `/usr/sbin/screencapture` to a temp file (`apps/desktop/src/computerUse/MacComputerUse.ts:221`), main display only. Measured on M5: 0.5 to 0.8 s per capture, 3024x1986, about 750 KB as JPEG.
2. **Input is one `osascript` per action**, yields to the person at the machine and refuses the app's own windows (`computerUseJxaScripts.ts:54-58`, `MacComputerUse.ts:336-338`). It is built for agents, not for a person's pointer.
3. **The computer-use host is the app window's renderer.** A Mac with no window open has no host (`apps/web/src/state/computerUse.ts:68-101`). Any session with `terminal:operate` can register as host with a self-declared platform (`apps/server/src/auth/RpcAuthorization.ts:51-53`).
4. **No guard means "a person's approved device".** `principal.kind === "device"` is the default for every session (`SessionStore.ts:945`). `deviceApprover` also admits the startup link and dev tokens (`deviceApprover.ts:43-48`). `access.answerRequest` needs only `orchestration:operate`, so a remote window or a management key can answer an access card (`RpcAuthorization.ts:208`).
5. **Connect ends TLS at Cloudflare.** The tunnel is a proxied hostname to `http://127.0.0.1:<port>` (`infra/relay/src/environments/ManagedEndpointProvider.ts:1268-1313`). No client pins a machine key (`seal.ts:7-9`). A WebSocket ticket is valid 5 minutes and is not single-use (`SessionStore.ts:568`).
6. **No WebRTC sender, STUN or TURN exists.** The one `RTCPeerConnection` is a viewer for simulator streams (`packages/client-runtime/src/device/stream.ts:911`).

## Threat model

- **Adversary: the network path, Cloudflare's edge included.** It can read, drop, replay and change traffic, and replay a WebSocket ticket it saw. It must not see the screen, start a session, or change one.
- **Adversary: any session that is not a person's approved device.** Agent threads, worker grants, outside MCP clients, management keys, the local CLI credential, pairing tokens, the startup link. None may view, host, approve or switch the feature on.
- **Adversary: an agent working through what the app gives it** (thread tools, MCP, RPC, HTTP routes, settings files, a click sent through computer use). It must not be able to switch the feature on, add a grant, answer the prompt or view. Turning on and every Allow need system authentication (Touch ID or the account password in the system's own dialog), which a synthetic click cannot give. What a synthetic click can still do: press Deny, and press Allow so that the system's dialog appears at a moment the agent chose. The dialog names the exact choice and the device, one dialog is up at a time and its answer counts only for that choice (AC-08); a person who authenticates without reading it is not defended.
- **Not defended: a process running as the same user on the target, an agent's shell included.** It can already take screenshots under the app's Screen Recording grant (measured in `reports/capture-spike.md`) and post clicks under its Accessibility grant, so screen sharing gives it no screen it lacks. The build also leaves Electron's run-as-node and inspect switches on and turns library validation off (`scripts/build-desktop-artifact.ts:1467-1471`), so such a process can run code as the app, read the store and stand in as the host. The prompt, the banner and the session list are evidence about remote devices and people, never about a local process. Running code as the app, it needs no window and no authentication: it can read the machine key and the store and serve a viewer with no prompt, no banner and no entry in the session list. Nothing in this increment limits it on the target. One thing limits it elsewhere: a process that only stands in as the host, without reading the store, lacks the machine key, and a viewer that saved that key refuses it.
- **Trusted:** the relay Worker as a broker of who owns which machine (`docs/studio/security.md:58`), the approved-device list of 1327, macOS privacy grants, and the app's own code signature.
- **Out of reach (stated, not solved):** a person at the unlocked machine who knows its password; macOS itself. A viewer opened in a plain browser tab cannot stop a screenshot taken by something else on that device. A same-user process on the target can put back an older copy of the store that the owner once approved.

## Scope

In (slice 1, macOS, view-only):

- A switch per machine, "Screen sharing", off by default, changed only in that machine's own app behind system authentication.
- A viewer for the owner's approved Connect devices (the desktop app or a browser signed in to Connect): "View screen" on a connected machine's card.
- Approval on the target for each session, drawn by the app's main process and confirmed with system authentication, or a per-device "Always allow" grant made there the same way. The first time a device views a machine, a person at that machine reads a code off its prompt and types it on the device.
- An always-on-top banner with Stop on the target for the whole session.
- An end-to-end encrypted session between the viewer and the target app, signed with the viewer's approved device key and with a machine key the viewer pins.
- Frames: JPEG, up to about 3 per second, sent only when the screen changes, with the pointer position. A locked Mac shows a placard, never the lock screen.
- A session list on the target (audit), timeouts, one session at a time.

Out (later increments, see `plan.md`): pointer and keyboard control; WebRTC video and TURN; the iPhone app; Windows and Linux targets; clipboard and file transfer (off by default when they come; files stay on `studio_file_transfer`); audio; several viewers at once; viewers on LAN, SSH or pairing-code routes (they hold no approved device key); a Mac with no app running or no logged-in desktop; any MCP tool, RPC or agent path to the screen.

## Acceptance Criteria

- [ ] AC-01: Screen sharing is off on every machine until its owner turns it on there. While it is off a viewer gets "off" at once: no prompt, no capture, no banner.
- [ ] AC-02: The switch and the per-device grants change only through the target app's own windows. Each turn-on and each grant needs system authentication (Touch ID, or the account password in the system's dialog) run by the main process; when it fails, is cancelled or is unavailable, nothing changes. No HTTP route, RPC, MCP tool or `settings.json` key changes them. The store is encrypted with AES-256-GCM under a key wrapped by `safeStorage`, with its purpose and version authenticated: a file that was edited, replaced, copied from another machine or cannot be read is treated as off with no grants and a new machine key, and Settings says the store was reset. Where the system cannot encrypt, the feature cannot be turned on and Settings says so. Limit: putting back an older valid copy is not detected (Threat model).
- [ ] AC-03: The server opens a viewer socket only for a Connect or phone-link session whose device key (`jkt:`) is on this machine's approved list and that holds no coordinator principal. A test refuses each other class by name: management key, `mcp-client`, `local-cli-owner`, `one-time-token`, startup link, dev tokens, the desktop app's own session, a phone link with no key, a Connect session with an unapproved or missing key, and a session carrying `boundDevice`.
- [ ] AC-04: The server accepts a host socket only from the machine's own app session (`desktop-bootstrap`, loopback, not over Connect, not a bot), and only once its first message carries the app's proof, checked on every connection: the owner proof against the verifier file, or, for a backend the app started, a host proof made from the launch secret under its own label. That proof is not the bootstrap token the app's window holds, and the token does not pass as it (tested both ways). It lasts 10 minutes either side, the app sends a new one every 4 minutes over the open link, and the server checks the latest proof of either kind again when a viewer opens and drops a host whose proof no longer holds. A later host with a valid proof replaces the earlier one. The app, when refused or replaced, says so in Settings on that machine and records it. Every other class is refused in a test. Limit: against a same-user process that rewrites the verifier, the check and the recheck add nothing, because both read that process's own file; only the real app attaching again evicts it (Threat model). A `desktop-bootstrap` session made that way also stays valid for everything else it can reach until it expires; this increment does not change sign-in revocation.
- [ ] AC-05: A session starts only after the viewer signs the handshake (machine id, session nonce, both session keys, mode, its own commitment) with its device key, in a JWS whose `typ` is not DPoP's. The viewer's hello commits to a random value that only the signed proof reveals, so neither side can steer the first-use code. The target refuses a signature from another key, a key that differs from the one the server attested, a stale or replayed nonce and a changed handshake. The DPoP verifier refuses this JWS and the session verifier refuses a DPoP proof.
- [ ] AC-06: The target signs the handshake with its screen-sharing key. A viewer that has saved this machine's key refuses any other key and says so. First use is the target's own decision: a device is past it only when the target's store records that its person typed this machine's code, and the viewer also says it has the key saved; what the viewer says can add a first use, never skip one. On first use the target ignores any grant and asks; its prompt shows a 6-digit code made from this session's secret and the revealed random; the viewer shows only a field to type it into. The viewer draws no frame and saves no key until the typed code matches its own, and the target sends no frame until it receives the viewer's sealed confirmation with the right code. Three wrong codes end the session. A test presses Allow with mismatched codes and never reaches live. Who the code protects: the person at the viewing device, against a stand-in machine. A viewer changed to skip its own comparison can compute the code and harms only itself; what protects the target is the device's signature, the prompt and system authentication. So the first view of a machine from a device needs a person at it, enforced by the target: with no record there is always a prompt, and a prompt needs system authentication. Removing a device forgets the record.
- [ ] AC-07: After the handshake every message is sealed between the viewer and the target app. A test relay that flips a bit, replays a record or reorders two ends the session and shows nothing. The server process holds only sealed bytes: a test shows the relay cannot open a record. Logs, threads and the session list never hold a frame. No frame is written to disk except the fallback capture's own file, in a `0700` folder, deleted after the read.
- [ ] AC-08: With no grant, the target shows a prompt with Deny, Allow once and Always allow. It names the device by the name on this machine's approved list and its short ID; a different name the device gives for itself shows only as a second line. Allow once and Always allow each need system authentication; Deny is a click and wins at any point before the screen is shown. The system's dialog names the choice ("this once" or "always ... without asking again") and the device with its short ID; only one such dialog is up at a time, a press while one is up does nothing, and an answer counts only for the session and the choice it was asked for (dropped when that session ended, was denied, or the switch was used again meanwhile). Answers are accepted only from the prompt window's own frame. No answer in 60 seconds is Deny. One handshake and one prompt at a time: anyone else gets "busy". A handshake has 15 seconds to finish. Three refusals, timeouts or unfinished handshakes for one device in 10 minutes stop prompts for that device for 10 minutes, and the count is kept in the store across restarts. Hello, challenge and proof messages over 64 KB, sealed records from the target over the frame limit and sealed records from a viewer over 64 KB are dropped by the relay and end the session; so does any text from a viewer. The relay keeps bounds of its own that hold whatever the app does: 20 seconds for the handshake, 5 more for the app's first sealed word, a longest session life (2 hours plus the asking), and 12 opens per device in 10 minutes. One WebSocket message is still read whole before its size is known; that is the server's WebSocket limit, not this feature's.
- [ ] AC-09: From before the first frame until the session ends, the target shows an always-on-top banner on every desktop naming the device, with the elapsed time and Stop. Stop ends the session within 1 second. If the banner cannot be shown or is destroyed, the session ends. Turning the switch off ends it too.
- [ ] AC-10: Slice 1 is view-only: the target accepts only "frame received", "show display N", "end" and the first-use code from the viewer. Any other message ends the session. The host code imports nothing from `computerUse`.
- [ ] AC-11: A session ends: after 2 hours; after 2 minutes with no "frame received"; when the device is removed from the approved list (within 5 seconds); when its sign-in is revoked (at once in the same server process, within 30 seconds from another); when its sign-in expires (at the expiry time, by a timer on the socket; a sign-in with no expiry is refused at the door); when its grant is removed or the switch is turned off at the target (at once); when the viewer's socket closes; when the app quits. A grant ends 30 days after its last use. One session at a time: a second viewer gets "busy". Not an end cause: another account signing in on the viewing device. The session belongs to the device key the target approved, not to an account; signing out closes the viewer and with it the socket, and a new sign-in opens a new session that meets the grant or the prompt for that same device key.
- [ ] AC-12: The target keeps the last 500 session attempts: time, device name and short ID, how it was allowed or why it was refused, start, end and the reason it ended. Settings > Machines > Screen sharing lists them on that machine. No entry holds a frame.
- [ ] AC-13: While the target is locked the viewer gets a "This Mac is locked" placard and no frame. Lock state comes from `powerMonitor`'s lock and unlock events and from `getSystemIdleState` read before and after every capture: a frame whose capture met a lock, or an unknown state, is dropped. During a session the display is kept from sleeping; a display already asleep is not woken, and after 10 seconds with no picture the viewer says the display may be asleep.
- [ ] AC-14: Frames are at most 1920 px on the long edge, sent only when the picture changed, one unconfirmed frame at a time. The pointer position comes from `screen.getCursorScreenPoint`, mapped to the frame; both capture paths leave the cursor out of the picture. In the fixture run the viewer draws each frame and the pointer mark at the reported position.
- [ ] AC-15: "View screen" shows on another machine's card only when that machine reports the capability and this device is approved there. The viewer shows each state in words: connecting, waiting for approval, type the code (first use), live, locked, ended (with the reason), off, busy, not available on this system. With two displays the viewer can switch. End closes it.
- [ ] AC-16: No MCP tool, RPC or thread item reaches screen sharing: a test lists the MCP tools and the guarded RPC map and finds nothing; for HTTP it checks by behaviour that only the two socket paths answer (every other path under the prefix, and any non-WebSocket request, is 404 before sign-in is read), and by source that no server file outside the feature's folder names screen sharing beyond the guard, the capability flag and the one mount, so nothing else can reach the relay. Limit: the source half is a text check, not a walk of the running router. While the app shows another machine's screen, the computer-use tool on the viewing machine refuses a whole-screen screenshot with a reason. That binds the tool, not a shell (Threat model).
- [ ] AC-17: A Windows or Linux target, or a Mac with no app running, answers "not available" and the card says why. No switch shows there.

## Approach

Full design, alternatives and later slices: `plan.md`. In short:

- **The target app's main process is the authority.** It holds the switch, the grants, the machine key and the audit list in one authenticated store whose key `safeStorage` wraps, draws the prompt and the banner, captures the screen and ends the encryption. The server only checks who is calling and passes sealed bytes between two sockets.
- **Transport: two WebSockets through the existing server**, `GET /api/screen-share/host` (the app) and `GET /api/screen-share/view` (the viewer), on the pattern of `/api/preview-stream/ws`. No new RPC group, so `rpc.ts` and `ws.ts` are untouched.
- **Channel:** X25519 key agreement, HKDF-SHA256, AES-256-GCM with a counter per direction, in one module shared by the browser and the app (`packages/shared/src/screenShareChannel.ts`): `@noble` for X25519 and Ed25519, WebCrypto for AES-GCM.
- **Capture:** `desktopCapturer` stills in the main process, with `screencapture` as the fallback (`reports/capture-spike.md`).
- Order: contracts and channel, server guard and relay, desktop store and session logic, desktop windows and IPC, web viewer and settings, docs.

Risks: the Screen Recording grant is read once at launch, so a fresh grant needs the existing relaunch step. `apps/server/src/server.ts` (1,750 lines) and `packages/contracts/src/ipc.ts` (1,640) are already over the 1,500 limit and `MachinesSettings.tsx` is at 1,351, so each gets an import and a mount only: routes register through a `routeLayer`, IPC types live in `packages/contracts/src/screenShare.ts`. Live capture on a signed build cannot be proven from a worktree; see Decisions, Open.

## Decisions

### Asked
- D-01 Where may screen sharing be turned on? → only at that machine (Anton, November 25, 2026). m1 and m3 each need one visit to turn it on and press "Always allow" for his devices.
- D-02 A locked Mac → a "This Mac is locked" placard; the lock screen is never sent and cannot be unlocked remotely (Anton, November 25, 2026).
- D-03 TURN relay spend (slice 4) → yes, capped at Cloudflare's free 1,000 GB a month; at the cap sessions fall back to frames (Anton, November 25, 2026). The relay can only stop issuing credentials on its own estimate; whether overage blocks or bills is a setting on the Cloudflare plan, which the owner confirms before slice 4 (`plan.md` section 6).
- D-04 Password fields over remote control (slice 2) → nothing is typed into any secure field; clicks still work; website sign-ins go through the 1488 sign-in view (Anton, November 25, 2026). 1438 D-01 stands. The review found this cannot be kept as worded for web pages; see Open.

### Defaulted (change any before sw-do)
- D-05 Slice 1 sends encrypted JPEG frames over the existing connection, not WebRTC. The brief asked for WebRTC over the relay with TURN; that is slices 3 and 4. Reasons: no sender-side WebRTC exists, Connect is optional so a non-WebRTC path is needed anyway, the iPhone app has no WebRTC library, TURN is spend, and frames need no new network path to review.
- D-06 Viewers are approved Connect devices only. A window paired by code, on LAN or over SSH has no device key to sign with and is refused.
- D-07 The app's main process, not the server, decides and encrypts. The server is one more hop that sees ciphertext.
- D-08 Approval is a main-process window, not the access card: a remote window or a management key can answer `access.answerRequest`.
- D-09 "Always allow" is per device and view-only, ends 30 days after its last use, and is offered only when a person presses it at the machine.
- D-10 Numbers: prompt 60 s, session 2 h, silence 2 min, cooldown 3 in 10 min, 500 audit entries, 3 frames per second, 1920 px.
- D-12 Control comes before WebRTC (slice 2 before slice 3): clicking a button works at a few frames per second, and it is what the owner asked for first.
- D-13 Turning on, Allow once and Always allow each need system authentication (`systemPreferences.promptTouchID`: Touch ID, Apple Watch or the account password). A click alone never allows, because a click can be synthetic.
- D-14 The first view of a machine from a device needs a person at that machine to read a code. The target decides what a first view is, from its own record (AC-06). It fits D-01: the same visit turns the switch on and presses "Always allow".
- D-15 Electron's run-as-node and inspect switches stay as they are in this increment; the app starts its own helpers through them. Closing them is its own change (`plan.md` section 10).

### Open
- Live capture on a Developer ID build is unproven until a release is installed and the owner turns the switch on at a Mac. Recorded as a proof limit in `reports/`.
- 1488 needs the same person-device guard (its AC-07), a device-key signing helper in `apps/web/src/cloud/dpop.ts` and a `packages/shared` export. The guard is `apps/server/src/auth/personDevice.ts` and the helper is `signWithDeviceKey(typ, payload)`; whoever merges second imports the other's.
- A Mac with no Touch ID sensor in reach (Mac mini, Mac Studio, a laptop with the lid closed): Electron's prompt asks for user presence, which should fall back to the account password, but this is unverified. If it rejects there, screen sharing cannot be turned on at that Mac until a password path is built.
- D-04 for web pages (before slice 2): macOS reports secure input for system and native password fields only. A password field on a web page looks like any text field. Either remote typing may enter them, or typing into browsers is off and every website sign-in uses 1488. The owner chooses.
