## [minor] R2-7. The relay keeps the raw owner proof in server memory for the life of the host socket

Files: `apps/server/src/screenShare/ScreenShareHttp.ts:179-196`, `apps/server/src/screenShare/ScreenShareRelay.ts:82-87` and `:115-118`, `apps/server/src/auth/deviceApprover.ts:126-129`, `plan.md:21-22` (the server "passes bytes it cannot read").

The viewer-open recheck works by keeping the proof string itself in the relay's host record (`credential`) and re-running `proofKind` on it later. The owner proof is a bearer secret: whoever holds it can mint the app's `desktop-bootstrap` session class at token exchange. Before this feature the server held only the verifier, a SHA-256 digest it cannot spend (`desktopOwnerProofMatches`, `deviceApprover.ts:126-129`). Now a long-lived, spendable copy sits in the heap of the one process every session class can reach, for as long as the app stays attached, which is normally the app's whole run. Any server memory disclosure, heap snapshot or debug surface gains more than screen sharing needs it to have. It is also the kind of value that ends up in a log line during future debugging; today it is not logged (`ScreenShareHttp.ts:182` logs only the kind).

Nothing about the recheck needs the secret. It needs to know whether the verifier file still says the same thing it said at attach. Store the digest instead: at attach, keep `SHA-256(proof)` (which is exactly the verifier's format), and at viewer-open compare those bytes with the file's current bytes in constant time. Equal means the proof that attached still matches; different or unreadable means `dropHost`, as now. That keeps the eviction behaviour of `ScreenShareHttp.ts:192-196` and removes the credential from the process that the design elsewhere insists should hold nothing worth stealing. A test can pin it cheaply: attach, rewrite the verifier, open a viewer, expect the host dropped, and assert the relay exposes no accessor returning the proof. The same change makes the `launch` asymmetry in R2-1 harder to reintroduce, because there is no longer a reason for one proof kind to be stored and the other not.

## [minor] R2-8. AC-16's test greps source, and the capability flag says yes on machines that cannot share

Files: `spec.md:62` (AC-16), `spec.md:63` (AC-17), `spec.md:61` (AC-15), `apps/server/src/screenShare/noAgentPath.test.ts:44-68`, `apps/server/src/environment/ServerEnvironment.ts:331`, `packages/contracts/src/environment.ts:229-232`, `apps/server/src/screenShare/ScreenShareRelay.ts:216-220`.

AC-16 promises a test that inventories the MCP tools, the guarded RPC map and the HTTP routes and finds only the two guarded sockets. The route half of that test regular-expression-searches server source for three constant names or the literal path, asserts exactly one file matches, and asserts the guard's source text sits above the text `request.upgrade` (`noAgentPath.test.ts:44-68`). It never enumerates the router the server actually builds. A route added inside the same `router.add` wildcard in `ScreenShareHttp.ts`, a path spelled by string composition, or a second registration in that one allowed file all pass, and a refactor that renames `request.upgrade` breaks the test while changing no behaviour. The MCP half has the same shape: it greps toolkit file contents for "screen shar", so a tool that reaches the relay through an innocuous name and an import is invisible to it. For a criterion whose entire point is "no agent path exists", the test should walk the built route table and the real tool registry and compare against an allowed list, the way the relay half of AC-07 is now tested against real sealed bytes (`ScreenShareRelay.test.ts:224-229`). Until then AC-16 should be read as guarded by convention plus a tripwire, which is weaker than its wording.

Separately, the environment now reports `screenShare: true` unconditionally (`ServerEnvironment.ts:331`), on every platform and on a headless service with no desktop at all. AC-15 keys "View screen" visibility to the machine reporting the capability, and AC-17 wants unsupported targets to answer "not available" with the card saying why. With the flag always true, every machine shows the button and the explanation has to be reconstructed from the socket refusal (`no_host`, `unsupported`, `off`) by web code that is not written yet. That can be made to work, but then the flag means "this server build knows the routes", not the capability AC-15 names, and the contracts comment at `screenShare.ts:169` already half-admits it by noting no route serves the relay's status. Either make the capability mean what AC-15 says (an attached app on a supported platform reports it; the server alone does not) or rewrite AC-15 and AC-17 around refusal reasons and test that mapping in T-06. One related wart for the same fix: a host that has attached but not yet sent its first `status` leaves the relay at its default `OFF` with `supported: false`, so a fast first viewer is refused `unsupported` rather than asked to wait (`ScreenShareRelay.ts:47`, `:147`, `:218`). Section C records the host-side duty this creates.
