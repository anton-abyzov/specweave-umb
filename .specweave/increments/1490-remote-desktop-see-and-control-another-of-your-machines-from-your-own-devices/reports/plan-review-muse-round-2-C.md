# Round 2, section C: what a later builder would implement wrongly

Continuation of `plan-review-muse-round-2.md` (review at `900ff8dd9ab1`). Not findings against shipped code: each item is a place where spec, plan and the written layers leave two readings, and the wrong one still compiles and passes existing tests. Minor unless marked.

**C-1 [major] The binary framing is defined in a test, not in a module or the plan.** The relay keys binary messages on a first byte (`SCREEN_SHARE_WIRE`, `packages/contracts/src/screenShare.ts:56-62`), while the channel's parsers take decoded objects (`packages/shared/src/screenShareChannel.ts:258-295`) and its sealed record starts with a *record* type byte (`screenShareChannel.ts:617-620`; record types at contracts `:64-78`). The composition, wire byte prefixing the sealed record, exists only as test scaffolding (`apps/server/src/screenShare/ScreenShareRelay.test.ts:228-229`). Nothing states how hello, challenge and proof bodies are encoded after their wire byte (UTF-8 JSON is only a guess), or who strips the sealed prefix before the opener. The trap is loaded: `SCREEN_SHARE_RECORD.frameReceived` equals `SCREEN_SHARE_WIRE.sealed`, both 16 (contracts `:61`, `:71`), so raw channel records get viewer traffic half-accepted by coincidence and host frames (type 2) rejected. Add encode/decode helpers beside the constants, state the body encoding in `plan.md` section 3, and add one test running a real handshake through the relay's order rules.

**C-2 [major] Who counts the three wrong codes?** AC-06 (`spec.md:52`) says the viewer compares locally, saves the key and then sends the code sealed, and also says three wrong codes end the session; the target's state carries `triesLeft` (`packages/contracts/src/screenShare.ts:189-190`). If the viewer sends only after a local match, the target never sees a wrong code and `triesLeft` is dead. If it sends every typed attempt, local comparison is not the gate described. Both readings pass AC-06's test and differ in audit and cooldown behaviour. Pick one; say which side decrements and whether a wrong-code end counts toward AC-08's cooldown.

**C-3 The relay, not the click, tells the viewer which machine it is talking to.** Both ends take `environmentId` and `sessionId` from relay `open` messages (`apps/server/src/screenShare/ScreenShareRelay.ts:224-227`) and bind them into the transcript (`screenShareChannel.ts:180-195`). Differing values fail closed; identical values for the *wrong* of the owner's machines complete a genuine handshake. Nothing in AC-15 or T-06 (`spec.md:61`, `:140-141`) says the viewer compares `opened.environmentId` with the machine whose card was clicked, or which identifier keys the saved pin. State both, with a mismatch as its own viewer state.

**C-4 Cooldown counting has no trigger point.** AC-08 counts "refusals, timeouts or unfinished handshakes" (`spec.md:54`). Unfinished where: socket opened, hello forwarded, challenge issued, proof failed, prompt unanswered? That decides whether pre-proof abort-and-retry is free, and an abandoning viewer can compute the would-be code from each challenge, since it holds its DH secret and `r`. Only the host knows a hello arrived; only the relay knows a socket opened. Assign the counting point and component, jointly with R2-3.

**C-5 Handshake objects are reusable unless the caller remembers otherwise.** The channel is pure: a viewer start can answer several challenges, re-revealing the same `r` (`screenShareChannel.ts:322-346`, `:359-428`), and `acceptScreenShareProof` can run twice on one target start (`:494-551`). Reusing a viewer start after a fake or failed challenge hands a known `r` to the next session and defeats the commit ordering. The relay enforces one proof per session, not one start per session. State that both starts are single-use, discarded on any failure, timeout or retry.

**C-6 Sealed records flow the moment a proof goes by, valid or not.** The relay gates on order, not on the host having accepted the proof, finished the prompt or received the code (`ScreenShareRelay.ts:249-279`). The resulting endpoint duties are nowhere listed together: the host processes sid frames strictly in order and opens no sealed record, except the first-use `confirmCode`, before the session is live; the viewer opens `state` records to learn the phase while drawing no `frame` record until its code gate passed (AC-06, AC-10 at `spec.md:52`, `:56`). Write one state list per endpoint in `plan.md` section 4.

**C-7 The host must report status first, and nobody says so.** A freshly attached host is `OFF` with `supported: false` until its first `status` text (`ScreenShareRelay.ts:47`, `:147-168`), and `openViewer` checks `supported` before `enabled` (`:218-219`), so a viewer racing app startup is refused `unsupported` on a good Mac. T-04 should state the hello-then-status duty, whether status may change mid-handshake, and that a replaced host's late status is dropped by design (`:151-154`).

**C-8 Authentication leftovers for R2-4.** Whether a failed authentication counts toward a cooldown; whether pressing Allow twice stacks two system dialogs; what the prompt shows while the sheet is up; whether turn-off and grant removal deliberately need no authentication. A sentence each in AC-02 or AC-08, or T-05's first implementation decides.

**C-9 Small leftovers.** The AC-11 expiry timer does nothing when a session lacks `expiresAt` (`apps/server/src/screenShare/ScreenShareHttp.ts:220-224`); a guard test should pin that viewer-admissible sessions always carry one. An empty approved-list label passes `apps/server/src/auth/personDevice.ts:117` and would render a nameless prompt; specify a "Device <short ID>" fallback. AC-12's "every attempt" cannot include refusals the relay issued before the host heard of the session; scope it the way the threat model already scopes the list.
