# Round 2, section B (part 1): new holes the answers opened

Continuation of `plan-review-muse-round-2.md` (review at `900ff8dd9ab1`): R2-1 to R2-3.

## [blocker] R2-1. The `launch` host proof is the renderer's token, is never rechecked, and never expires on the socket

Files: `apps/server/src/auth/personDevice.ts:171-187`, `apps/server/src/screenShare/ScreenShareHttp.ts:179-196`, `packages/shared/src/desktopBootstrapToken.ts:16-45`, `apps/desktop/src/ipc/methods/window.ts:191-194`, `apps/desktop/src/backend/DesktopBackendConfiguration.ts:866-868`, `spec.md:50` (AC-04), `spec.md:69`, `plan.md:24`.

Attack: `ownAppProofKind` accepts the main-process `owner` proof, and also a `launch` proof: the current desktop bootstrap token, derived in 12-hour windows from the backend launch secret, with the previous and next windows also accepted, so a token can be good for roughly 24 to 36 hours (`desktopBootstrapToken.ts:16`, `:34-45`). That token is not a main-process secret. The window IPC hands `bootstrapToken` to the web code for every locally launched backend (`window.ts:191-194`), the desktop's own comment says "the renderer holds a single token" (`DesktopBackendConfiguration.ts:866-868`), and the secret itself goes to every backend the app launches. So on any backend started with a launch secret, code in the app's window, or anything holding the renderer's token, already has a `desktop-bootstrap` session over loopback and can open `/api/screen-share/host`, present the token as its hello proof, and attach as host. `attachHost` then replaces the real main process and ends its sessions (`apps/server/src/screenShare/ScreenShareRelay.ts:142-148`): no banner, no prompt, no audit, no machine key. That is round 1 finding 2's impact with no file rewritten, and it contradicts the design's own reason for putting authority in the main process rather than a window (`plan.md:24`).

Two compounding defects. AC-04 says "The proof is checked again when a viewer opens" (`spec.md:50`), but only the `owner` proof is stored; for `launch` the relay gets `undefined` and the recheck is skipped (`ScreenShareHttp.ts:179-180`, `:192-196`). And after the hello the host socket's deadline becomes `Effect.never` (`ScreenShareHttp.ts:184-189`), while the session watch does not end non-cookie sessions at expiry (`apps/server/src/auth/EnvironmentAuth.ts:1745-1748`), so the socket outlives the token's window indefinitely. The comment at `personDevice.ts:162-164` says the secret does not change while the process lives. The token does; that is its purpose.

Fix: at the host socket accept the owner proof only, since only the main process holds it, or prove the launch token reaches no renderer on slice-1 machines. Rechecking a launch token at viewer-open is not enough, because the renderer legitimately holds a fresh one. If `launch` stays for some backend shape, scope it in AC-04, recheck it like `owner`, end the socket when its window ends, and test that a renderer bootstrap token is refused as a host proof.

## [major] R2-2. The first-use gate is viewer-asserted and the confirming code is viewer-computed, so the target enforces neither

Files: `spec.md:52` (AC-06), `spec.md:94` (D-14), `packages/shared/src/screenShareChannel.ts:52-55`, `packages/shared/src/screenShareChannel.ts:370-372`, `packages/contracts/src/screenShare.ts:51-52` and `:76-77`, `plan.md:58`.

Failure: two things stated as target behaviour are viewer behaviour. First use reaches the target only as `hello.knowsMachine`, a boolean the viewer asserts. The honest library checks it against its own pin (`screenShareChannel.ts:370-372`), in the viewer. A viewer that lies, or whose pin store was cleared while a target-side grant survives, sends `true` and gets the grant with no person at the machine, and the target has no independent way to know, so AC-06's "the target ignores any grant and asks" cannot be built as written. Second, the sealed `confirmCode` is derived from values the viewer itself holds, so a correct one proves to the target only that viewer software chose to send it, nothing about a person reading the machine's screen.

The real protection stands, but it is one-directional: an honest viewer will not pin a fake target's key. AC-06 and D-14 should say so, and say the target sees an asserted flag. If the target is to enforce first use itself, it needs its own record, in the store next to the grants, of which devices completed a code exchange against the current machine key; a store reset then re-asks every device, which is what `spec.md:48` already promises. The browser viewer needs the same honesty: over Connect it loads its code, and keeps its device key, in the origin served by the machine being authenticated through Cloudflare-terminated TLS (`spec.md:19`), so the comparison is enforced by code an impersonator serves, while the desktop-app viewer gets the strong version. `plan.md:58` should carry that split, and the viewer wording must say the digits come from the other machine's screen, never from anything the viewer itself shows.

## [major] R2-3. The relay holds the one session with no deadline of its own; every time bound waits on the host

Files: `apps/server/src/screenShare/ScreenShareRelay.ts:205-245`, `apps/server/src/screenShare/ScreenShareHttp.ts:219-224`, `spec.md:54` (AC-08), `packages/contracts/src/screenShare.ts:33-34`, `plan.md:70`.

Failure: `openViewer` creates the relay's single session at once (`ScreenShareRelay.ts:221-223`) and nothing in the relay ends it for age. AC-08's 15-second handshake deadline and the 3-in-10-minutes cooldown are constants and spec text with enforcement assigned to nobody; the only socket timer is the viewer's session expiry (`ScreenShareHttp.ts:220-224`), which can be days away. An approved device, malware using its key, or a replayed ticket that passes the guard can open the viewer socket, send nothing, and hold "busy" for every real viewer (`ScreenShareRelay.ts:220`). The same squat works after a hello with no proof. A future desktop host can close sessions it dislikes, but a wedged main process, or R2-1's fake host, never sends that close, so the deadline cannot live only there.

Two smaller bounds leak in the same place. Viewer-to-target sealed records pass at frame size (`ScreenShareRelay.ts:257-261`) although everything a viewer legitimately sends is small JSON (`packages/contracts/src/screenShare.ts:70-77`), each costing the main process a 4 MB decrypt attempt in counter order. Viewer text frames are read and discarded (`ScreenShareHttp.ts:214-217`) with no size bound at this layer.

Fix: the relay owns per-session handshake deadlines and ends the session itself; cap viewer-to-target sealed records at a control size; set an explicit WebSocket payload limit on both sockets. State in AC-08 who counts a pre-proof abort toward the cooldown (section C).
