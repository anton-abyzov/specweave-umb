# Copy to another machine keeps ticked secrets, names what sends the ones left behind, and links both sides without the dialog

## Problem

A real "Copy to another machine…" run on November 16, 2026 (specweave project, m4 to the M5, both on SpecWithCode 1.0.322, "Copy everything", coordinator kept on m4) showed two bugs.

1. Secrets. The dialog defaults to secrets included, yet the destination record ended `withoutSecrets: true` with no secret file, and the source record has no `secrets` field although it listed 10 secret files. The m4 server trace has 19 `ws.rpc.machineHandoff.*` calls for this copy and not one `machineHandoff.copySecrets`, while the m4 window itself reported zero `RpcClient.machineHandoff.*` calls. So the copy was driven from the M5 window, signed in to m4 through Connect. A Connect session holds the standard scopes without `access:write` (`apps/server/src/cloud/CloudLink.ts:1818`), so the window is "denied": `useSecretsGate.ts:27` clamps the choice to none, `copySecretsPolicy.ts:36` sends nothing when nothing is staged, and `copySecretsPolicy.ts:87` approves `withoutSecrets`. The setup form does say so, but as muted helper text under a disabled box. The finish text then says "10 secret-like files (.env and similar) stayed on m4. Copy them yourself, or run the copy again with “Let me choose file types first” to send them." That option has not chosen secrets since November 13, and in this window no option can send them.

   Reading every approval path found two more ways a copy that said "included" ends with nothing sent:
   - The gate reads "unknown" until the source's session loads, so the form can say "included"; if it then turns "denied", the background watcher approves a one-click copy `withoutSecrets` with no screen in between (`HandoffFolderCopyWatcher.tsx:489-493`), and so does the dialog's own one-click approval for an older source (`HandoffFolderCopy.tsx:536-542`).
   - In a window that can send secrets, `sendTickedSecrets` returns without sending when the source's summary is unread (`HandoffFolderCopy.tsx:910`, summary cleared on reopen at `:592`, a failed read swallowed at `:493`), and the approval then goes out without `withoutSecrets` and with nothing staged.

   A pointer without a `secrets` field still reads as "left on the source" (`handoffFolderCopyPending.ts:274`); every copy started on 1.0.322 saves the field (`HandoffFolderCopy.tsx:752`), so that is not a live path.

2. Link. The M5 project was registered at 06:00:27 UTC but `workspaceSettings.logicalProject` was written on both projects only at 06:04:03, when the person reopened the dialog. In between, the M5 sidebar showed a second greyed "specweave" row under "On other machines". Only the mounted dialog links a finished copy (`useCopyLink.ts:71-75`); the background watcher sees the copy applied (`HandoffFolderCopyWatcher.tsx:589-599`) and only announces it.

3. Reopened dialog (found after PR 494 merged). Anton switched the M5 window to m4 and the "Send specweave to Anton M5MAX PROLED" dialog opened by itself with the full setup form and a primary Copy button, although that copy had finished. He read it as "copy it again". Two causes:
   - `ProjectWorkspaceSurface.tsx:415` kept the machine menu's `handoffRequest` in state and never cleared it. `ProjectMachineHandoff` is keyed by `${project.environmentId}:${project.id}` (`:2172`) and its page is kept under a hidden `Activity` (`KeptProjectPages.tsx`), so switching the window's machine mounts it again (or runs its effects again) with the stale request, and the effect at `ProjectMachineHandoff.tsx:908-914` opened the dialog.
   - `useCopyDraft.ts` archived a finished copy whose Done was seen and showed the setup form with a small "last copy" note, so even an intended reopen looked like a new copy.

4. Secrets, second pass ("These secrets should be a part of the copy mechanism"). The approval said nothing about which secret files the window sent, so a list withdrawn or replaced between the send and the approval, or a 404 on the staged list, ended as a copy "without secrets" (`sourceClient.ts:330-333`). The watcher left `~/` secret files out (`machine: undefined`), a pointer without a secrets choice was approved `withoutSecrets`, a Replace all approved by the watcher named no files, and Add to another machine could start its clone before the secret scan answered.

## Scope

In: the copy dialog, its background watcher and the Done screen in `apps/web`. A window that cannot send secrets says so as a warning before the copy starts and in the finish text; a copy that said "included" is never approved without secrets unseen; an approval never skips the secrets list because the summary was unread; the finish text names the action that works, with a "Copy again with secrets" action where it can work; the watcher links a finished copy-only copy.

Also in (after PR 494): a finished copy opens as done, the dialog never opens without a click, and the approval names every secret file the window sent so the destination finishes only with all of them (`packages/contracts`, `apps/server/src/fleet`).

Out: letting a window without `access:write` send secrets (the rule stays); a server RPC that sends only the left-behind secrets after a copy finished (see D-02); a server-side link at the end of the copy (see D-01); Add to another machine and the agent copy tools, which already link themselves and stage their own secrets.

## Acceptance Criteria

- [ ] AC-01: In a window that cannot send the source's secrets, the Secrets line on the setup form and on the review shows "Only SpecWithCode on {source} can send secrets. To include them, start this copy in the SpecWithCode window on {source}." as a warning, not muted helper text, with the box off, before anything is copied. The review shows it even when the source's secret list is unread.
- [ ] AC-02: A copy that started while the form said secrets are included is never approved without them unseen: when the window turns out unable to send secrets after the copy started, the background watcher and the dialog's one-click approval stop at the review instead of approving `withoutSecrets`. A copy started with the warning shown still runs through in one click.
- [ ] AC-03: In a window that can send secrets, an approval with secrets included never goes out with nothing staged because the source's summary was unread: the dialog reads it first, and when it cannot, nothing is approved and the error says the secrets list could not be read from {source}. A review with an unread list still has a Secrets box, so the person can untick it and copy without them.
- [ ] AC-04: The finish text, on Done and in the background toast, no longer mentions "Let me choose file types first". In a window whose session confirmed it can send secrets it reads "N secret-like files (.env and similar) stayed on {source}. To send them, copy again with Secrets ticked."; in a window that cannot: "N secret-like files (.env and similar) stayed on {source}. This window can't send them: only SpecWithCode on {source} can. Start the copy again there with Secrets ticked."; while the window's access is unconfirmed: "N secret-like files (.env and similar) stayed on {source}. To send them, start the copy again in SpecWithCode on {source} with Secrets ticked."
- [ ] AC-05: On Done, in a window that can send secrets and when a left-behind file can travel to that machine, "Copy again with secrets" starts a fresh copy of the same folder and machine with every secret ticked; the action is absent in a window that cannot send them or whose access is unconfirmed, and when a fresh copy would carry none of what stayed (then Done names no action).
- [ ] AC-06: With the dialog closed, the background watcher links a finished copy-only copy (applied, committed, registered) to its source right when it sees it, and records it on the pointer, so both projects share one `logicalProject` without the dialog being reopened. A copy found finished after a restart is linked too; the watcher waits up to a minute for the destination to connect. A link that needs review is left for the dialog, and a copy already linked is not linked again.
- [ ] AC-07: Opening "Copy to another machine…" for a folder and machine whose last copy finished shows a done view first: "{project} is on {machine}" with when it finished, "Open on {machine}", Undo (after "View" when the copy was put aside), and a secondary "Copy changes again" that leads to the form. The setup form and a primary Copy button appear only after "Copy changes again". A failed or cancelled last copy keeps today's behaviour. When the machine cannot be reached, the view says the copy finished and still offers a new copy.
- [ ] AC-08: The dialog never opens without a click: switching the window's machine, reconnecting or a finished copy does not reopen a closed dialog. The machine menu's request is taken once and dropped by the workspace, so a dialog mounted again finds none.
- [ ] AC-09: A copy with the default choice carries every file in `summary.secretFiles` that can travel, from the dialog and from the background watcher with the dialog closed (one-click and Replace all, `~/` files included when the machine takes them). The approval names the files the window sent (`expectedSecrets`); the destination fails at Apply with "N secret files approved for this copy were no longer offered by {source}" instead of finishing when one is missing, and Retry finishes once they are offered again. A pointer without a secrets choice and an unknown `~/` capability stop at the review. Add to another machine cannot start its clone before the secret scan answers.

## Approach

All in `apps/web/src/components/studio`.

- `handoffFolderCopyPending.ts`: new pointer flag `secretsStay`, set when the copy starts (or Replace all is clicked) in a window that showed the warning.
- `useCopySecrets.ts` (new): the dialog's secrets choice, gate, send-before-approve and finish note move here from `HandoffFolderCopy.tsx`, which is at the 1,500-line limit. Send-before-approve reads an unread summary and refuses to approve blind (AC-03).
- `HandoffFolderCopy.tsx`: uses the hook; one-click approval for an older source and Copy again take the new rules; Copy again accepts a secrets choice (AC-05).
- `HandoffFolderCopyWatcher.tsx`: `settle` asks when the window is denied, the pointer says included and `secretsStay` is unset (AC-02); `announceCopy` gets whether the window can send (AC-04); after a copy-only copy is done it calls `linkCopyAsWorkers` and writes `linked` (AC-06), also on a restored first check.
- `handoffCopyAuto.ts`: `secretsLeftText(count, source, canSend)`.
- `HandoffCopySetup.tsx`, `HandoffSecretsStep.tsx`: the locked note in the warning colour with its own data slot.
- `HandoffCopyDone.tsx`, `HandoffCopyStepPanels.tsx`: the "Copy again with secrets" action beside the note.

After PR 494:

- `useMachineHandoffRequest.ts` (new) holds the menu's request until `ProjectMachineHandoff` reports it handled (`onRequestHandled`); `ProjectMachineHandoff.tsx` also acts on each request and each requested target once per mount (AC-08).
- `useCopyDraft.ts` resumes a finished copy on a plain open (`showFinished`: no requested machine, not a move) instead of archiving it, and re-adopts a copy already put aside unless a new form was started; `HandoffCopyDone.tsx` shows "Copy changes again" as an outline button; `MachineHandoffDialog.tsx` titles it "{project} is on {machine} (copied {when})" from the status's `finishedAt` (AC-07).
- `packages/contracts/src/folderCopy.ts`: `FolderCopyApproveInput.expectedSecrets`; `destinationService.ts` stores it and refuses to finish without each file; `sourceService.ts` refuses `approveSecrets` while closing. Older destinations ignore the field (AC-09).
- `HandoffFolderCopyWatcher.tsx` sends the choice again before every approval and passes the list; `FolderCopyWatchers.tsx` tells it which machines take `~/` files; `useCopySecrets.ts` reads the gate at call time and keeps what it sent; `addToMachineCopy.ts` and `AddToMachineDialog.tsx` follow (AC-09).

Risks: the watcher and a reopened dialog may both link; `linkCopyAsWorkers` is replay-safe (shared operation id in storage, server replays `accept` and `commit`). The watcher link uses only RPCs present in 1.0.322, so it works against older peers.

## Decisions

### Asked
- none (the task fixed the options)
### Defaulted (change any before sw-do)
- D-01 Link from the watcher, not from the server that finishes the copy → default. The link is a three-step protocol (prepare on the source, accept on the destination, commit on the source) run with the window's sessions. Doing it server-side needs new source routes on the copy's transfer grant, which is revoked at commit, and both machines updated. The watcher fixes the real run (the window was open, the dialog closed) and works with 1.0.322 peers. A fully closed app links at its next start.
- D-02 No "send only the left-behind secrets" action → default. After commit the source refuses `copySecrets` (`sourceService.ts:1290`), the transfer grant is revoked (`:1402`), and the destination has no re-pull (`destinationService.ts:1344`). Opening that needs a new secret-sending grant surface. "Copy again with secrets" moves only changed files plus the secrets.
- D-03 A pointer without a saved secrets choice stops at the review (changed after PR 494; it was read as "left on the source") → default. Only copies started before November 13 lack it.
- D-04 Secrets from a window that is not the source's own: neither the one-approval path nor a "Start without secrets / Open on {source}" block is built here. Another worker owns the one-approval path end to end (server authorization of `machineHandoff.copySecrets` without `access:write`, the approval record and the Secrets row) and replaces the row PR 494 left; building a block here would edit the same files and be thrown away.
### Open
- none
