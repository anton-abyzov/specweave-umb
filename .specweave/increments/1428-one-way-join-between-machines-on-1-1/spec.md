# One-way join between machines on 1.1

## Problem

When a new machine joins another (1422's Problem: Windows joined to M5 on November 19, 2026), today's join gives more than Anton meant and asks twice:

- The code typed on the joined machine (M5) approves the new machine's app as a full device there, so Windows's app can open M5. Anton: "I think this Windows machine has no access to M5. I never intended this to be."
- The new machine asks a second code for the joined machine's app, a sixth step the five-step join never planned (`decision_machine_join_flow`).
- The level picked at Allow is not remembered: the joined machine names its own level and can raise it.

Anton decided the fix on 1422's cards (1422 D-01 to D-06, D-08 to D-11). The design (below, moved from 1422) went through three reviews on November 19, 2026 and still said fix first (`1422-*/reports/design-review-1.md` to `design-review-3.md`). Round 3 showed most of what was left is how the app already works: the joined machine's one-year management key on the new machine is never asked for a device code, can open a window there and can mint a pairing code (`design-review-3.md`, baseline section). On November 19, 2026 Anton split 1422: wording now in 1422, this access work here (1422 D-07, card answer "Wording now, access later"; "No, I wouldn't include it in this increment").

## Scope

In, all between machines that both run 1.1 or newer (1422 D-08):

- The code typed on the joined machine approves the join only (1422 D-03).
- The joined machine vouches for its own app on the new machine, so no second code (1422 D-01), only while the grant is full access to all projects and all sign-ins (1422 D-05).
- The new machine remembers the level picked at Allow and refuses anything higher (1422 D-04), and its Settings offers a menu to lower it later (1422 D-10).
- Agents run one way; after the reverse Allow the new machine's app never opens the joined machine by itself (1422 D-02, D-06).
- Remove on the joined machine ends the vouch within a day, even while the new machine is offline (1422 D-11).

Between a 1.1 machine and a 1.0 machine the join works as today, and the screens say so, only until 1.0 is retired (1429). This increment builds no 1.0 compatibility path beyond today's behaviour (1422 D-08, D-09). The rule that an older build refuses the new scopes (Design, rule 1) stays: it is rollback safety, not a 1.0 path.

Out:

- Retiring 1.0 (1429).
- The shipped management-key gap (owner question 16 below; not chosen as scope: Anton did not pick "Close the key gap first").
- The sleep and suspend routes (`S/project/CoordinatorSuspendRoute.ts:26-36`, item 7): their own increment.
- 1422's wording, which ships first and stays true to today.

Lane: `[access]`. Every task waits for a Muse Wonderful review and Anton's acceptance before release.

## Acceptance Criteria

- [ ] AC-01 [access]: A written baseline of today's access between two joined machines (person, management key, worker grant; who can open, approve, mint and run what) is saved in `reports/baseline.md` before the design changes, and every design finding is sorted against it as new exposure, a promise to close, or a regression.
- [ ] AC-02 [access]: The code typed on the joined machine lets the new machine join and hand over its line; it gives the new machine's app no lasting access to the joined machine. A machine joined before this change keeps what it has until the owner removes it. (1422 D-03; was 1422 AC-10)
- [ ] AC-03 [access]: After a join, the app that typed the new machine's code opens the new machine with no second code and no pop-up: the joined machine vouches for that app with the credential the join gave it, and the new machine checks that proof. No other device gets a vouch. It applies only while the grant is full access to all projects and all sign-ins; a capped, project-limited or sign-in-limited grant, a 1.0 machine on either side, or a request without a valid proof falls back to the code. Remove and revoking the grant end it. (1422 D-01, D-05; was 1422 AC-05)
- [ ] AC-04 [access]: The new machine remembers the level picked at Allow and refuses anything higher, even if the joined machine asks for more later; a menu on the joined machine's card in the new machine's Settings lowers it, and only a new join raises it. (1422 D-04, D-10)
- [ ] AC-05 [access]: A join grants agents one way only; the reverse is set up only by the owner's Allow on the joined machine, and after it the new machine's app does not open the joined machine by itself. (1422 D-02, D-06; was 1422 AC-06)
- [ ] AC-06 [access]: Remove on the joined machine ends the vouch within 24 hours even while the new machine is offline: the vouch lapses unless the joined machine renews it, and a lapsed vouch is not renewed. (1422 D-11)
- [ ] AC-07 [access]: The rules above run only when both machines run 1.1 or newer. Against a 1.0 machine the join works as today and the screens say what it gives and to update that machine. No other 1.0 path is built. (1422 D-08, D-09)
- [ ] AC-08 [label]: Every new string goes through the translation function with entries for the eight shipped languages.
- [ ] AC-09 [access]: Checked after release with two real machines by Anton: the join's screens, then what each machine can open and run on the other.

- [ ] AC-10 [privacy]: An explicit authentication or permission denial hides cached project and chat metadata and content, clears the environment’s persisted projections, and discards warm thread resumes. Ordinary offline use keeps its cache. A successful new session can show fresh data.

### Design

To be reworked from the baseline (T-01). Design only, written November 19, 2026, rounds 2 to 5 the same day. Code was read at app `origin/main` `c924fa8340` of `repositories/anton-abyzov/specwithcode` and rechecked at `2504755da`, `0b80025bb` and, for round 5, `30445e8a2`. Round 5 answers design review 2 (`reports/design-review-2.md`) by sweeping the whole design for three patterns, and removes mechanism where it can: no grant mirror in the device store, no pending-revocation file, no sidecar marks on N. `D/` is `apps/desktop/src/`. Path prefixes: `S/` is `apps/server/src/`, `W/` is `apps/web/src/`, `C/` is `packages/contracts/src/`, `R/` is `packages/client-runtime/src/`. J is the joined machine (M5), N is the new machine (Windows).

**Three rules the design keeps** (round 5).

1. Nothing is narrowed only by an optional claim on a credential an older build accepts. Every credential a join or a reverse Allow creates carries a scope an older build does not know. Scopes are a closed list there (`C/auth.ts:114-137`). A session carries the new scope in its signed token, which every check decodes token by token (`S/auth/SessionStore.ts:575-587`, `:1080`), so an older or rolled-back build refuses it. The stored row keeps its `scopes` to known values and records the new scope in a new field the older row schema ignores, because an older build's session list decodes every row and fails whole on one it cannot read (`S/persistence/AuthSessions.ts:609-630`). A pairing code keeps the scope in its row (`S/persistence/AuthPairingLinks.ts:23`): an older build refuses it at redeem, and its pairing list (`:401-422`) fails only until such short-lived codes expire. Two new scopes: `fleet:join`, the only scope of the join-only session, and `fleet:workers-only`, added to the management session, the worker grants and the pairing codes of a join or reverse tie. Where no such credential exists, the behaviour is today's, and the version floor says so.
2. No promise rests on two writes both landing. The vouch is ended by a generation read at check time from the grant policy's own record, and Remove relies on a lease J must renew, so stopping is enough.
3. An automatic open is stopped before the relay mint, by the code that would register the route, and only the attested key's request is ever held back.

**Version floor** (owner question pending, item 15). Answer A: the one-way rules hold only between machines that both run this version, an older machine works as today, and the screens say so. Answer B: they also hold against older machines. The design is A, and lists what B would add.

- Everything below runs only when the other side advertises `deviceJoinApproval` and `deviceJoinVouch` on its descriptor, which needs no credential and is read before the token exchange (`C/environmentHttp.ts:722-726`, `R/authorization/service.ts:454-463`). Otherwise today's flow runs, and its screens say what it gives. N's card against an older J: "{machine} runs an older SpecWithCode. Typing the code there also lets this app open {machine}. Update {machine} for a one-way join." J's pop-up for an older N's app keeps PR 712's full-device wording, which is true for it.
- B would add a join mark on J, so J refuses its own Tailscale pairing (`connectFleet`, `S/studioFleet.ts:477-530`) to an older N it joined (item 14). B cannot hold AC-10 for an older N's app: its code approves a full device before J can know it is a join (items 3 and 10).
- AC wording that would change, not changed here. Under A, AC-06 and AC-10 gain "between machines on version {X} or newer; an older machine works as today, and the screens say so". Under B, AC-10 does not hold as written for an older new-machine app, and AC-06 gains item 14.

#### Facts the design rests on

- Order today: N's app picks J, which opens J over the relay at once (`W/components/settings/AccountJoinCard.tsx:235-262`). J has not approved N's app, so N shows J's code where Allow would be (`W/components/settings/IncomingWorkerSetup.tsx:258-263`). The code is typed on J before Allow, not after. Allow then mints N's line on N and posts it to J (`W/studio/fleet.ts:404-426`).
- A device is its relay proof key, `jkt:<thumbprint>` (`S/fleet/ConnectDeviceTrust.ts:126`, `:162-171`). The code approves that key as a full device: `approve` writes a `DeviceRecord` (`:993-1040`), and every later session of the key passes the gate (`:912-913`, `S/auth/EnvironmentAuth.ts:642-665`).
- `accountJoinFleetWorkers` needs only `orchestration:operate` and a Connect subject (`S/studioFleetHttp.ts:777-821`). It has no join-specific approval; it relies on the device gate above.
- Scopes cannot make a session join-only. Of 60 authenticated HTTP endpoints, 8 check no scope: the websocket ticket (`S/auth/http.ts:650-663`) and the six `connect-devices` routes, where an approved device is an approver whatever its scopes (`S/auth/connectDevicesHttp.ts:40-61`). `orchestration:operate` alone also opens `/ws` RPCs and project changes.
- The join gives J two credentials on N: a management token (subject `fleet-invitation`, coordinator principal J, Standard scopes plus `access:write`, bound to J's fleet key, 365 days, never renewed; `S/studioFleetHttp.ts:614-693`, `S/fleet/fleetRedemption.ts:24-29`) and a worker grant (subject `mcp-client`, 30 days, renewed; `S/fleet/workerGrantMint.ts:348-395`). Neither can approve devices today (`S/auth/connectDevicesHttp.ts:28-31`, `:51-52`).
- J's server never sees its own app's proof key. The local app signs in with a bearer or a cookie, and the approver is recorded as `key: null`, "this machine" (`S/auth/connectDevicesHttp.ts:58-60`). The key lives in the app's IndexedDB (`studio:cloud-auth`, id `relay-dpop-proof-key`, private half not extractable; `W/cloud/dpop.ts:24-27`, `:135`), one per install and OS user, shared by its windows. It is used only towards other machines (`W/cloud/managedRelayLayer.ts:16-37`). The span `relay.connection.deviceIdentity.resolve` (`R/authorization/service.ts:423-425`) resolves a relay device ID that the web and desktop app never send (`W/connection/platform.ts:341-343`); it does not name the key.
- N does not bound the grant's access level. J sends the level it wants at mint (`S/fleet/workerGrantMint.ts:277`), N copies it into the session (`S/auth/McpOAuth.ts:613-623`, `S/auth/EnvironmentAuth.ts:1654-1656`), and the level lives only in the signed token (`S/auth/SessionStore.ts:575-587`, claim `rtc`). The owner's choice in the Allow card is sent to J and never stored on N. `runtimeCap` in `work-grants.json` is copied from the caller's token on its first `/mcp` call (`S/fleet/WorkGrants.ts:519-523`). Project and account limits are different: only N's owner can change them (`S/studioFleetHttp.ts:227-241`, `:447-455`).
- Stop on N revokes every session of coordinator J, the management token included, and Restore does not bring it back (`S/fleet/WorkGrants.ts:650-665`, `S/persistence/AuthSessions.ts:317-341`). Remove on J revokes the management token on N (`S/studioFleetJoin.ts:586-639`).
- Older builds drop unknown keys on decode (Effect's default) and lose them on the next write. `connect-devices.json` is decoded that way (`S/fleet/ConnectDeviceTrust.ts:327-343`). Exact input structs refuse unknown keys with an empty 400: approve (`C/connectDevices.ts:11-17`, `:101`) and account-join (`C/studioFleet.ts:124-127`, `:158-161`). `/oauth/token` ignores unknown form fields (`C/auth.ts:323-332`). The descriptor is readable with no credential and the client reads it before the token exchange (`C/environmentHttp.ts:722-726`, `R/authorization/service.ts:454-463`).

- The window that opened N by itself is `W/cloud/GrantedAccountMachines.tsx:253-256` (selection in `W/studio/grantedAccountMachines.ts:30-77`): it saves a Connect route for each account machine that granted this one. `AutoConnectPrivateMachines.tsx` and `fleetAutoConnect.ts` are the Tailscale path (`W/studio/fleetAutoConnect.ts:155-161`, `:180`) and did not act in this join. The Problem table and `reports/evidence.md` now say so.
- "Owner" in `deviceApprover` is not "the app on this machine". Any session with `access:write` and a device principal counts (`S/auth/connectDevicesHttp.ts:58-60`), and a window on another machine can hold one: a pairing code made on J with "Manage access" ticked and redeemed there, the startup link of a web-mode server, or a token from `auth session issue`. The fleet's own "Connect machine" codes do not count, because they carry a coordinator principal (`S/studioFleet.ts:523-531`, `S/auth/http.ts:725-728`). Such a window reaches J over Tailscale, the LAN or an SSH tunnel, so "not over Connect" does not single out J's app either: `arrivedOverConnect` reads headers only and is documented as a reason to refuse, never to grant (`S/auth/CredentialFailureLimiter.ts:158-170`, `S/fleet/fleetOrigin.ts:70-74`). The peer address does not help: Tailscale Serve, the Connect tunnel and an SSH tunnel all arrive from loopback.
- What does mark J's own app: the session subject `desktop-bootstrap`. The server gives it only for a token derived from a secret the desktop app passes to the server it starts, over a private channel (`S/auth/PairingGrantStore.ts:545-553`, `packages/shared/src/desktopBootstrapToken.ts:4-8`); the exchange copies the subject into the session (`S/auth/EnvironmentAuth.ts:1129-1134`), and the pairing route can only ever mint `one-time-token` (`:1356-1360`). When the app instead attaches to an installed service, nothing marks it today: it pairs through the service's command line and gets `one-time-token` with a device principal and a label anyone can choose (`D/backend/localServiceAttach.ts:352-362`, `S/cli/pair.ts:268-281`), the same shape as a code redeemed on another machine.

#### 1. D-03: the code approves the join only

**Declared and enforced.** N's app adds `client_purpose=join`, `client_join_ticket` (section 2) and `client_join_machine` (N's environment ID) to `POST /oauth/token` on J (`S/auth/http.ts:571-649`; an older build ignores unknown form fields, `C/auth.ts:323-332`). The session J issues has one scope, `fleet:join`, which maps to no RPC (`C/auth.ts:102-113`) and which an older J cannot decode (rule 1).

- The request kind is set before its code can be read (`ensureWaiting`, `S/fleet/ConnectDeviceTrust.ts:744-812`; codes are shown only to a session, `:920-925`). A relay mint (`:933-949`, `S/cloud/CloudLink.ts:1820-1825`) never changes it. A session of the other kind, or another ticket, replaces the code, so a code approves exactly what it was shown with.
- Approving a join request (`:993-1040`) writes no `DeviceRecord` and no "new device" notice. It writes `{ key, approval, ticket, machine, state, approvedAt, expiresAt, attestation? }` into a new top-level array `joins` of `connect-devices.json`. An older build drops the array and the key is unapproved again. `isApproved`, `bindingFor` and `deviceApprover` never read it.
- The gate (`:892-931`) lets a key with a live join approval in only with a `fleet:join` session. `authenticateHttpRequest` and `authenticateWebSocketUpgrade` refuse such a session (`S/auth/EnvironmentAuth.ts:1489-1527`) except for two callers: `layerAuthenticatedAuth` for `accountJoinFleetWorkers` (`S/auth/http.ts:436-471`) and `getSessionState` (`S/auth/EnvironmentAuth.ts:874-899`). So no websocket ticket, `/ws`, media, raw or `connect-devices` route; `/mcp` already refuses the subject (`:1576-1577`). `accountJoinFleetWorkers` takes `fleet:join`, or `orchestration:operate` from a fully approved device as today (`S/studioFleetHttp.ts:781`).

**What the approval names, and its one spend** (review 1, finding 2; review 2, first spend). The approval names N's app key A (the session's proof key), the ticket and N's environment ID. `accountJoinFleetWorkers` refuses a line whose destination (`decodeFleetJoinCode`) is another machine, or whose `ticket` (new optional field of the line, sent only to a J with `deviceJoinApproval`) is another ticket, before it reserves anything. Then `reserveJoin` turns `ready` into `reserved { digest }`, the line's SHA-256, under the trust store's one lock (`S/fleet/ConnectDeviceTrust.ts:539`, `:670`, `:687`), before `addAndAllowWorkers` (`S/studioFleetHttp.ts:368-391`, called at `:800`); the run's end writes `spent` with the answer. Another request gets 409 while it runs, the stored answer for the same line, and 403 for any other line. A failure before the redeem (`addMachine` refuses before `redeemFleetInvitation`, `S/studioFleetJoin.ts:336-365`) returns it to `ready`; a later one leaves it spent. A reservation found when the store loads its file, read once at start (`S/fleet/ConnectDeviceTrust.ts:614-616`), was cut off by a restart and becomes spent, never replayed. The join session stays until the approval's 10 minutes end (the session itself lasts at most 1 hour, `S/auth/EnvironmentAuth.ts:1137-1141`), so a lost answer can be fetched again; it reaches nothing else.

**N's app.** For a J with `deviceJoinApproval`, the join card holds the join in memory instead of `environmentCatalog.register` (`W/components/settings/AccountJoinCard.tsx:235-262`): a proof-bound token kept out of the saved token cache (`R/authorization/service.ts:502-665`, the cache key gains the purpose) and a poll of `GET /api/auth/session` on J every 4 seconds. `throughAccount` (`W/components/settings/IncomingWorkerSetup.tsx:256-257`) takes "join approved" in place of `operateThere`, and `joinAccountMachineForWorkers` (`W/studio/fleet.ts:404-426`) posts with the handle, which is dropped after the join, on failure and when the card closes. Once the session has ended, the card reads N's own "Who can run work here" list for the done card.

**Only a join-aware window shows or approves a join** (review 1, finding 7; closed in review 2). Windows learn of requests only from the list (`W/studio/connectDevices.ts:29`). Its input gains optional `understands: ["join"]`, and the list (`S/auth/connectDevicesHttp.ts:124-136`) leaves join requests out without it. The approve input gains optional `join: true`; a join code without it answers "not-found", is not counted as a wrong code (`S/fleet/ConnectDeviceTrust.ts:998-1005`), and no status is added (`C/connectDevices.ts:101-104`). When no join-aware window listed in the last 60 seconds (windows list every 4 seconds, or 20 when hidden, `W/components/devices/ConnectDeviceHosts.tsx:42-43`), J's session state gives `approverReady: false`, and N's card says "Open SpecWithCode on {machine} to type this code. If it is not there, or the code is not found, update the app on {machine}."

**Screens** (T-07; every string through `tx`, eight languages). J's pop-up for a join (`C/connectDevices.ts:46-68` gains optional `purpose`; `W/components/devices/ConnectDeviceViews.tsx:236-261`, `:325-330`): "{device} wants to join {machine}. Typing its code lets it hand over a line, so agents on {machine} can run work on it. It does not let that device open {machine}." The line that the name is the device's own word stays. J after the code: "{device} can now join. Press Allow on it." (`W/components/devices/ConnectDeviceHosts.tsx:166-190`; the status stays "approved" with optional `join: true`). N while waiting: today's code line plus "This lets {machine} join you to it. It does not let this app open {machine}."

Closed: the code approves one join, once, for the machine and ticket it names, and nothing else; a line with no ticket from a join-only session is refused; on an older or rolled-back J the join session does not decode. Left: an older new-machine app (version floor, items 3 and 10). Depends on: the ticket and its route come from section 2 (T-03); moved alone, D-03's approval names the key and the machine only.

#### 2. D-01: the joined machine vouches for its own app

**The key and its proof** (review 1, finding 1; closed in review 2). The vouched key is K, the relay proof key of the SpecWithCode app on J where the owner typed the code (IndexedDB `studio:cloud-auth`, not extractable, `W/cloud/dpop.ts:24-27`, `:135`). J's server never sees it today (`S/auth/connectDevicesHttp.ts:58-60`), so N checks what it can itself:

1. N's app gets a ticket from its own server, new `POST /api/studio/fleet/join-ticket` (owner only and same-origin, as `requireGrantManager`, `S/studioFleetHttp.ts:227-241`, with a `dpop` proof by A). N stores `{ ticket, appKey: A, coordinator: J, expiresAt: 10 minutes }` in a new `tickets` array.
2. When a code matches a join request and the approver's subject is `desktop-bootstrap` or `local-desktop-app` (below), the approve answer carries `attest: { tkt, j, n, a, nonce }`, that request's own values, so the window never chooses which request it signs for. J's window signs them with K in a JWT (`typ: "studio-join-attest+jwt"`, the DPoP signer, `W/cloud/dpop.ts:145-184`) and posts it to new `POST /api/auth/connect-devices/attest` from the same session. J checks the signature, the values and the nonce, and stores the attestation on the join approval. J's session state then reads "approved" with `approverKey`, or "approved" with none after 10 seconds.
3. N's app mints the line with `joinTicket`, `expectedKey: K` and `access` (`C/studioFleet.ts:215-226`). N binds ticket, line and key, and at redeem (`S/studioFleetHttp.ts:614-693`) the management session.
4. J forwards the attestation in the vouch. N accepts it only when the signature verifies with the header's key, that key is the vouched thumbprint and the ticket's `expectedKey`, the ticket is open and bound to the calling management session, `a` is the ticket's app key, `n` is N and `j` is the session's coordinator. The ticket is spent in the write of the vouch.

**Only J's own app.** `attest` goes only to two subjects that only the app on J can hold; neither the scopes, the route nor "not over Connect" decide it (Facts).

- `desktop-bootstrap`, for an app that started its own server (`S/auth/PairingGrantStore.ts:545-553`, copied into the session at `S/auth/EnvironmentAuth.ts:1129-1134`).
- `local-desktop-app`, new, for an app attached to an installed service, which `desktop-bootstrap` does not mark (review 1). `POST /api/auth/pairing-token` (`S/auth/http.ts:707-771`, input `C/auth.ts:504-513`) mints it when the `local-cli-credential` session (`S/auth/LocalCliCredential.ts:44`, `:57-63`) asks with `localApp`, which only the desktop's own `pair` call does (`D/backend/localServiceAttach.ts:352-362`, `S/cli/pair.ts:268-281`), never `auth pairing create` (`packages/ssh/src/tunnel.ts:776`). It joins the old subject where that is named (`S/auth/SessionStore.ts:138-152`, `S/design/DesignRpc.ts:32-46`), and `auth session issue --subject` refuses both (`S/cli/auth.ts:291-326`).

Any other approver still approves the join; it gets no vouch.

**The vouch.** `accountJoinFleetWorkers` sends it inside the uninterruptible region of `addAndAllowWorkers` (`S/studioFleetHttp.ts:368-391`), once the grant came back allowed or expiring, with the management token (`S/fleet/fleetTransport.ts:358-403`, as `S/studioFleetHttp.ts:875-886` does), only to an N with `deviceJoinVouch` (`checkIdentity`, `:846-856`), once per join, within 5 seconds. A failed vouch leaves the join done and the code in place. N's route, `POST /api/studio/fleet/vouch` `{ thumbprint, attestation }`, sits with the fleet routes because it reads the grant store. It takes only J's `fleet-invitation` session (coordinator principal, proof-bound, `access:write`), the attestation as above, a grant with `projects` and `accounts` both of kind `all` (the fields of `newGrantDefaults`, `S/fleet/workGrantPolicy.ts:103-108`), `ownerCap` full and not stopped, a key not removed or denied (`isTurnedAway`, `S/fleet/ConnectDeviceTrust.ts:881-890`), team rules (`S/studioFleetHttp.ts:797-798`) and the redeem rate limit (`:618`). One key per coordinator; a waiting request of that key is cleared. The record is a new top-level `vouched` array, never `devices`, so an older build drops it and the key waits for a code: `{ key, coordinator, session, generation, leaseUntil, vouchId, vouchedAt, label, system, app }`.

**What ends it, read at check time** (review 2, finding 3 and the Remove finding; rule 2). The gate checks on every request, and every 5 seconds on an open socket (`S/auth/EnvironmentAuth.ts:1529-1536`):

1. the management session named in the record is live (`S/persistence/AuthSessions.ts:356-380`);
2. the coordinator's grant policy, read from its own record in `work-grants.json` (`S/fleet/WorkGrants.ts:46`, `:104-113`, `:294`), still has the record's `generation` and meets the predicate. `generation` starts at 1 and is bumped by every write that changes what the predicate reads (projects, accounts, owner, `ownerCap`, Stop and Restore), not by the routine writes that follow a join (`principalPending`, `S/fleet/WorkGrants.ts:395-401`; the period and routines, `:605-630`); an older build drops the field when it rewrites the record, which reads as a mismatch. The gate reads the file through the decoder, moved into `S/fleet/workGrantPolicy.ts`, not through the `WorkGrants` service, which imports `EnvironmentAuth` (`S/fleet/WorkGrants.ts:24`). The policy write is the only write that ends the vouch, so a crash after it changes nothing, and narrowing then restoring leaves another generation;
3. `leaseUntil` has not passed (pending the owner's answer, item 11). J renews the lease every 6 hours from its renewal loop (`S/fleet/FleetWorkerGrants.ts:335-360`), with new `POST /api/studio/fleet/vouch/renew` from the same management session, while N is in J's fleet with workers allowed; each renewal sets 24 hours from then, and a renewal after it lapsed is refused.
