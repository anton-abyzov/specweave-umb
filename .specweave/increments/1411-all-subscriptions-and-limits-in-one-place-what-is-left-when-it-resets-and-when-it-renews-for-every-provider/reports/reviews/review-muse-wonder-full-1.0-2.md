## New findings

### Must-fix

**N1. AC-01's board-only collection has no workable row identity, eligibility rule or ACP agent id source.**

What is wrong: AC-01 asks for "a row for every provider instance that is enabled, installed and signed in" and Approach 1 says the new collection shares `collectLimitAccounts`' merge. Today's merge is account-level, not instance-level, and is a closure inside `collectLimitAccounts` (`packages/shared/src/usageLimits.ts:190-259`). Its output type requires a reading (`packages/shared/src/usageLimits.ts:157-183`, `limits` at line 182), while AC-01's new rows may have no reading and need a notice/reason. The only fallback merge key is `${environmentId}:${provider.instanceId}` (`packages/shared/src/usageLimits.ts:267-282`), which answers row identity for no-email/no-fingerprint instances only if the spec says so. It does not say whether two machines signed in to one unidentified account make one row or two, or whether offline presentations remain, although today's collection keeps and flags them.

Eligibility is also lost in the rewrite. ACP snapshots deliberately use `auth.status: "unknown"` when discovery does not prove sign-in (`apps/server/src/provider/Drivers/AcpRegistryDriver.ts:489-508`) and upgrade only after confirmed authentication (`apps/server/src/provider/Drivers/AcpRegistryDriver.ts:853-862`), so a strict `authenticated` gate can again omit working ACP agents. API-key accounts are `authenticated`: Codex labels them at `apps/server/src/provider/CodexProvider.ts:111-117`, the auth contract carries `apiKeyBilling` (`packages/contracts/src/server.ts:77-83`), and the existing unreported collection gives API billing its own reason and skips `externalUsage` (`packages/shared/src/usageLimits.ts:470-503`). AC-01 would count those instances as subscriptions under AC-03. AC-01 also says ACP rows pass the agent id to the header, but `LimitPresentations` carries providers and usage-limit sources only (`packages/shared/src/usageLimits.ts:90-101`), `ServerProvider` has no ACP agent id field (`packages/contracts/src/server.ts:293-350`), `LimitAccount` has none (`packages/shared/src/usageLimits.ts:157-183`), and `SubscriptionRow` drops straight to labels (`apps/web/src/components/usage/subscriptions/SubscriptionRow.tsx:148`). The resolver can use a label only for Copilot and requires the real agent id for Cursor (`packages/shared/src/providerUsageLinks.ts:41-58`).

Smallest fix: define the board row/account type in the spec (`limits` optional; notice and reason; driver, agent id, instance id and environment ids; offline flag), its merge key and fallback, and an eligibility table for authenticated, unknown-auth ACP, API-key/API-billing, external-usage, unmetered, reader-off and offline instances. Name where the agent id comes from (a new `ServerProvider` field or settings threaded into presentations) and add that file to T-01. State that rotation, fallback, capacity and quota alerts keep reading `collectLimitAccounts`; I verified their callers are separate, so a board-only collection is workable once this type is pinned.

**N2. Copilot, the owner's named renewal example, still cannot hold a set renewal day.**

What is wrong: AC-04 says a row with no stable identity says "Renewal: sign in again to set a day." Copilot does publish a stable identity, but not one the renewal setting uses. The reader builds `subscriptionKey` from the GitHub login and plan (`apps/server/src/provider/copilotUsageLimits.ts:151-157`), and the ACP driver stamps `auth.login`, not `auth.email` (`apps/server/src/provider/Drivers/AcpRegistryDriver.ts:591-604`). `accountKey` accepts only email or `credentialFingerprint` and otherwise returns null (`packages/shared/src/usageLimits.ts:139-149`); Copilot publishes neither. `subscriptionRows` therefore gives the row `accountKey: null` (`apps/web/src/components/usage/subscriptions/subscriptionRows.ts:168-177`), and the renewal setting cannot save. "Sign in again" would be permanent and false for a signed-in Copilot account.

Answer to the survival question: a day set while identity is only the instance fallback cannot be set today. If identity later becomes `driver:email`, a day already saved under that same email key survives; a day saved under any board-only fallback key would not survive unless the spec defines migration. For OpenCode Go the key appears only after a read computes the fingerprint (`apps/server/src/provider/openCodeUsageLimits.ts:106-116`), so a first no-reading row also cannot take a day.

Smallest fix: pin one renewal identity precedence for the board, for example email, then `subscriptionKey`, then `credentialFingerprint`, and state whether it changes `limitAccountKey` globally (history, ledger, prices and targets use that key) or is board-only with an explicit mapping. Add a Copilot test in T-01/T-04 showing the day survives sign-out/sign-in and a later reading.

**N3. The window-rules table still miskeys Claude, and Cursor's monthly rule can fire from a default rather than evidence.**

What is wrong: the table is keyed by the row's plan, and the row's plan is `limits.planLabel || account.plan`, where `account.plan` is `provider.auth.label` (`apps/web/src/components/usage/subscriptions/subscriptionRows.ts:177`, `packages/shared/src/usageLimits.ts:270-276`). Spec line 55 cites `apps/server/src/provider/ClaudeProvider.ts:204-246`, the internal short label, but the auth label is produced by `formatClaudeSubscriptionAuthLabel` at `apps/server/src/provider/ClaudeProvider.ts:261-276` and installed at `apps/server/src/provider/ClaudeProvider.ts:301-305`: Ultra reaches the row as "Claude Ultra Subscription", not the table key "Ultra" (spec line 59). The "Verified" qualifier in the vendor quote is also not represented in the auth label. Codex's three Pro keys are real: `codexAccountAuthLabel` returns `codexPlanLabel` directly (`apps/server/src/provider/CodexProvider.ts:111-117`, labels at `apps/server/src/provider/CodexProvider.ts:120-154`).

Cursor is keyed by window kind, but kind is weekly only when plan info says so; missing plan info defaults to monthly timing from `billingCycleEnd` (`apps/server/src/provider/cursorUsageLimits.ts:82-100`). A current weekly Cursor plan read without `GetPlanInfo` therefore gets monthly windows and the table's "Two monthly pools that reset with your billing cycle" (spec line 64), a false fact manufactured by the reader. Grok's kind is weekly/monthly only from `currentPeriod.type`, otherwise "other" (`apps/server/src/provider/grokUsageLimits.ts:55-66`), so its rule safely does not fire. AC-02 does answer the no-match case: "only what was read."

Smallest fix: key Claude on the exact row labels the app emits (or on `subscriptionType` normalized server-side and carried as `planLabel`), state the verified condition or drop the Ultra claim, and let Cursor's monthly wording fire only when plan info explicitly reports a monthly period.

**N5. AC-08/AC-09 do not pin the off snapshot, OpenCode's token precedence, stale identity or the "Show it here" jump.**

What is wrong: "an environment token is consent" does not hold as a drop-in rule for OpenCode Go. Today `OPENCODE_AUTH_CONTENT` replaces the file, but with only `OPENCODE_API_KEY` set the reader still reads `auth.json`, and a stored key wins over the environment key because "OpenCode overlays stored API credentials after environment credentials" (`apps/server/src/provider/openCodeUsageLimits.ts:55-68`). With the switch off, reading the file to learn that a stored key exists is the very read the switch forbids; skipping it silently reads a different account under the env key and changes the fingerprint identity (`apps/server/src/provider/openCodeUsageLimits.ts:106-116`). Cursor and Grok do take their env token first (`apps/server/src/provider/cursorUsageLimits.ts:149`, `apps/server/src/provider/grokUsageLimits.ts:120-123`), so the rule is per-reader, not uniform.

The spec also never says what a switched-off reader publishes. That choice is load-bearing: `resolveUsageLimitsAfterProbe` keeps prior bars for `probeFailed` and replaces them for `unsupported` in the normal non-Claude path (`apps/server/src/provider/providerUsageLimits.ts:383-400`, `:456`). "Keeps the last identity" (AC-09) names no store, lifetime or invalidation: sign in to another Grok or OpenCode Go account while the switch is off and the board keeps showing the old email or fingerprint, with the old account's renewal day, price and reset history attached. Grok's email and token are read together precisely so "the email always names the account whose quota was read" (`apps/server/src/provider/grokUsageLimits.ts:136-157`); a kept identity breaks that invariant silently.

"Show it here" cannot be built from the row as specified. `SubscriptionRow.machines` is labels only (`apps/web/src/components/usage/subscriptions/subscriptionRows.ts:179-184`), so no environment id reaches the row. The switch does not live at "Settings > Usage": `UsageProviderSettings` is rendered inside Settings > Providers (`apps/web/src/components/settings/ProviderSettingsPanel.tsx:1350-1357`), settings search maps "usage-providers" to `/settings/providers` (`apps/web/src/components/settings/settingsSearch.ts:882-885`), and the Cursor switch renders on Darwin only (`apps/web/src/components/settings/UsageProviderSettings.tsx:148-162`), while AC-08 now gates Windows and Linux file reads with the same field. T-03 omits `SubscriptionsView.tsx` (the callback owner, `apps/web/src/components/usage/subscriptions/SubscriptionsView.tsx:217-225`) and `settingsSearch.ts` (new switch target ids).

Smallest fix: write per-reader precedence with the switch off, the exact published `unavailable` reason/message when off, where the last identity is stored and when it is dropped (account change, sign-out, a different identity on the next read), and give the row `environmentIds`. Name the real navigation (`/settings/providers` with the row machine's `environmentId` and a per-switch target id rendered on every platform) and add `SubscriptionsView.tsx` and `settingsSearch.ts` to T-03.

### Should-fix

**N8. AC-06 leaves sparse-merge carry and the amount unit's source open.**

What is wrong: `used`, `limit` and `unit` are each optional, so a window may carry one without the others, and "merge and equality carry the new fields" does not say whether an update that omits amounts keeps the previous amounts beside a new percent. The existing merge carries omitted `resetsAt`, `windowDurationMins` and `modelScope` forward field by field (`apps/server/src/provider/providerUsageLimits.ts:110-128`) and equality enumerates fields (`apps/server/src/provider/providerUsageLimits.ts:320-330`); amounts need the same explicit treatment or stale amounts will sit beside a fresh percent. The example unit "requests" also merges two sources the research keeps apart: `account.getQuota` amounts are requests while the billing page counts AI credits (research section 4). I checked the other decoders: no Swift or Kotlin `usageLimits` window decoder exists at `c46e2efe5`, the iOS wire fixtures carry the settings snapshot as JSON rather than a strict window type, `packages/shared/src/quotaAlerts.ts:39-51` defines its own percent-only window, mobile consumes the shared TypeScript contract type, and persisted history samples store percent and reset only (`apps/server/src/usage/usageLimitHistoryStore.ts:36-49`). An optional field therefore breaks no strict decoder I found, provided the old-schema test AC-06 already requires passes against `ForwardCompatibleArray` (`packages/contracts/src/providerUsageLimits.ts:67-69`).

Smallest fix: make the three fields all-or-none, state carry-on-omission in sparse merges, require a non-empty trimmed `unit`, and name the exact unit each reader publishes per snapshot instead of one example word.

**N9. AC-03's "next reset" can name a window that is not the spent one, and the row does not carry the reader's denial.**

The board also has an efficiency dashboard above the rows (`apps/web/src/components/usage/subscriptions/SubscriptionsDashboard.tsx:352-438`), which T-01 does not list; the header line's home should be stated so the two do not disagree.

Smallest fix: compute the reset from the binding (spent or denying) account window, say what shows when it has no reset time, add the denial fields to the row shape in T-01, and name the header's component.
