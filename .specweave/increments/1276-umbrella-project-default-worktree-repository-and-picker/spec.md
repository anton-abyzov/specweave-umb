# Umbrella project: default worktree repository and picker

## Problem

Anton, November 10, 2026, on Project settings > General for the specweave project: "if we are using worktrees, we should specify at least one repository which we're going to use for cloning, or what's available, because it might be an umbrella repository. By default, you could suggest an umbrella repository, right, but it's not mandatory to use it."

Pointing a project at an umbrella (`~/Projects/github/specweave-umb`, child clones under `repositories/<owner>/<repo>`, ignored by the umbrella's `.gitignore`) is allowed, and increment threads already get a per-repo worktree set (`apps/server/src/mcp/toolkits/project/handlers.ts:228-288`, `launchWorkspace.ts:73-98`). Everything else loses isolation (research: thread "Umbrella folder as project root", November 10, 2026):

1. A launch with no increment and no `repository` runs in the umbrella folder itself (`handlers.ts:280-281`, `UMBRELLA_WORKTREE_NOTICE` in `launchWorkspace.ts:55`).
2. The composer's worktree switch is on/off only (`apps/web/src/components/chat/WorkspaceModeControl.tsx`, used in `BranchToolbar.tsx:685`). Its launch sends `prepareWorktree.projectCwd = workspaceRoot` (`ChatView.tsx:10518`), mapped to a worktree strategy without `repository` (`packages/client-runtime/src/operations/commands.ts:739-765`), so it cuts a worktree of the umbrella that holds no child code.
3. There is no project setting naming the repository worktrees come from.
4. The folder Check describes the problem (`ProjectFolderChange.tsx:157-165`) but offers no way to register the child repos as Environment repositories, so `repository` launches fail after the move (`ThreadLaunchService.ts:128-152`). The only hint is "use Import SpecWeave workspace under Environment" when a SpecWeave workspace is present (`ProjectFolderChange.tsx:514-518`).
5. The recommendation says "Use worktrees: off" for every umbrella (`apps/web/src/lib/folderLayoutGuidance.ts:31-35, 74-78`), which is wrong once a default repository exists.

Anton, November 11, 2026, on Project settings > Environment after moving the project to the umbrella: "What is the workspace, and do we have workspace enabled? Because the umbrella project has nothing to clone, actually... What will we choose as the folder to clone, or maybe cut multiple folders? I believe we could specify multiple folders that we use, or maybe it could recognize it and set it up automatically to this list."

What the page does today for that project (read from the code and the live project record, November 11, 2026):

6. "Workspace" on that page means SpecWeave's repository list, `workspace.repos` in the folder's `.specweave/config.json`. It is not a switch. This umbrella has one, listing 3 repositories (specweave, vskill, vskill-platform). The folder holds 7 clones; specwithcode-dev, specwithcode, specweave-status and greet-anton are not in the list, so "Preview import" can never offer them (`apps/server/src/project/ProjectEnvironmentImport.ts:18-33, 131`). A config with no `workspace.repos`, or only the legacy `umbrella.childRepos`, fails the preview as "invalid".
7. The page offers three separate ways to add a repository (a URL, a checkout path with "Match existing checkout" and "Prepare checkout", and the SpecWeave import) and none shows what the folder already holds, although the server can already list it (`apps/server/src/project/FolderLayout.ts`, `ProjectRepositoryPresence.ts:listNestedRepositories`).
8. Both saved entries are broken. `dbc4018e` is saved as `specwithcode-dev.git` but its checkout pulls from `specwithcode.git`, so it reads "mismatch". `704405a3` (`specwithcode.git`) has no folder; the server resolves it to `<project folder>/.studio-repositories/<id>` (`ProjectEnvironmentPaths.ts:341`) and the page compares that with the saved empty path (`ProjectEnvironment.tsx:374-379`), so the row can only say "Checkout status unknown". "Prepare checkout" there would clone a third copy of a repository already checked out twice in the folder.
9. The approved folder `.../repositories/anton-abyzov/specwithcode-dev` is now inside the project folder and grants nothing.

## Scope

In: a per-project optional default worktree repository chosen from Environment repositories; the server launch rule for threads without an increment; a repository choice in the composer's worktree control and its branch list; one-click registration of the umbrella's child repos from the folder Check; recommendation and notice copy. Added November 11, 2026: the Environment page's Repositories section becomes one list of saved repositories, clones found in the project folder and repositories SpecWeave lists, with a status and one fix per row, one-click add, clone controls only where a clone is needed, and plain copy. Mockup: `.specweave/increments/1276-umbrella-project-default-worktree-repository-and-picker/reports/environment-repositories-mockup.html`.

Out: increment worktree sets (unchanged), the mobile and iOS new-task flows (they get the server default with no picker), routine editor UI (routines get the server default), moving the specweave project's folder (Anton does that himself after release), writing `.specweave/config.json` from the app, changes to `repositories/anton-abyzov/specweave/src/core/workspace/`, an MCP tool that adds repositories, removing existing `.studio-repositories` checkouts.

## Approach

All paths below are inside `repositories/anton-abyzov/specwithcode-dev/`.

1. Contracts (`packages/contracts/src/projectEnvironment.ts`): `defaultWorktreeRepositoryId: Schema.optionalKey(ProjectRepositoryId)` on `ProjectEnvironmentSettings`, with the existing filter extended so it must name a listed repository; the same key plus `supportsDefaultWorktreeRepository` on `ProjectEnvironmentReadResult`. Composer: optional `repository` on `prepareWorktree` in `packages/client-runtime/src/operations/commands.ts`, passed through to the existing `OrchestrationV2ThreadLaunchWorkspaceStrategy.repository` (`orchestrationV2.ts:677-684`); no new RPC.
2. Server launch rule (`launchWorkspace.ts`, `handlers.ts`): after the increment branch and before the umbrella fallback, resolve the default repository through `resolveLaunchRepository`; when its checkout is a Git repository, return `{type: "worktree", repository, baseRef: <its branch>}` with a new `defaultRepositoryWorktreeNotice`. A checkout with no branch uses `refs/remotes/origin/HEAD` (AC-17). The same rule applies in `ThreadLaunchService` when a worktree strategy arrives without `repository` for a project whose root holds separate clones, so composer, routines and mobile share one rule. Stale default: fall through with a notice (AC-03).
3. Settings default (`apps/web/src/components/studio/ProjectEnvironment.tsx`): the "New threads work in" select, suggestion and stale state; suggestion logic in a pure `defaultWorktreeRepository.logic.ts`. Removing a repository clears the key server-side in the same write.
4. Composer (`WorkspaceModeControl.tsx`, `BranchToolbar.tsx`, `BranchToolbar.logic.ts`, `ChatView.tsx` launch site): repository dropdown, branch list queried with the repository checkout as cwd, `repository` sent in `prepareWorktree`. `ChatView.tsx` gets only the prop and the launch field; logic stays in `BranchToolbar.logic.ts`.
5. Folder Check (`ProjectFolderChange.tsx`, server `ProjectFolderChange.ts`): after a successful change to an umbrella or nested layout, show the not-added count from step 7's read and "Add N repositories" (step 8's apply). The check result already carries `layout.repositories`.
6. Copy in `folderLayoutGuidance.ts` takes an optional default repository name.
7. Found repositories, no new RPC (`ws.ts` import limit): `ProjectEnvironmentReadInput` gets optional `discover: true`; the result gets optional `found` rows `{path, relativePath, name, url, branch, defaultBranch, inSpecweave, state: "ready" | "add" | "fix-url" | "fix-folder" | "absent" | "missing" | "no-remote", repositoryId?, origin?, reason?}` and `skippedLinks`. Its presence is the support flag (AC-22). A new `apps/server/src/project/ProjectRepositoryDiscovery.ts` builds the rows from `readFolderLayout`, the SpecWeave list and the saved entries, with the same bounded Git inspection as `ProjectEnvironmentImport.ts` (5 s, `repositoryInspectionEnv`, origin and `symbolic-ref` only). The walk runs only when `discover` is set, so launches and MCP reads cost what they do today.
8. One-click add: `previewWorkspaceImport` takes its rows from step 7 instead of only `workspace.repos`, keeps its re-read, fingerprint and `applyWorkspaceImport` path, and accepts an optional `paths` subset (the checked rows), which the fingerprint covers. "Clone" on an "absent" row adds the entry with its listed folder through the same apply, then runs the existing `prepare` in `clone` mode; the page chains the two under one button. "Use `<owner/name>`" and "Use this folder" are edits to the existing draft (`setRepository`), saved with Save like "Update URL" today.
9. Page: `ProjectRepositoryList.tsx` renders the list and `projectRepositoryRows.logic.ts` holds the pure parts (row order, status text, the one fix per row, counts, add-button state), so `ProjectEnvironment.tsx` (700 lines) shrinks. `ProjectEnvironmentImport.tsx` and its test are deleted. A row saved without a folder is matched to its read row by id, which removes "Checkout status unknown".

Rejected: a Settings > General field (the list of repositories lives in Environment, and a default must reference it); auto-registering child repos on folder change or on opening the page (silent change to what a project can launch into; detection is automatic, adding is one click); making the default mandatory for umbrellas (Anton: "not mandatory"); keeping the SpecWeave import as its own section (the same repositories shown twice under a word, "workspace", nobody could place); writing found clones back into `.specweave/config.json` (a second owner for a file the CLI owns); a managed checkout for an umbrella (a hidden third copy under `.studio-repositories`).

Risks: `ChatView.tsx` size and churn from other increments (touch only the launch site); `ws.ts` import limit (no new RPC planned, TS2589); the shared checkout is used by other workers (branch only on the coordinator's go); the folder walk on a large folder (bounded at depth 3 and 5,000 folders, 50 listed; the page says when it stopped early); two checkouts of one repository in one project (allowed by the settings filter, labelled "same repository as").

## Decisions

### Asked
- none (Anton's November 10 message settles optional, suggested-by-default; his November 11 message asks for the folder's repositories to be recognised and listed)
### Defaulted (change any before sw-do)
- D-01 The setting lives under Environment, next to the repositories it references.
- D-02 Default is the project folder; the suggestion needs one click (AC-02).
- D-03 The default applies to every launch without an increment or explicit repository, including routines and mobile, via one server rule.
- D-04 Composer pick is per draft, never remembered.
- D-05 Finding repositories is automatic and read-only; adding them takes one click (coordinator's brief, November 11, 2026). Clones inside the project folder need no extra folder approval.
- D-06 The app reads SpecWeave's repository list and never writes it. A clone SpecWeave does not list can still be added; listing it in SpecWeave stays with the CLI (`specweave get`).
- D-07 New entries have no managed checkout: a clone names its folder, inside the project folder by default.
- D-08 Two checkouts of one repository (specwithcode and specwithcode-dev) may both be in the project.
- D-09 A default repository with no branch checked out starts worktrees from its default branch on origin.
- D-10 On an older server the list shows saved repositories only, with an update hint; the SpecWeave import section is removed rather than kept as a fallback.
- D-11 The label is "New threads work in", not "Default worktree repository".
### Open
- none
