# Umbrella project: default worktree repository and picker

## Problem

Anton, November 10, 2026, on Project settings > General for the specweave project: "if we are using worktrees, we should specify at least one repository which we're going to use for cloning, or what's available, because it might be an umbrella repository. By default, you could suggest an umbrella repository, right, but it's not mandatory to use it."

Pointing a project at an umbrella (`~/Projects/github/specweave-umb`, child clones under `repositories/<owner>/<repo>`, ignored by the umbrella's `.gitignore`) is allowed, and increment threads already get a per-repo worktree set (`apps/server/src/mcp/toolkits/project/handlers.ts:228-288`, `launchWorkspace.ts:73-98`). Everything else loses isolation (research: thread "Umbrella folder as project root", November 10, 2026):

1. A launch with no increment and no `repository` runs in the umbrella folder itself (`handlers.ts:280-281`, `UMBRELLA_WORKTREE_NOTICE` in `launchWorkspace.ts:55`).
2. The composer's worktree switch is on/off only (`apps/web/src/components/chat/WorkspaceModeControl.tsx`, used in `BranchToolbar.tsx:685`). Its launch sends `prepareWorktree.projectCwd = workspaceRoot` (`ChatView.tsx:10518`), mapped to a worktree strategy without `repository` (`packages/client-runtime/src/operations/commands.ts:739-765`), so it cuts a worktree of the umbrella that holds no child code.
3. A launch's single `repository` must be a saved Environment repository (`ThreadLaunchService.ts:128-152`), while `repositories` and `studio_worktree_add_repository` already take a path relative to the project folder. After a move to the umbrella, `repository` launches fail until someone registers each child repo by hand.
4. `studio_worktree_add_repository` is refused in a thread that works in the project folder (`WorktreeMcpService.ts`, `not_in_worktree`), which is where every umbrella thread without an increment starts. The agent has no way to get a worktree of the one repository its task turns out to need without ending its turn.
5. The recommendation says "Use worktrees: off" for every umbrella (`apps/web/src/lib/folderLayoutGuidance.ts:31-35, 74-78`).

Anton, November 11, 2026, on Project settings > Environment after moving the project to the umbrella: "What is the workspace, and do we have workspace enabled? Because the umbrella project has nothing to clone, actually... I believe we could specify multiple folders that we use, or maybe it could recognize it and set it up automatically to this list."

Anton, November 11, 2026, on the first draft's "found automatically, added on a click": "If our umbrella project has several repos in the repositories, I would suggest making them available for worktrees. But the decision will be made by the model: which exact repositories we need to clone in worktrees."

What the Environment page does today for that project (code and the live project record, November 11, 2026):

6. "Workspace" on that page means SpecWeave's repository list, `workspace.repos` in the folder's `.specweave/config.json`. It is not a switch. This umbrella has one, listing 3 repositories (specweave, vskill, vskill-platform). The folder holds 7 clones; "Preview import" can never offer the other 4 (`apps/server/src/project/ProjectEnvironmentImport.ts:18-33, 131`), and a config with no `workspace.repos` fails the preview as "invalid".
7. The page offers three separate ways to add a repository and none shows what the folder already holds, although the server can list it (`apps/server/src/project/FolderLayout.ts`, `ProjectRepositoryPresence.ts:listNestedRepositories`).
8. Both saved entries are broken. `dbc4018e` is saved as `specwithcode-dev.git` but its checkout pulls from `specwithcode.git` ("mismatch"). `704405a3` (`specwithcode.git`) has no folder; the server resolves it to `<project folder>/.studio-repositories/<id>` (`ProjectEnvironmentPaths.ts:341`) and the page compares that with the saved empty path (`ProjectEnvironment.tsx:374-379`), so the row can only say "Checkout status unknown". "Prepare checkout" there would clone a third copy of a repository already checked out twice in the folder.
9. The approved folder `.../repositories/anton-abyzov/specwithcode-dev` is now inside the project folder and grants nothing.

## Scope

In: every Git clone inside a project folder is available to that project's threads without registration; a thread in such a project starts in its own folder and gets a worktree only of the repositories named at launch, derived from its increment, or added by the agent or the user while it runs; what the thread shows about its repositories; the composer's repository choice; a read-only repository list on the Environment page with clone controls only where a clone is needed; guardrails for disk use and dependency installs; recommendation and notice copy. Mockup: `.specweave/increments/1276-umbrella-project-default-worktree-repository-and-picker/reports/environment-repositories-mockup.html`.

Out: a project-level default repository (dropped, see D-12), registering found clones as Environment repositories, the mobile and iOS new-task flows and the routine editor (they get the server default, no picker), moving the specweave project's folder (Anton does that himself after release), writing `.specweave/config.json` from the app, changes to `repositories/anton-abyzov/specweave/src/core/workspace/`, removing existing `.studio-repositories` checkouts, how increments derive their repositories (unchanged), installing dependencies for the agent.

## Acceptance Criteria

Availability and how repositories are named

- [ ] AC-01: Every Git clone found in a project's folder (the bounded walk in `FolderLayout.ts`, a `.git` folder) is available to that project's threads with nothing to register. A launch's `workspaceStrategy.repository` and `repositories`, an increment, and `studio_worktree_add_repository` all accept the same names: the clone's path relative to the project folder (`repositories/anton-abyzov/vskill`), `.` for the project folder's own repository, or a saved Environment repository's id or checkout path. Any other name is refused with the valid names listed, and never falls back to the project folder. A link to a clone already found is not a second repository.
- [ ] AC-02: Agents can see what is available without scanning: the project context's environment section, `studio_environment_read` and the launch notice list the found repositories (name, relative path, origin as `owner/name`, checked-out branch), at most 50, then "and N more".
- [ ] AC-03: A launch that names repositories gets a thread folder with a worktree of each on one branch (today's worktree set), and a named `repository` gets a worktree of that one. An explicit choice, including `{type:"root"}`, always wins over every default below.
- [ ] AC-04: A launch for an increment gets the repositories in its `metadata.json` `repositories`, else the owners of its tasks' `Files` paths, exactly as today, whether or not those repositories are saved in Environment. Existing `handlers.ts`, `launchWorkspace` and `ThreadLaunchService` tests pass unchanged.

The default when nothing is named

- [ ] AC-05: With Use worktrees on, in a project folder that holds separate clones, a launch that names no increment and no repository (MCP launch, routine, composer, mobile, an older client) starts in its own thread folder on its own branch with no worktree yet. Nothing is checked out, so a thread that only reads or answers costs no disk. It no longer runs in the project folder, and `UMBRELLA_WORKTREE_NOTICE` is retired.
- [ ] AC-06: That thread's first message carries a notice with AC-02's list and the rules: read anything in the project folder; before changing a repository add it with `studio_worktree_add_repository`, after which it sits at the same relative path inside the thread's folder; do not edit or commit in the project folder's clones; SpecWeave planning stays in the project folder. The session loads the project folder's instruction files (AGENTS.md, CLAUDE.md) and can read the project folder, as an increment's worktree set does today.
- [ ] AC-07: Unchanged cases: Use worktrees off keeps the thread in the project folder with `WORKTREE_OFF_NOTICE`; a project that is one repository with no separate clones gets one worktree of it; a project folder with no Git repository at all works in the folder.

Adding a repository while the thread runs

- [ ] AC-08: `studio_worktree_add_repository` works in a thread whose folder holds no worktree yet, and in one that holds some. The repository's worktree appears at its relative path on the thread's branch, the turn keeps running, and the result names the path, the branch it was cut from and "Dependencies not installed". Adding a repository the thread already has returns that member instead of failing. In a thread that works in the project folder the refusal names the fix (`studio_worktree_handoff`, or Use worktrees is off).
- [ ] AC-09: A member is cut from its repository's checked-out branch, honouring `newWorktreesStartFromOrigin`. When that repository has no branch checked out (specwithcode-dev today), it is cut from its default branch on origin and the result says so; when that cannot be found either, the add is refused with the cause and the thread keeps what it had.
- [ ] AC-10: The user can do the same from the thread: the repository popover's "Add repository" lists the available repositories the thread does not have and adds the one picked through the same server action, for when the agent picked wrong or too few.

What the user sees

- [ ] AC-11: The thread header shows its branch and how many repositories it holds ("fix/environment-list · 2 repositories", or "No repository yet"). Its popover lists each repository with the branch it was cut from, "Changed" or "No changes", "Dependencies installed" or "not installed", and its pull request when there is one.
- [ ] AC-12: The timeline shows a row when the thread starts with no repository ("Started in its own folder with no repository.") and one for each repository added, saying who added it ("Agent added `specwithcode-dev`" or "You added"), the branch it was cut from and the dependency state.
- [ ] AC-13: In a project folder that holds separate clones, the composer's worktree control gets "Repositories": "Agent decides" (the default) or any checked set of the available repositories. The pick holds for that draft only and the launch sends `repositories`. A base branch picker shows only when exactly one repository is picked; it lists that repository's branches and resets to its current branch when the pick changes.

The Environment page

- [ ] AC-14: Environment > Repositories is one read-only list built on the server from the clones found in the project folder, the saved Environment repositories, and the repositories in the folder's `.specweave/config.json` (`workspace.repos`, else `umbrella.childRepos`; a missing or unreadable list counts as empty, never an error), joined by real path. The lead line reads "This folder holds 7 Git repositories. Threads can use any of them. The agent picks the ones a task changes, and the thread gets its own worktree of only those." Each row shows name, relative path, origin as `owner/name`, the checked-out branch or "no branch checked out", a "SpecWeave" tag when SpecWeave lists it, and how many thread worktrees it has. A skipped link is named under the list.
- [ ] AC-15: A row's status is "Available" (with "no remote, so no pull request" on a clone that has none), "Not on this machine" with "Clone" when it is saved or listed in SpecWeave but has no checkout, or "Folder missing" with "Clone again" and "Remove from project". There are no checkboxes, no "Add" button and no project default. "Checkout status unknown" and "Checkout: mismatch" no longer appear.
- [ ] AC-16: Saved entries the list makes redundant (their folder is a found clone, or they have no folder while a clone of the repository is in the folder) are named in one line, "2 saved entries from before are no longer needed", with "Remove both". A new clone always names its folder (default `repositories/<owner>/<name>` in an umbrella layout, else `<name>`, inside the project folder); "Leave empty for a managed checkout" is gone, and entries already using a `.studio-repositories` checkout keep working and show that folder.
- [ ] AC-18: The "Import SpecWeave workspace" section, its Workspace folder field and "Preview import" are removed, and the word "workspace" does not appear on the Environment page. The folder Check's hint (`ProjectFolderChange.tsx:514-518`) is replaced by "N repositories found. Threads can use any of them."
- [ ] AC-19: "Approved additional folders" is titled "Other folders agents can use". An entry inside the project folder is marked "Already inside the project folder, so this entry does nothing." with "Remove".
- [ ] AC-20: A project that is one Git repository with no clones inside sees "This project is one Git repository: the project folder." and the closed "Add a repository that is not in this folder", and nothing else in the section.

Guardrails

- [ ] AC-21: Disk. No worktree is made at launch unless a repository was named or an increment needs it (AC-05). A worktree shares its clone's Git objects; the app never clones a repository again to give a thread a copy. A thread holds at most 8 repositories; a ninth is refused with that reason. An add is refused, with the free space named, when the worktree volume is under the app's low-disk threshold (`DiskSpaceMonitor`).
- [ ] AC-22: Dependencies. Adding a repository installs nothing and runs no setup script. The result and the notice say so and tell the agent to run that repository's normal install in the worktree only when it builds or tests there, never by linking another checkout's `node_modules`. The thread shows the dependency state per repository (AC-11), read from the worktree (its dependency folder exists).
- [ ] AC-23: The project's clones stay clean. - [ ] AC-24: Cleanup. "Manage thread worktrees" lists a thread's folder once with its repositories; removing it removes every member worktree, prunes each repository and deletes the set's manifest. An empty thread folder is removed with its thread.

## Approach

All paths below are inside `repositories/anton-abyzov/specwithcode-dev/`. Most of the mechanism exists: worktree sets (`apps/server/src/worktreeSet.ts`, `git/worktreeSetGit.ts`), `repositories` on a launch, and `studio_worktree_add_repository` taking a path relative to the project folder. This increment removes the registration step, makes the empty set the default, and shows it.

1. One resolver. `resolveLaunchRepository` (`ThreadLaunchService.ts:128-152`) accepts what `addWorktreeSetMember` already accepts: a saved id or checkout path, else a path relative to the project folder that is a clone's own root. `repository`, `repositories` and the add tool share it, so the three ways of naming a repository cannot drift.
2. Found repositories, cached. A new `apps/server/src/project/ProjectRepositoryDiscovery.ts` builds the list from `readFolderLayout`, the SpecWeave list and the saved entries, with the bounded Git inspection `ProjectEnvironmentImport.ts` uses (5 s, `repositoryInspectionEnv`, origin and `symbolic-ref` only). It is cached per project for 60 seconds and on demand ("Check again"), so the project context, launches and the page share one walk.
3. Empty thread folder. `projectLaunchWorkspace` (`handlers.ts`) returns a worktree strategy with `repositories: []` where it returned `UMBRELLA_WORKTREE_NOTICE`; `ThreadLaunchService` applies the same rule to a worktree strategy that arrives with no repository for a folder of separate clones, so the composer, routines, mobile and older clients share it. `worktreeSetGit.ts` creates the folder, the branch name and a manifest with no members; the thread records the folder and branch as it does for a set.
4. Add. `performAddRepository` (`WorktreeMcpService.ts`) keeps its lock and manifest write, gains the base-branch rule (AC-09), the 8-member cap and the disk check, returns an existing member instead of failing, and records a thread activity the timeline renders. No handoff: the folder binding does not change, so the provider session stays attached.
5. Contracts, no new RPC (`ws.ts` import limit, TS2589). `ProjectEnvironmentReadInput` gets optional `discover: true` and the result optional `found` rows `{relativePath, path, name, origin, branch, defaultBranch, inSpecweave, state: "available" | "absent" | "missing", noRemote, threadWorktrees, repositoryId?}`, `skippedLinks` and `redundantEntries`; its presence is the support flag (AC-26). `packages/contracts/src/worktreeMcp.ts` adds `baseRef`, `dependencies` and `alreadyMember` to the add result. `prepareWorktree` in `packages/client-runtime/src/operations/commands.ts` gets optional `repositories`, passed to the existing `OrchestrationV2ThreadLaunchWorkspaceStrategy.repositories`. The popover's "Add repository" reuses the worktree toolkit's server action through the existing thread command path.
6. Page. `ProjectRepositoryList.tsx` renders the list and `projectRepositoryRows.logic.ts` holds the pure parts (row order, status text, counts, redundant entries), so `ProjectEnvironment.tsx` (700 lines) shrinks. `ProjectEnvironmentImport.tsx`, its test and the server's `ProjectEnvironmentImport.ts` preview path are deleted with the section; `ProjectEnvironmentAdoption.ts` goes with them.
7. Thread and composer. The header chip and popover extend `BranchToolbar.tsx` with logic in `BranchToolbar.logic.ts`; the timeline row sits beside `WorktreeSetupCard.tsx` in `MessagesTimeline.tsx`. `WorkspaceModeControl.tsx` gets the "Repositories" control. `ChatView.tsx` gets only the prop and the launch field.
8. Guard and copy. `ManualWorktreeGuard.ts` puts its `git` on the PATH of threads with their own folder too, refusing only the two commands in AC-23 inside a project-folder clone. `folderLayoutGuidance.ts` recommends "on" for a folder of separate clones.

Rejected: registering found clones with a click (the first draft; Anton: make them available, the model decides); a project-level default repository (it gives every thread, questions included, a worktree of the heaviest repository, and the agent or the composer pick covers the need); giving a new thread a worktree of every repository (7 checkouts and installs for a one-file fix); starting umbrella threads in the project folder and moving them on first need (a handoff ends the turn); a worktree of the umbrella's own repository as the first member (a second copy of `.specweave` on a thread branch); per-repository "available" switches (nothing asked for them); installing dependencies on add (minutes and gigabytes for threads that only edit); writing found clones into `.specweave/config.json` (a second owner for a file the CLI owns); a managed checkout for an umbrella (a hidden third copy under `.studio-repositories`).

Risks: the agent edits a project-folder clone instead of adding it (notice plus AC-23's refusal; uncommitted edits there are still possible); an agent that adds too many repositories (cap of 8, visible on the thread); `ChatView.tsx` size and churn from other increments (touch only the launch site); `ws.ts` import limit; the folder walk on a large folder (depth 3, 5,000 folders, 50 listed, cached; the page says when it stopped early); a provider that enforces folders must get the project folder as readable for AC-06, as increment sets do; the shared checkout is used by other workers (branch only on the coordinator's go).

### Defaulted (change any before sw-do)

- D-15 A thread holds at most 8 repositories.
- D-16 The user can add a repository to a running thread from its popover.
- D-17 The app's `git` refuses commits and branch switches in the project folder's clones from a thread that has its own folder.
