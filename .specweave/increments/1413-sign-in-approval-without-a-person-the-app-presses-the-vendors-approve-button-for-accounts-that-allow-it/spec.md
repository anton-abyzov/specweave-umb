# Sign-in approval without a person: a model chooses and the app presses the vendor's approve button for accounts that allow it

Version 5, November 19, 2026. Three review rounds returned "fix first" (`reports/reviews/review-muse-wonder-full-1.0-1.md`, `-2.md`, `-3.md`; answers in `reports/review-responses.md`). Round 2 kept the skeleton and asked for cuts and pins, applied in version 4 with Anton's answer on how the press is chosen (D-04). Round 3 found one blocker, the recipient named in AC-04 (R-01), and ten entry conditions (R-02 to R-11); all are applied here. Anton approved starting the build on November 19, 2026. The folder name says "the app presses": it was created before Anton chose an agent (D-01), and the folder is not renamed.

Follows 1397 (named accounts, sign-in without the terminal) and builds only after 1397 is released. It amends 1397 in two places, for accounts with this switch on only (AC-05). Auth change: no code before Anton accepts this spec.

## Problem

Anton's first request: "it knows what to do to switch the subscription without a person, for example, opening a terminal, typing `/login`, and then going into the browser and confirming this." 1397 removes the terminal and the hunt for the right Chrome profile, and leaves one step to him: the press on the vendor's approve page.

On November 18, 2026 he decided five things, the first four against the recommendation put to him:

- Who presses: "An agent presses it for both" vendors.
- What presses: "An agent with the Chrome tools", not the app by a fixed rule.
- SpecWithCode's own "Sign in" card when the switch is on: "No card, just a notice".
- The Claude half: "Everyone, off by default".
- How the press is chosen, asked after two reviews showed a model holding the Chrome tools cannot be built without storing the page and the link in a thread: "A model chooses, the app presses".

What the code allows and what it does not. App paths are in `repositories/anton-abyzov/specwithcode` at `origin/main` `a0e87a0ae`; each was opened while answering the review.

1. **Anthropic's terms.** Consumer Terms, prohibited uses: "Except when you are accessing our Services via an Anthropic API Key or where we otherwise explicitly permit it, to access the Services through automated or non-human means, whether through a bot, script, or otherwise." Claude Code's legal page adds a sentence for developers: "Anthropic does not permit third-party developers to offer Claude.ai login into their own applications". A press on `claude.ai` made by software, shipped to every user, falls under both. OpenAI's terms do not address a sign-in press.
2. **With a model choosing and no card, nothing a person does stands between an agent's request and a signed-in account.** Every stop has to be a refusal by the server. A sentence in a model's instructions is not a stop.
3. **A setting is writable by every client.** `serverUpdateSettings` needs only `settings:write` (`apps/server/src/auth/RpcAuthorization.ts:139`), which every standard client holds, remote and paired ones too (`packages/contracts/src/auth.ts:224-238`). A session does carry where it came from: the desktop shell's is `desktop-bootstrap`, handed over at launch (`apps/server/src/auth/PairingGrantStore.ts:279-284`, `:366-369`), and a handler has the session (`apps/server/src/ws.ts:1325`).
4. **No run exists that holds exactly three tools and stores nothing.** A provider turn needs a thread and a run (`apps/server/src/orchestration-v2/ProviderTurnStartService.ts:157-160`); the `chrome_*` tools need a thread caller (`apps/server/src/mcp/toolkits/chrome/handlers.ts:68-78`); a thread's tool inputs and results are stored, shared with every connected device, and written to provider event files (`apps/server/src/provider/ProviderEventLoggers.ts:67-89`). What does exist is a one-shot model call with no tools and no thread, used for titles and commit messages (`apps/server/src/textGeneration/ClaudeTextGeneration.ts:183-203`, with `--tools ""` and `--strict-mcp-config`; `apps/server/src/textGeneration/CodexTextGeneration.ts:191-211`, with `exec --ephemeral -s read-only`). The two are not alike. Claude's argv removes the tools; Codex's names a sandbox policy and passes the person's launch arguments through (`apps/server/src/provider/codexLaunchArgs.ts:10-20`), so its shell, web search and MCP servers remain. Claude's argv has no flag that stops the CLI keeping its own transcript; the CLI has one, `--no-session-persistence` (Claude Code 2.1.302, `claude --help`: "sessions will not be saved to disk"). Whether Claude's run is tool-free and leaves nothing in practice is gate G1's question, not a fact stated here.
5. **The page reader threads use cannot carry a refusal.** `snapshotScript` runs inside the page with the page's own functions, sees only the top frame, and does not look into shadow roots or frames (`apps/server/src/browserExtension/pageScripts.ts:7-27`, `:34-70`). A click looks the element up again and presses at coordinates, with nothing checked in between (`apps/server/src/browserExtension/chromeTools.ts:398-412`). Its results carry the full address, link targets and input values (`pageScripts.ts:60-68`).
6. **A paired Chrome profile is known only by what it says about itself.** The label, extension id and install id all arrive in one hello (`apps/server/src/browserExtension/relayHub.ts:171-179`); a profile is found by label, then by a part of it (`relayHub.ts:504-513`); pairing state is one token per machine (`apps/server/src/browserExtension/pairingState.ts:12-16`). A 1397 account names a Chrome profile by folder (`packages/contracts/src/externalBrowser.ts:51-54`), which no extension can report. Nothing ties the two.
7. **Any thread can take any tab.** `chrome_tabs` lists every tab with up to 500 characters of address (`chromeTools.ts:274-294`); a tab is held only while its thread acted in the last 120 seconds (`relayHub.ts:27`, `:522-546`); a thread on another machine acts through `chrome_peer` (`apps/server/src/mcp/toolkits/chrome/handlers.ts:490-521`).
8. **The relay keeps addresses.** Its audit records an opened address, up to 300 characters, and every client can read the last 50 (`relayHub.ts:575-585`).
9. **A sign-in started for an account that is signed in is destructive.** 1397 AC-06: it "is signed out first and stays signed out if you cancel. Running threads on this account stop".

## Scope

In: a per-account switch, off by default, for Codex and Claude accounts of every user; a model on a Claude instance that reads a reduced view of the vendor's sign-in page and chooses what to press; the server's reader, refusals and press; the notice and the record.

Out: typing anything into a vendor's page (a password, a 2FA or emailed code); answering a passkey prompt or a robot check; signing in to the vendor's website when the profile is signed out; signing in an account that is signed in; creating accounts; turning on takeover at a limit (1400); vendors other than OpenAI and Anthropic; a model on any provider but Claude reading the page (a person with no Claude instance cannot turn this on); machines that run SpecWithCode without the desktop app; any new Chrome permission.

### Reading, choosing and pressing

- [ ] AC-07: The server reads the page through the debugger (the document and accessibility trees of every frame, shadow roots included), never through the in-page script. From it the server builds the reduced view: title, host and path, visible text capped at 8,000 characters, and a list of at most 40 controls with role and name in which only the pressable candidates (buttons and G3's chooser entries) are numbered; every other control is listed unnumbered as context. Removed from every field of the view before anything leaves the server, in this order. First by exact value, since the server holds them: the full link, its `state`, Claude's code once read, and the percent-encoded form of each, wherever they appear, in the title and in a control's name too. Then by kind: the query and fragment of every address, every link target, every input value, and any string that has the shape of an address or of Claude's code (the pattern at `apps/server/src/provider/ClaudeCliLogin.ts:83`).
- [ ] AC-08: The model is called once per step through a new text-generation operation, `chooseSignInPress`, which only the Claude runner implements (`apps/server/src/textGeneration/TextGeneration.ts:122-176` has fixed operations and none fits). It is optional: it is not part of the shared `TextGenerationOperations.fromRunner` shape, the Claude runner's assembly alone adds it, and `TextGeneration` refuses the call when a provider's service has none (the `generateHandoffNote` pattern, `TextGeneration.ts:306-318`). Its argv is the existing one-shot argv (`ClaudeTextGeneration.ts:183-203`) plus `--no-session-persistence`, with the model picked in AC-03, a throwaway working directory removed after the call (as titles use, `:172-182`), fixed instructions shipped in the code and the reduced view as its only input. The 25-second limit, the throwaway directory and the extra flag are one branch of that operation inside the Claude runner, and the service-level working directory the call carries (read by the capacity and team-rules checks, `TextGeneration.ts:218-233`) is the same throwaway directory, so no project folder is consulted; a test shows a sleeping fake CLI is dead at the deadline and the flow ends. Its answer is held to a schema with two shapes: the number of a numbered control on the server's list, or "needs a person" with a reason that is a literal from a fixed union, never free text. Each call has its own 25-second limit, not the runner's 180 seconds (`ClaudeTextGeneration.ts:38`); at most three steps and 90 seconds per flow. There is no thread and no move to another model or instance: a call that fails, runs out of time or is refused for capacity (`TextGeneration.ts:240-255`) ends as "needs a person".
- [ ] AC-09: The press is one server step with these properties, whatever commands G2 finds for them: the tab's address is read again from Chrome's tab record, and the step is refused while the tab is loading or has a pending address that differs; control N is read again by node and refused if the address, role or name differ from the view that was answered; and in the same step, immediately before input, the whole condition set of AC-11 to AC-13 is run again on that re-read (address and pending address, the editable scan, the robot-frame scan, link or form target, the expected email, node identity, role and name); the press is trusted input at that node's position as just read, never a click made by script in the page. The answer can name only a number on the list.
- [ ] AC-10: Each step runs in this order: the refusals of AC-11 to AC-13, then the code, then the choice. Where Claude's sign-in still shows a code after 1397 T-06, the server reads it from the tab by the existing shape check (`readClaudeLoginCode`, `ClaudeCliLogin.ts:90-102`), hands it to the waiting CLI process and ends the steps. The code reaches no model.

Any other address, an identity provider's page included, ends the steps. A page dialog on the flow's tab is left unanswered and ends the steps; the hub's automatic answers (`relayHub.ts:344-357`) do not apply to it.

### How it ends

- [ ] AC-14: Success is the CLI reporting the sign-in finished, and nothing else. When the tab leaves the sign-in pages the steps stop and the server waits 20 seconds for the CLI. A refusal, "needs a person", the time limit or that wait running out ends the start: the server closes the tab first and, once that call resolves, cancels its own flow and records the start. A success ends the same way: close the tab, then record. No live flow is handed over. The row and the notice give the reason ("Claude asked for a password", "The page shows another email", "Robot check") and 1397's "Sign in", which starts an ordinary 1397 sign-in. Nothing retries by itself.
- [ ] AC-15: After a success 1397's email check decides: another email holds the account as "Wrong account". A pressed sign-in never clears a hold.

## Approach

**The model chooses and the server presses** (D-04, Anton's answer). A model that held the tools itself would need a thread, and a thread's inputs and results are stored and readable by other threads and devices (Problem 4). So the server reads the page, gives the model a reduced view, takes one answer and makes the press itself. The model is given no tools, which G1 has to show, and never receives the link.

A `SignInPress` service beside 1397's `ProviderAuthFlow` replaces the "open link" step for an account with the switch on. `signInPageReader.ts` reads the page over the debugger; `signInPressGuards.ts` holds every refusal and is the only code that lets a press through; `SignInPressRun.ts` makes the one-shot call through the text-generation layer. The switch has its own store and its own call, in new files; `rpc.ts` and `ws.ts`, both far over 1,500 lines already, get one registration line each.

Order: 1397 released → T-01 → T-02 → T-03 → T-04, then Anton's watch-only sign-ins for G3 → T-05 → T-06 → T-07 → T-08.

Risks, stated plainly:

- **Anthropic may act on an account** whose sign-in was pressed by software, and its sentence for developers puts SpecWithCode itself in question for shipping this to every user. AC-04 tells the user. A lawyer's read before the release is recommended; by D-03 it is not a gate.
- **The server does not know which control approves.** It refuses pages and controls that are dangerous by kind. Among what is left, a wrong choice by the model can press "Deny", "Use another account" or a sign-out button: a failed sign-in, a held "Wrong account", or that Chrome profile signed out of the vendor's website.
- **The page's text goes to the service the picked Claude instance is configured to use**: Anthropic for a claude.ai subscription sign-in, otherwise its API, Bedrock, Vertex, Foundry or a custom address, under that service's terms; for an OpenAI sign-in too. It carries names, emails of every account on a chooser, plan and organisation names. The link, state and code do not.
- **The page can still move the press in the last interval.** The refusals are run again on the re-read immediately before input, but between that re-read and the trusted press there are separate relay calls, and a page that watches the press sequence can move a control under the point. That residual risk is the same as the one already admitted for a wrong choice.
- **Only a Claude instance can read the page.** Codex's one-shot run keeps its tools (Problem 4), so it is not used. A person with Codex accounts and no Claude instance cannot turn the switch on.
- **The switch is safe against the app's interfaces, not against the machine.** A program, or an agent with full access, running as the same user can edit the switch's file, mint a session with any subject through the offline CLI (`apps/server/src/cli/auth.ts:291-311`), or run script in the desktop window.
- **The pairing token is the relay's only authentication** (1394 AC-03 says so itself). The install id is self-asserted. A local program holding the token, or another paired profile claiming the id, replaces the real connection and receives the link. Binding by install id narrows this to a deliberate attacker; it does not close it.
- **Whether a link is usable alone is not shown.** The app's own managed Codex sign-in keeps a verifier the link does not carry (`apps/server/src/provider/CodexChatGptAuth.ts:526-532`, `:588-591`); that is not evidence for the Codex CLI or for Claude Code, which is closed. AC-01 records evidence on the first. Both are treated as usable.
- **A vendor may show a robot check** to a tab with the debugger attached. Then every start ends in "needs a person" and the switch is not offered for that vendor (G3).

Rejected: a model holding the `chrome_*` tools in a thread, hidden or not (stored and shared, Problem 4); the asking thread pressing; a provider run with a tool allow-list (no such mode is shown for any provider at `a0e87a0ae`); matching the 1397 profile folder to a paired label automatically (Problem 6); storing the run's inputs "redacted" (the vendor CLI's own transcript is not the app's to redact); the app pressing by a fixed rule with no model (offered on the D-04 card, not chosen); Codex's one-shot run reading the page (it keeps its tools); an extension content script (new permission).
