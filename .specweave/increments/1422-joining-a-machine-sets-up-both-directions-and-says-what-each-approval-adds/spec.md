## Acceptance Criteria

- [ ] AC-01 [label]: The device pop-up says what Allow adds and that letting a machine's agents run work is separate: Allow lets the SpecWithCode app on that device open this machine (chats, terminals, files, settings, sign-ins). No reassurance keys on the device's own name; the line that the name is the device's own word stays.
- [ ] AC-02 [label]: The joined notice on the machine that was joined says the join is one way: its agents can run work on the new machine and its app can open it; the new machine cannot use this machine. It offers Allow for the reverse direction (D-02), which nothing grants by itself.
- [ ] AC-03 [label]: The Allow on the new machine says what it covers: the other machine's agents may run work here and its SpecWithCode app may open this machine, with no second code; this machine gets no access to the other one.
- [ ] AC-09 [label]: The join's done card names the next step with 1390's verbs (Add a project to this machine) instead of sending the owner to the other machine's Settings.
- [ ] AC-04 [label]: First run names no main machine: the row reads as joining one of your machines (wording agreed with the 1390 owner so join, Sync and Hand off read as one concept).
- [ ] AC-05 [access]: After a join, the app that typed the new machine's code on the joined machine opens the new machine with no second code and no pop-up: the joined machine vouches for that app with the credential the join gave it, and the new machine checks that proof. No other device gets a vouch. It applies only when the grant the Allow gave is full access to all projects and all sign-ins (D-05); a capped, project-limited or sign-in-limited grant, an older machine on either side, or a request without a valid proof falls back to the code. Remove and revoking the grant end it. (D-01)
- [ ] AC-06 [access]: A join grants agents one way only. The reverse is offered on the joined machine (AC-02) and set up only by the owner's Allow there. (D-02) After that Allow the new machine's app does not open the joined machine by itself: the automatic open is skipped for a machine whose only tie is the reverse grant, and the new machine's app reaches the joined machine only if the owner opens it there and types a code. (D-06)
- [ ] AC-10 [access]: The code typed on the joined machine lets the new machine join and hand over its line; it gives the new machine's app no lasting access to the joined machine. A machine joined before this change keeps what it has until the owner removes it. (D-03)
- [ ] AC-07 [label]: Every new string goes through the translation function with entries for the eight shipped languages.
- [ ] AC-08 [label]: Checked after release with two real machines by Anton: the join's screens, then what each machine can open and run on the other.

## Decisions

- D-01 [access] Should the join stop asking for the second code? → Drop it; Allow covers it, and the Allow says so (Anton, November 19, 2026: "drop it. I think allow covers it, but just explain this"). Built as AC-05 and AC-03.
  Options weighed for Anton's "a code sounds tricky" (November 19): a one-click Allow for any device signed in to the same account would drop the guarantee the code gives, because a stolen sign-in is also the same account and the name is the device's own word (why 1327 kept the code, November 17). Comparing a code shown on both screens and clicking Allow is lighter but easier to click through. What keeps the guarantee and drops the typing is proof from a machine already trusted: the joined machine vouches for its own app with the credential the join gave it, which an attacker with only a sign-in does not have. So one typed code stays per new machine, and every later prompt between the two machines is covered by that proof.
- D-02 [access] Should a join let agents run work both ways? → One way; offer the reverse (Anton, November 19, 2026). Built as AC-06 and AC-02.
- D-03 [access] Should the code typed on the joined machine give the new machine's app access to it? → No, the code only joins (Anton, November 19, 2026, card answer "Yes, the code only joins"). Anton, November 19, 2026, on "Your first code let Windows's app into M5": "I think this Windows machine has no access to M5. I never intended this to be, or maybe I interpreted it wrong." It does today: M5's records show Windows's app approved at 9:54:29 AM with a live session, and photo 3 shows Windows listing M5's projects through it. Today that code approves the new machine's app as a full device on the joined machine (1327), because its app hands the join line over through that session (`accountJoinFleetWorkers`). Built as AC-10; replaces the November 17 reading in `decision_machine_join_flow` that the code is an ordinary device approval.
- D-04 [access] Should the new machine remember the access level chosen at Allow and refuse anything higher, even if the joined machine asks for more later? → Yes, remember my choice (Anton, November 19, 2026, card answer "Yes, remember my choice"). Built in T-03 as `ownerCap` (Design, section 2); it holds the capped half of AC-05.
- D-05 [access] Should the no-code vouch also need all sign-ins, not only all projects? → All projects and all sign-ins (Anton, November 19, 2026, card answer "All projects and all sign-ins"). Built as AC-05's condition.
- D-06 [access] After the reverse Allow, should the new machine's app open the joined machine by itself? → No (Anton, November 19, 2026, card answer "Don't open M5 by itself"). The automatic open (`apps/web/src/cloud/GrantedAccountMachines.tsx`) is skipped for a machine whose only tie is the reverse grant; the new machine's app reaches the joined machine only if the owner opens it there and types a code. Built as AC-06, in T-04.

## Approach

D-01's vouch reverses a property project memory lists as sound ("A management key cannot approve devices itself"), within the bounds of AC-05; the design note and the review name it. It widens nothing only while the grant is full access to all projects, hence AC-05's condition. Which key the vouch names is not settled: read `apps/web/src/cloud/managedRelayLayer.ts` and the `relay.connection.deviceIdentity.resolve` span first, because a server does not obviously know the proof key of the app that typed a code (the local desktop app may approve over its local session). Design note and a Muse Wonderful design review come before code; tests fail first. T-07's strings ship together with T-03 and T-08, never ahead, since they are false before.


Wording first (AC-01 to AC-04, AC-07), then D-01 and D-02 as decided. Each side words only what it knows for certain: a window knows which machine it waits on, and a machine knows which machine it just allowed. A device request carries no machine identity (`packages/contracts/src/connectDevices.ts`), so the pop-up never claims "this is M5".

Code was read at `origin/main` `c924fa8340` of `repositories/anton-abyzov/specwithcode`, rechecked in round 3 at `2504755da` (three cited ranges moved and were updated) and in round 4 at `0b80025bb` (no cited file changed). Round 4 answers design review 1 (`reports/design-review-1.md`, "fix first"); each answer names its finding. `D/` is `apps/desktop/src/`. Path prefixes: `S/` is `apps/server/src/`, `W/` is `apps/web/src/`, `C/` is `packages/contracts/src/`, `R/` is `packages/client-runtime/src/`. J is the joined machine (M5), N is the new machine (Windows).

#### Facts the design rests on

- Order today: N's app picks J, which opens J over the relay at once (`W/components/settings/AccountJoinCard.tsx:235-262`). J has not approved N's app, so N shows J's code where Allow would be (`W/components/settings/IncomingWorkerSetup.tsx:258-263`). The code is typed on J before Allow, not after. Allow then mints N's line on N and posts it to J (`W/studio/fleet.ts:404-426`).
- A device is its relay proof key, `jkt:<thumbprint>` (`S/fleet/ConnectDeviceTrust.ts:126`, `:162-171`). The code approves that key as a full device: `approve` writes a `DeviceRecord` (`:993-1040`), and every later session of the key passes the gate (`:912-913`, `S/auth/EnvironmentAuth.ts:642-665`).
- `accountJoinFleetWorkers` needs only `orchestration:operate` and a Connect subject (`S/studioFleetHttp.ts:777-821`). It has no join-specific approval; it relies on the device gate above.
- Scopes cannot make a session join-only. Of 60 authenticated HTTP endpoints, 8 check no scope: the websocket ticket (`S/auth/http.ts:650-663`) and the six `connect-devices` routes, where an approved device is an approver whatever its scopes (`S/auth/connectDevicesHttp.ts:40-61`). `orchestration:operate` alone also opens `/ws` RPCs and project changes.
- The join gives J two credentials on N: a management token (subject `fleet-invitation`, coordinator principal J, Standard scopes plus `access:write`, bound to J's fleet key, 365 days, never renewed; `S/studioFleetHttp.ts:614-693`, `S/fleet/fleetRedemption.ts:24-29`) and a worker grant (subject `mcp-client`, 30 days, renewed; `S/fleet/workerGrantMint.ts:348-395`). Neither can approve devices today (`S/auth/connectDevicesHttp.ts:28-31`, `:51-52`).
- J's server never sees its own app's proof key. The local app signs in with a bearer or a cookie, and the approver is recorded as `key: null`, "this machine" (`S/auth/connectDevicesHttp.ts:58-60`). The key lives in the app's IndexedDB (`studio:cloud-auth`, id `relay-dpop-proof-key`, private half not extractable; `W/cloud/dpop.ts:24-27`, `:135`), one per install and OS user, shared by its windows. It is used only towards other machines (`W/cloud/managedRelayLayer.ts:16-37`). The span `relay.connection.deviceIdentity.resolve` (`R/authorization/service.ts:423-425`) resolves a relay device ID that the web and desktop app never send (`W/connection/platform.ts:341-343`); it does not name the key.
- N does not bound the grant's access level. J sends the level it wants at mint (`S/fleet/workerGrantMint.ts:277`), N copies it into the session (`S/auth/McpOAuth.ts:613-623`, `S/auth/EnvironmentAuth.ts:1654-1656`), and the level lives only in the signed token (`S/auth/SessionStore.ts:575-587`, claim `rtc`). The owner's choice in the Allow card is sent to J and never stored on N. `runtimeCap` in `work-grants.json` is copied from the caller's token on its first `/mcp` call (`S/fleet/WorkGrants.ts:519-523`). Project and account limits are different: only N's owner can change them (`S/studioFleetHttp.ts:227-241`, `:447-455`).
- Stop on N revokes every session of coordinator J, the management token included, and Restore does not bring it back (`S/fleet/WorkGrants.ts:650-665`, `S/persistence/AuthSessions.ts:317-341`). Remove on J revokes the management token on N (`S/studioFleetJoin.ts:586-639`).
- Older builds drop unknown keys on decode (Effect's default) and lose them on the next write. `connect-devices.json` is decoded that way (`S/fleet/ConnectDeviceTrust.ts:327-343`). Exact input structs refuse unknown keys with an empty 400: approve (`C/connectDevices.ts:11-17`, `:101`) and account-join (`C/studioFleet.ts:124-127`, `:158-161`). `/oauth/token` ignores unknown form fields (`C/auth.ts:323-332`). The descriptor is readable with no credential and the client reads it before the token exchange (`C/environmentHttp.ts:722-726`, `R/authorization/service.ts:454-463`).

- The window that opened N by itself is `W/cloud/GrantedAccountMachines.tsx:253-256` (selection in `W/studio/grantedAccountMachines.ts:30-77`): it saves a Connect route for each account machine that granted this one. `AutoConnectPrivateMachines.tsx` and `fleetAutoConnect.ts` are the Tailscale path (`W/studio/fleetAutoConnect.ts:155-161`, `:180`) and did not act in this join. The Problem table and `reports/evidence.md` now say so.
- "Owner" in `deviceApprover` is not "the app on this machine". Any session with `access:write` and a device principal counts (`S/auth/connectDevicesHttp.ts:58-60`), and a window on another machine can hold one: a pairing code made on J with "Manage access" ticked and redeemed there, the startup link of a web-mode server, or a token from `auth session issue`. The fleet's own "Connect machine" codes do not count, because they carry a coordinator principal (`S/studioFleet.ts:523-531`, `S/auth/http.ts:725-728`). Such a window reaches J over Tailscale, the LAN or an SSH tunnel, so "not over Connect" does not single out J's app either: `arrivedOverConnect` reads headers only and is documented as a reason to refuse, never to grant (`S/auth/CredentialFailureLimiter.ts:158-170`, `S/fleet/fleetOrigin.ts:70-74`). The peer address does not help: Tailscale Serve, the Connect tunnel and an SSH tunnel all arrive from loopback.
- What does mark J's own app: the session subject `desktop-bootstrap`. The server gives it only for a token derived from a secret the desktop app passes to the server it starts, over a private channel (`S/auth/PairingGrantStore.ts:545-553`, `packages/shared/src/desktopBootstrapToken.ts:4-8`); the exchange copies the subject into the session (`S/auth/EnvironmentAuth.ts:1129-1134`), and the pairing route can only ever mint `one-time-token` (`:1356-1360`). When the app instead attaches to an installed service, nothing marks it today: it pairs through the service's command line and gets `one-time-token` with a device principal and a label anyone can choose (`D/backend/localServiceAttach.ts:352-362`, `S/cli/pair.ts:268-281`), the same shape as a code redeemed on another machine.

#### 1. D-03: the code approves the join only

**Who declares it.** N's app, in the token exchange on J: a new optional form field `client_purpose=join` on `POST /oauth/token` (`S/auth/http.ts:571-649`). Nothing changes at the relay, which is out of scope. N sends it only when J's descriptor carries the new capability `deviceJoinApproval`; an older J would ignore the field and approve a full device, so against an older J the new N uses today's flow and today's words.

**What the server enforces.** The claim can only narrow, so it needs no proof.

- The session J issues carries a signed claim `pur: "join"` (a new optional key in `SessionClaims`, `S/auth/SessionStore.ts:575-587`) and one scope, the new `fleet:join`, which maps to no RPC, like `fleet:update` (`C/auth.ts:102-113`). `DeviceSessionFacts` (`S/fleet/ConnectDeviceTrust.ts:91-102`) gains `purpose`.
- A waiting request has a kind. The entry is first written at the relay mint from the thumbprint alone (`S/cloud/CloudLink.ts:1820-1825`) with kind "device". The kind becomes "join" when a join session asks (`ensureWaiting`, `S/fleet/ConnectDeviceTrust.ts:744-812`). The code is only ever revealed to a session (`:920-925`), so the kind is set before the code can be read. A later relay mint for the same key (`refuseAtMint`, `:933-949`) never changes an existing request's kind or code. If a session of the other kind asks for the same key, the kind changes and the code is replaced: a code approves exactly the kind it was shown with.
- `approve` on a join request (`:993-1040`) writes no `DeviceRecord` and no "new device" notice. It writes a join approval into a new top-level array `joins` of `connect-devices.json`: `{ key, approval, approvedAt, expiresAt, ticket, machine, state, attestation?, approverAppKey? }` (`state` is finding 2's reservation). A separate array fails closed: an older build drops it and the key is unapproved again. `isApproved`, `bindingFor` and `deviceApprover` never read `joins`, so the key cannot approve devices, mint bound credentials or pair anything.
- The gate (`check`, `:892-931`) lets a key with a live join approval in only for a session whose claim says join, and marks the verdict join-only. A session without the claim finds no `DeviceRecord` and waits for a full-device code as today. A join approval never becomes a device approval.
- Deny by default at the source. `authenticateHttpRequest` and `authenticateWebSocketUpgrade` (`S/auth/EnvironmentAuth.ts:1489-1527`) refuse a join-only session. Two callers opt in: `layerAuthenticatedAuth` when the endpoint is `accountJoinFleetWorkers` (the middleware is handed the endpoint and ignores it today, `S/auth/http.ts:436-471`), and `getSessionState` for `GET /api/auth/session` (`S/auth/EnvironmentAuth.ts:874-899`). So no websocket ticket, no `/ws`, no media, no raw route, no `connect-devices` route. `/mcp` already refuses the subject (`:1576-1577`).
- `accountJoinFleetWorkers` accepts `fleet:join` from a join-only session, or `orchestration:operate` from a fully approved device as today (`S/studioFleetHttp.ts:781`). Its other refusals stay.

**What the approval gets, and when it ends** (review 1, finding 2). One `accountJoinFleetWorkers` run, reserved before anything happens. A join approval has a state in `joins`: `ready`, `reserved { digest, at }` or `spent { digest, result }`, where `digest` is the SHA-256 of the line. After its checks and before `addAndAllowWorkers` (`S/studioFleetHttp.ts:368-391`, called at `:800`), the handler calls `reserveJoin({ key, approval, digest })`, which runs under the trust store's one lock (`S/fleet/ConnectDeviceTrust.ts:539`, `:670`, `:687`), so two requests that both passed authorization cannot both get past it. Only `ready` becomes `reserved`. When the run ends, the same lock writes `spent` with the answer (`{ id, workers, appOpens, vouchedKey }`). What another request gets:

- `reserved`, same line: 409 "This join is still running." N's app asks again after 4 seconds.
- `spent`, same line: the stored answer, with no second add, allow or vouch. A lost answer is recovered this way.
- Any other line, in any state but `ready`: 403 "This code was already used for a join. Ask for a new code."
- A run that failed before the line was redeemed (`addMachine` refuses before `redeemFleetInvitation`, `S/studioFleetJoin.ts:336-365`) puts the approval back to `ready`, so N may try again with a new line. A run that failed after it ends `spent` with the failure, and a new code is needed.
- A reservation older than 2 minutes (a server restart mid-run) reads as `spent` with "interrupted" and is never run again, since its line may be redeemed already.

The join session stays until the approval's 10 minutes end, so the stored answer can be fetched again; spent, it reaches nothing else. Unspent, the approval ends 10 minutes after the code was typed; the session itself lasts at most 1 hour (`S/auth/EnvironmentAuth.ts:1137-1141`). After that N's app has nothing on J. A machine joined before 1422 has a `DeviceRecord` and keeps it until the owner removes it.

**N's app.** It must not save a route to J. For a J with `deviceJoinApproval` the join card holds an in-memory join handle instead of `environmentCatalog.register` (`W/components/settings/AccountJoinCard.tsx:235-262`): a proof-bound token from the same mint and exchange, kept out of the saved token cache (`R/authorization/service.ts:502-665`, cache key gains the purpose), and a poll of `GET /api/auth/session` on J every 4 seconds for the code and then for "approved". `throughAccount` (`W/components/settings/IncomingWorkerSetup.tsx:256-257`) takes "join approved" in place of `operateThere`, and `joinAccountMachineForWorkers` (`W/studio/fleet.ts:404-426`) posts with that handle. The handle is dropped after the join, on failure and when the card closes, so N stops asking J. If the approval ran out before Allow, the next poll starts a new request with a new code. If the answer to the join is lost, a retry with the same line gets the stored answer; once the session has ended, the card reads N's own "Who can run work here" list, shows the done card when J is on it, and asks for a new code only when it is not. An N whose app is already a full device on J keeps today's path.

**Only a join-aware window shows or approves a join** (review 1, finding 7). A window older than J's server would show a join request with PR 712's full-device words (`W/components/devices/ConnectDeviceViews.tsx:325-330`). A window learns of requests only through `POST /api/auth/connect-devices/list` (`W/studio/connectDevices.ts:29`; no socket feeds the pop-up, so no RPC changes) and approves by code alone (`C/connectDevices.ts:101`), so both are gated:

- The list input gains optional `understands: ["join"]`. The list (`S/auth/connectDevicesHttp.ts:124-136`) leaves join requests out for a caller that did not send it. The input is exact, so a new window sends it only to a server that advertises `deviceJoinApproval`.
- The approve input gains optional `join: true`, sent by a window that showed the join request. A code that matches a join request without it answers "not-found" and changes nothing. It is not counted as a wrong code (`S/fleet/ConnectDeviceTrust.ts:998-1005`), and no status is added (`C/connectDevices.ts:104`).
- J notes when a join-aware window last listed. J's answer to N's join session carries `approverReady: false` when none did in the last 30 seconds, and N's card adds "Open SpecWithCode on {machine} to type this code. If it is not there, or the code is not found, update the app on {machine}."

**An older new machine.** It sends no purpose, so its request is an ordinary device request: J's pop-up says so, and the code approves a full device as today. D-03 cannot be enforced against a client that cannot declare the join, short of refusing it; the stated fallback is the code as today. Removing that approval after the join is an option, under Open for the owner, item 10.

**What each screen says** (T-07; every string through `tx` with eight languages).

- J's pop-up for a join request (`C/connectDevices.ts:46-68` gains optional `purpose`; `W/components/devices/ConnectDeviceViews.tsx:236-261`, `:327`): "{device} wants to join {machine}. Typing its code lets it hand over a line, so agents on {machine} can run work on it. It does not let that device open {machine}." The line that the name is the device's own word stays. A plain device request keeps PR 712's wording.

- J's joined notice and N's Allow: see 2 and 3.

#### 2. D-01: the joined machine vouches for its own app

**The key, and proof that it typed this join's code** (review 1, finding 1). The key is the relay proof key K of the SpecWithCode app on J in which the owner typed the join's code, `jkt:<thumbprint>` of the key in that app's IndexedDB. N does not take J's word for which key that was. It checks a one-use attestation signed by K over values N issued itself, tied to the approved join, both machines and N's own app key A:

1. **Ticket.** Before the token exchange on J, N's app asks its own server for a join ticket: new `POST /api/studio/fleet/join-ticket` (owner only and same-origin, as `requireGrantManager`, `S/studioFleetHttp.ts:227-241`), with a `dpop` proof signed by A. N stores `{ ticket (128 random bits), appKey: A, coordinator: J's environment ID, expiresAt: 10 minutes, state: "open" }` in a new `tickets` array of `connect-devices.json`.
2. **The join request names it.** The exchange on J sends `client_join_ticket` and `client_join_machine` (N's environment ID) with `client_purpose=join`. J keeps both on the waiting request; a different ticket for the same key counts as a kind change and replaces the code.
3. **The line names it.** At Allow, N's app mints the line with `joinTicket` next to `access` (`C/studioFleet.ts:215-226`). N binds the ticket to that line, and at redeem (`S/studioFleetHttp.ts:614-693`) to the management session it issues.
4. **K signs.** When the owner types the code into a join request, J's window signs with K a JWT with header `{ typ: "studio-join-attest+jwt", alg: "ES256", jwk: K }` and claims `{ tkt, j: J's environment ID, n, a: A's thumbprint, iat, exp: iat + 10 minutes }`, and sends it as `attestation` with the approve. The signer is the one DPoP proofs use, with the same non-extractable key (`W/cloud/dpop.ts:145-184`); T-03 adds `createJoinAttestation` beside `createBrowserDpopProof`. J's approve handler (`S/auth/connectDevicesHttp.ts:137-153`) verifies the signature and the `jwk`, checks that `tkt`, `n` and `a` are the matched join request's (`a` is the requesting key) and `j` is J, and stores the attestation on the join approval, with `approverAppKey` its thumbprint. It reads it only from the two subjects below; from anyone else the join is approved with no attestation.
5. **N verifies.** J forwards the attestation unchanged in the vouch. N accepts it only when the signature verifies with the header's `jwk`; `jkt(jwk)` is the `thumbprint` being vouched; `tkt` is an open ticket N issued; the calling management session is the one redeemed from the line bound to that ticket; `a` is the ticket's app key; `n` is N; `j` is the session's coordinator and the ticket's; and `exp` has not passed. The ticket is spent under the trust lock in the step that writes the vouch, so one ticket vouches once.
6. **N's app confirms.** The vouch is written `pending`. J's answer to N's app over the join session carries the vouched thumbprint (`vouchedKey`), and N's app posts it to its own server: new `POST /api/studio/fleet/vouch/confirm { ticket, thumbprint }`. The vouch stands only when the two match; a mismatch, or no confirm within 2 minutes, deletes it.

What N then knows: the vouched key's holder signed for this join, for N's app's own request, for these two machines, once and within 10 minutes, and J's server and J's answer to N's app name the same key. Step 6 covers a stolen line: a thief who redeems it holds the management session for that ticket and can sign an attestation with its own key, but J's own redeem then fails, N's app gets no successful join answer and never confirms. That K is J's own app, not some other window on J, still rests on J's server, which N cannot look into; the next paragraph is how J decides it.

**Only J's own app.** The attestation is accepted only when the approving session's subject is one of two that only the app on J can hold. Review 1 keeps this check as necessary but not sufficient, which the attestation above adds to. Neither the caller's scopes nor how the request arrived decides it.

- `desktop-bootstrap`, which exists today, for an app that started its own server.
- `local-desktop-app`, new in T-03, for an app attached to an installed service, where `desktop-bootstrap` does not mark the app (review 1). Without it such an install always falls back to the code. `POST /api/auth/pairing-token` (`S/auth/http.ts:707-771`, input `C/auth.ts:504-513`) gains optional `localApp`. The server honours it only when the caller's subject is `local-cli-credential`, the in-memory credential the service keeps in an owner-only file on J (`S/auth/LocalCliCredential.ts:44`, `:57-63`), and then mints the code with subject `local-desktop-app` instead of `one-time-token`. Only the desktop's own `pair` call passes the flag (`D/backend/localServiceAttach.ts:352-362`, `S/cli/pair.ts:268-281`); `auth pairing create`, which an SSH-attached window on another machine uses (`packages/ssh/src/tunnel.ts:776`), never does. The new subject gets everywhere the old one is named for this app (`S/auth/SessionStore.ts:138-152`, `S/design/DesignRpc.ts:32-46`).

Every other approver gets no vouch and the join still completes: a window paired from another machine, a browser tab on J, a remote device, a session from a pasted token. Not passing over Connect stays as an added refusal, never as the reason to accept. Both subjects rest on the same footing: a process running as the owner on J could read either secret, and it already owns J. The one way to carry such a session elsewhere is deliberate: `auth session issue --subject` in J's terminal with the service stopped (`S/cli/auth.ts:291-326`); T-03 refuses both subjects there.

**The chain.** Ticket on N for A → code typed in J's app, which signs the attestation with K → join approval for A, holding the attestation → A's join-only session hands over N's line, bound to the ticket → J redeems it and holds the management token on N → J vouches K on N with the attestation → N's app confirms K. `accountJoinFleetWorkers` does the vouch itself, inside the same uninterruptible region as `addAndAllowWorkers` (`S/studioFleetHttp.ts:368-391`) so a caller that hangs up cannot skip it, only when the grant came back allowed or expiring (a failed mint still answers 200 with "not allowed"), and before it records the join or answers, with `fleetRequest` and the management token (`S/fleet/fleetTransport.ts:358-403`, as `S/studioFleetHttp.ts:875-886` does for self-allow), and only when N's descriptor carries the capability `deviceJoinVouch` (`checkIdentity`, as `:846-856`). J vouches once per join and never on its own later. A failed vouch never fails the join; the code remains.

**The route on N.** New `POST /api/studio/fleet/vouch`, exact body `{ thumbprint, attestation }`. It sits with the fleet routes, not the device routes, because it reads the grant store. N accepts it only when all of these hold:

- the caller's subject is `fleet-invitation` with a coordinator principal, the session is bound to a proof key, and it holds `access:write`;
- the attestation passes every check of step 5 above;
- N's grant to that coordinator is full access to all projects and all sign-ins right now (the predicate below), read with its vouch generation;
- the key is not one N's owner removed or denied (`isTurnedAway`, `S/fleet/ConnectDeviceTrust.ts:881-890`): after Remove only a typed code brings it back;
- team rules allow machine links and Connect, as for the join (`S/studioFleetHttp.ts:797-798`); the route is rate-limited like redeem (`:618`).

One key per coordinator: a new vouch replaces the earlier one and ends its sessions. When it stands, a waiting request of that key on N is cleared so N's pop-up closes.

**The record.** A new top-level array `vouched` in N's `connect-devices.json`, never `devices`: `{ key, coordinator: <J's environment ID>, session: <management session ID>, workerSession: <ID of the worker-grant session the join made>, ticket, generation, state: "pending" | "standing", vouchId, vouchedAt, label, system, app }`. A field on a `DeviceRecord` would fail open, because an older build would read it as a plain approved device and erase the field; a separate array is dropped and the key waits for a code again.

**The binding** (review 1, finding 3). A standing vouch holds only while all four hold, checked by the gate on every request and every 5 seconds on an open socket (`S/auth/EnvironmentAuth.ts:1529-1536`):

1. the management session named in the record is live (`S/persistence/AuthSessions.ts:356-380`);
2. the worker-grant session named in the record is live; renewal keeps its ID (`S/fleet/workerGrantMint.ts:409-415`);
3. the record's `generation` is the coordinator's current vouch generation, that generation is vouchable, and its `until` has not passed;
4. the key is not removed.

The grant store ends it when the policy is written, not at the next check. The gate is in the auth layer and cannot read the grant store: `WorkGrants` imports `EnvironmentAuth` (`S/fleet/WorkGrants.ts:24`), which holds the device store, so reading the other way would be a cycle. So the grant store pushes. Every policy write for a coordinator (`update`, `revoke`, `restore`, and the redeem that sets `ownerCap`; `S/fleet/WorkGrants.ts:579-690`) bumps a new per-coordinator `vouchGeneration` and, under the same grant lock, calls `deviceTrust.policyChanged(coordinator, { generation, vouchable, until })`. `vouchable` is the predicate (projects and accounts "all", `S/fleet/workGrantPolicy.ts:103-108`, `ownerCap` full access, not stopped) and `until` is the policy's `endsAt`. `policyChanged` deletes that coordinator's vouch and ends its sessions (`endSessions`, `S/auth/connectDevicesHttp.ts:94-121`). This is a new hook: today `update` settles sign-ins only when the period changes (`S/fleet/WorkGrants.ts:629`). The principal generation is not reused, because it moves only on revoke and then tombstones every session of the coordinator (`S/persistence/AuthSessions.ts:317-341`). Narrowing and then restoring moves the generation twice, so nothing a check missed in between survives. A vouch racing a policy write cannot stand either: the route reads the policy with its generation, and the trust store writes the record only if that generation is still current under its lock; a write that comes later finds the record and deletes it.

Sessions and derived credentials carry the generation. A vouched app's sessions carry the binding claim `dev: { k, a }` (`S/auth/SessionStore.ts:570-573`) with `a` set to `<vouchId>.<generation>`, and asset URLs, uploads and socket tickets are tracked under that binding (`trackCredential`, `boundIds`, `S/auth/EnvironmentAuth.ts:1214-1221`, `:1662-1667`; `S/fleet/deviceBoundTransfers.ts:30-52`). `checkBinding` (`S/fleet/ConnectDeviceTrust.ts:826-848`) compares the generation, so a credential made before a policy write is refused even before the next socket check.

**Remove on J while N is out of reach** (review 1, finding 3). Today Remove drops the entry and its token even when N did not answer (`S/studioFleetJoin.ts:628-638`, result "kept"), and N keeps the management session, so the vouch would stand. For a machine with a vouch, J instead moves the token, N's addresses and the worker-grant client name into a new `studio-fleet-pending-revocations.json` beside the fleet file, owner-only like it (new `S/fleet/pendingRevocations.ts`). A loop beside the renewal loop (`S/fleet/FleetWorkerGrants.ts:335-360`) retries `revokeManagementToken` and the worker-session revoke every 5 minutes until N answers 200 or 401, or until the token's 365 days end. Remove answers "kept" with optional `pendingUntil`, and J's Machines list keeps a row: "Removing {label}. {label} still lets this machine's app in until it is reached." The vouch therefore ends when N is reached, and at the latest when the worker grant lapses unrenewed, 30 days after Remove (condition 2). That is a change to what AC-05's "Remove ... end it" can promise while N is offline: Open for the owner, item 11.

**The level, held at issuance, renewal and use** (D-04; review 1, finding 4). N's app sends the level the owner chose with the line it mints (`C/studioFleet.ts:215-226` gains optional `access`; the request goes to N's own server). N keeps it with the line and writes it to the policy as `ownerCap` when the line is redeemed, not when it is minted: a policy made before J holds its management session defaults to linked projects, not all (`S/fleet/WorkGrants.ts:424-438`, `S/fleet/workGrantPolicy.ts:103-108`), and every join would become project-limited. The grant store pushes the cap into the auth layer with the generation, through a new `setPrincipalCeiling` beside `setPrincipalRevoked` in `settlePrincipal` (`S/fleet/WorkGrants.ts:383-395`; a new table beside `auth_principal_revocations`). Four places refuse a level above it:

- the decision, `/oauth/mcp/decision` (`S/auth/McpOAuth.ts:530-550`);
- issuance: the code exchange (`S/auth/McpOAuth.ts:613-623`) reads it again, since the cap can drop between decision and exchange, and `issueMcpClientSession` (`S/auth/EnvironmentAuth.ts:1640-1660`) refuses as well. The static token route refuses coordinators already (`S/auth/http.ts:782-786`), so it is no second path;
- renewal: `renewWorkerGrant` copies the claims, `rtc` included (`S/auth/SessionStore.ts:1136-1240`, `:1210`). It reads the ceiling and answers `grant_invalid` with `reapprovalRequired` when `rtc` is above it;
- use: `authenticateMcpClient` takes the level from the token (`S/auth/EnvironmentAuth.ts:1614-1625`), and `forClient` (`S/fleet/WorkGrants.ts:508-525`), which every `/mcp` request runs (`S/mcp/workGrantAccess.ts:109`), now refuses a level above `ownerCap` instead of copying it into `runtimeCap`.

Lowering the cap revokes every worker-grant session of that coordinator in the same transaction and moves the vouch generation, so a grant above the new cap ends at once and the vouch with it. J's next renewal finds no grant and mints again within the cap, or shows the refusal. Today only a later join or line from N's app with a lower level lowers it; a settings control is Open for the owner, item 12. Without `ownerCap`, "full access" would be J's word.

When any condition stops holding, the gate treats the key as unapproved: the record is deleted, the device waits for a code like any new device, and what it minted stops (below). Nothing revives it: after narrowing and widening again, J would have to vouch again, with a new join.

| Event | Effect on the vouch |
|---|---|
| Owner narrows projects or accounts on N, then restores them | ends at the first write; J's app is asked for a code |
| Owner lowers `ownerCap` on N | ends at once; worker-grant sessions above the cap are revoked |
| Stop on N | ends at once: every session of J's principal is revoked, the management session included; Restore does not revive it |
| Stop workers on J, or the grant lapses | the worker-grant session ends (condition 2), so the vouch ends |
| Remove N on J | ends when N is reached and gives the token up; pending until then, at most 30 days |
| Remove the device on N | ends, sessions ended (`endSessions`, `S/auth/connectDevicesHttp.ts:94-121`), and the key cannot be vouched again |
| The management token reaches 365 days | ends; the code, or a new join |

**What a vouched app is on N.** A device for use, never for approving. The gate allows it, and `bindingFor` and `checkBinding` (`S/fleet/ConnectDeviceTrust.ts:826-848`) honour it with `vouchId` as the approval, so `RequestDevice` (`:500-503`), asset URLs and uploads work (`S/fleet/deviceBoundTransfers.ts:30-52`) and die with the vouch, as `trackCredential`, `boundIds` and `creatorDeviceKey` already arrange for an approved device (`S/auth/EnvironmentAuth.ts:1214-1221`, `:1662-1667`). `deviceApprover` does not honour it: a vouched app cannot approve, deny, remove, confirm or repair on N. Otherwise a management key would approve devices through the app it vouched.

**Settings > Machines.** On N, "Devices that can use this machine" (`W/components/devices/ConnectDeviceViews.tsx:617-657`) lists the vouched app with its ID and "Let in by {machine}'s join, no code. Stays while {machine} has full access to all projects here.", with Remove. `ConnectDevice` (`C/connectDevices.ts:22-43`) gains optional `vouchedBy`. J's card on N gets a line under "can start work here": "Its SpecWithCode app can open this machine without a code." (`W/components/settings/machineDirections.logic.ts:37-110`).

**Saying it only when true.** The answer of `accountJoinFleetWorkers` and the recorded join (`C/studioFleet.ts:92-96`) gain optional `appOpens: "no-code" | "code"`. N's Allow promises "no second code" (AC-03) only when the level chosen is full access, both capabilities are present and J's join session state says the approving app signed an attestation; otherwise it says "{machine}'s app will ask for a code here." The no-code promise needs the confirm of step 6; if the confirm fails, the done card says the code will be asked.

**No pop-up** (review 1, finding 6). N must not show a request from J's app before the vouch has had its chance. The fleet row is one way J's app reaches N; a saved route from an earlier join, a project link (`W/studio/linkedMachines.ts:33-45`, `W/cloud/ConnectRouteReconciler.tsx:165-196`) and a connection already in flight are others, and none of them reads J's fleet list. So the control sits where the pop-up is made, on N's server, and the hold on J only keeps J's own notice and Tailscale pairing quiet.

- On J, `accountJoinFleetWorkers` holds the new machine back. Before it adds N it notes N's environment ID (known from the line, `decodeFleetJoinCode`) in an in-memory, counted set, only when N is not in the fleet file yet. `GET /api/studio/fleet` leaves a held machine out of `machines`, filtering after it has read the grants (`S/studioFleetHttp.ts:495-515`). The hold is released in a finalizer when add, allow and the vouch attempt have ended, whatever the outcome. Leaving N out needs no contract change, an older window is covered too, and it also holds back the Tailscale pairing path and the joined notice, which only announces a listed machine (`W/studio/fleetJoinNotice.ts:14-22`). The vouch call carries its own time limit of 5 seconds, as `S/studioFleet.ts:317-320` does, so the hold is bounded.
- On N, requests are held back while a join runs. While a join ticket is open, the device list (`S/auth/connectDevicesHttp.ts:124-136`) leaves out waiting requests first seen after the ticket opened. They are listed again when the ticket settles: the vouch stands (that key's request is deleted), or 20 seconds after the redeem of the ticket's line with no standing vouch, or when the ticket ends. Every path above ends at N's gate, and an older window on N reads the same list, so this covers them all. A request that existed before the ticket opened stays listed; the vouch deletes it when it stands.
- On N, a standing vouch never makes a waiting request. `ensureWaiting` (`S/fleet/ConnectDeviceTrust.ts:744-812`), which the relay mint also runs (`:933-949`), answers "approved" without writing when the key has a standing vouch, as it does for an approved device. Landing a vouch deletes any waiting request of that key.

So when the vouch succeeds, N never has a request to show. When the vouch attempt fails or times out, N is listed after it, J's window opens it, and N asks for the code: that is AC-05's fallback, and the pop-up is the code prompt.

What still ends at the code: J's or N's server restarts in the middle of a join (hold, ticket and pending vouch are lost; held requests are listed when the ticket would have ended); a vouch that is never confirmed.

**Where it falls back to the code by itself.** The code was typed in a browser tab or a development build and the installed app opens N (different keys); two windows that each made a key at first start (`W/cloud/managedRelayLayer.ts:20-36`, last write wins); the owner closed N's join card before it confirmed the key; the level chosen is below full access; the code was typed in anything that is not J's own app.

#### 4. Threats

| Threat | Answer |
|---|---|
| Stolen Connect sign-in | It still needs a code typed by the owner on the machine it wants. Claiming a join gets it less than today: it can hand over a line for the attacker's own machine and gets nothing on J. The owner then sees "{label} joined" with a name the attacker chose, so the notice says agents here can now run work on it and offers Remove. It cannot be vouched: a vouch names only the key proven in an approve request made by J's owner session. |
| Stolen or replayed join credential | The line is spent once (`S/auth/EnvironmentAuth.ts:1303-1333`); if a thief redeems it first, J's redeem fails and the join fails in view. A thief who redeems it holds a management token as coordinator J (`S/studioFleetHttp.ts:679-686` logs it) and can sign an attestation with its own key for that ticket, but the vouch stays pending: N's app confirms only the key J's answer names after a successful join, and J's own join failed. The token is workers-only, so it cannot pair a browser either. The management token and the join-only token are bound to proof keys, so a copy without the key is refused. Proofs are single use (`S/auth/dpop.ts:94-131`). |
| A window on another machine that is paired to J with Manage access types the join's code | It may approve the join, as it may approve any device today, but its key is never vouched: the attestation is accepted only from a session whose subject is `desktop-bootstrap` or `local-desktop-app`, and neither can be minted for another machine. Per-machine approval (1416 D-01) holds: that window still needs N's own code. |
| A management key minting devices outside the bounds | One route, one key per coordinator, the predicate at vouch time and on every request, refused for a removed or denied key, tied to the vouching session, and the vouched app is not an approver. `deviceApprover` still refuses every coordinator. A coordinator cannot change project or account limits, and with `ownerCap` it cannot raise the level. |
| A device request claiming to be a join | It gets the join-only session: one route, one use, 10 minutes. Without the claim it gets today's full-device request with today's wording. A code approves only the kind it was shown with. The kind is in the signed session, so it cannot change after issue. |
| Two requests spending one join approval | Reserved under the trust store's lock before any side effect: one runs, the other gets 409, then the stored answer. |
| A stale fleet snapshot, a saved route or a project link opens N during a join | N's list holds back requests made while the ticket is open; the vouch deletes them. |
| A Tailscale pairing on a join or reverse tie | The machine being opened mints only a workers code for that tie, which a browser cannot spend. |
| An older client on either side | See the table below. Every case lands on the code as today, with wording that is true for that case. |

| N | J | Result |
|---|---|---|
| new | new | join-only code, vouch, no second code |
| old app | new | full-device request and approval as today; no join approval, so no proven key and no vouch; second code |
| new | old (no `deviceJoinApproval`) | today's flow and wording; second code |
| new, old server on N | new | join-only code; no vouch; second code; over Tailscale J's app opens N with no code, as today |
| any | J's window older than its server | the join request is not listed there and its code is refused there; N's card asks to update the app on J |
