Design: fix first

- **High · Vouch provenance** (`spec.md:128`, `spec.md:139`, `apps/server/src/studioFleetHttp.ts:648`): N verifies the management key, not that the supplied app key entered the code on J. The proposed success test passes for a different key. Require a one-use attestation bound to the approved join, both machine identities, and the exact app key. Keep the local desktop subject check; it is necessary but not sufficient.
- **High · Join approval can be used twice** (`spec.md:113`, `apps/server/src/studioFleetHttp.ts:368`): Two concurrent requests can pass authorization before either spends the approval; a sequential retry test misses this. Atomically reserve the approval for one destination and invitation before side effects, and define how retries recover the same result.
- **High · Vouch revocation can be missed** (`spec.md:159`, `apps/server/src/fleet/WorkGrants.ts:579`, `apps/server/src/studioFleetJoin.ts:586`): Narrowing and restoring projects or sign-ins between checks can leave the vouch live; Remove on J can also succeed locally while N keeps the credential. Invalidate at policy-write time, bind sessions and derived credentials to that generation, and keep remote revocation pending until acknowledged or expired.
- **High · `ownerCap` only gates new decisions** (`spec.md:157`, `apps/server/src/auth/McpOAuth.ts:613`, `apps/server/src/auth/SessionStore.ts:1210`): A previously authorized grant can be issued or renewed at its old level after a narrower choice. Enforce the current cap at issuance, renewal, and use, and invalidate existing over-cap grants.
- **High · Tailscale pairing bypasses the device boundary** (`spec.md:203`, `spec.md:311`, `apps/server/src/studioFleet.ts:523`, `apps/server/src/studioFleetJoin.ts:414`): A capped forward rejoin retaining a tailnet address can pair without a vouch; a reverse grant with a tailnet route can do the same if N is older or loses its mark. Enforce pairing purpose on the credential issuer, preserve worker minting, and gate mixed-version offers on that enforcement.
- **Medium · Fleet snapshot tests miss the pop-up race** (`spec.md:178`, `spec.md:247`, `apps/web/src/cloud/ConnectRouteReconciler.tsx:159`): A linked project or saved route can open a machine independently of the held fleet row; a stale snapshot can also miss `reverseOnly`. Publish reverse restrictions before exposing the entry, and test all three paths with delayed snapshots and in-flight connections.
- **Medium · An older approver window misstates consent** (`spec.md:230`, `apps/web/src/components/devices/ConnectDeviceViews.tsx:325`): It describes a join-only code as granting chats, terminals, files, settings, and sign-ins. Require a join-aware approval surface rather than treating a decodable response as compatible consent.

Verified on app `origin/main` at `fa090f9cf`: today's code approves a full device; the join hands J separate management and worker credentials; N does not persist the chosen cap. The normal local approval does not present the app's relay proof key. `desktop-bootstrap` marks the spawned desktop path, not the installed-service attach path. Scopes alone are insufficient: the WebSocket ticket and device routes do not require one. The proposed source-level deny covers HTTP, WebSocket and media session entry points; `/mcp` requires a different subject, and raw transfers use separate credentials. Rotating the code on a purpose change separates the two kinds if matching and consumption are atomic.

AC-05: does not hold as designed. Vouch provenance, revocation, and code fallback are not guaranteed.
AC-06: does not hold as designed. The initial grant is one way, but reverse Allow does not reliably prevent an automatic open.
AC-10: does not hold as designed. The join-only route boundary is sound in principle, but approval is not atomically single-use; the stated legacy fallback still approves a full device.
