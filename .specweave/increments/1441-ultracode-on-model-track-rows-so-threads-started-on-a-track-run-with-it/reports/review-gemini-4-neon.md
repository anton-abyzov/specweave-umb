## [high] packages/shared/src/modelLanes.ts:576-581 moved track launches do not strip `ultracode: true` when the resolved model does not offer Ultracode (AC-06)
In `resolveLaneRouting`, only the `!moved` branch filters through `withTrackEntryUltracode` (`modelLanes.ts:582`). On the `moved === true` branch (`modelLanes.ts:576-581`), `chosen.options` is copied verbatim into `decision.selection` without checking `trackEntryOffersUltracode`. `chosen` can still carry `{ id: "ultracode", value: true }` for a model that does not advertise `ultracode` when:
- a saved/synced track entry retains `ultracode: true` after the provider catalog stops listing `ultracode` (older Claude CLI or changed model capabilities);
- `fitSavedTrackEntry` (`packages/shared/src/modelTracks.ts:271`) or `followNewestReleases` (`packages/shared/src/modelTiers.ts:432`) updates `model` to a newer family release (`served`/`newer`) while copying `entry.options`; or
- `trackAlternate` (`packages/shared/src/modelTracks.ts:362-363`) copies `entry.options` to another same-driver account whose model catalog does not advertise `ultracode`.

While `OrchestratorMcpService.ts:2380` avoids this by re-applying Ultracode through `withTrackEntryUltracode`, `apps/server/src/project/TracksLaunch.ts:122`, `apps/server/src/mcp/toolkits/project/handlers.ts:819`, and `apps/server/src/mcp/toolkits/project/remoteLaunchModel.ts:152` pass `decision.selection` straight to `routedSelection(...)`, which never removes `ultracode: true`. As a result, a moved launch attaches `ultracode: true` to a model that does not offer it, violating AC-06. (`withoutTrackUltracode` at `packages/shared/src/modelTracks.ts:435` even documents "an entry's option on a model that cannot run it" but is never invoked for capability filtering; `apps/server/src/project/TracksLaunch.test.ts:206-213` only exercised `!moved`, missing `moved: true`.)

Fix: in `resolveLaneRouting` (`modelLanes.ts:576-581`), apply `withoutTrackUltracode` to the moved selection whenever `!trackEntryOffersUltracode(movedSelection, input.providers)`. Add `moved: true` regression tests in `packages/shared/src/modelLanes.test.ts` and `apps/server/src/project/TracksLaunch.test.ts`.

## [high] apps/server/src/mcp/toolkits/project/remoteLaunchModel.ts:150 remote unnamed `studio_thread_launch` drops row Ultracode when `decision.moved !== true` (AC-04)
`remotePickedModel` (`remoteLaunchModel.ts:129-155`) routes unnamed remote `studio_thread_launch` calls via `routeWorkerTask`. When the chosen track row is the same `(instanceId, model)` as `baseline` (for example, a coordinator or worker on Opus 5.5 without Ultracode launching an unnamed worker on another machine where Daily row 1 is Opus 5.5 with Ultracode on), `resolveLaneRouting` returns `moved: false` with `decision.selection` carrying `{ id: "ultracode", value: true }`. Line 150 still returns early with `if (decision?.moved !== true) return baseline;`, dropping `decision.selection` and launching the remote worker without Ultracode. Local launch paths (`TracksLaunch.ts:121-123`, `handlers.ts:815-820`, `OrchestratorMcpService.ts:2346-2353`) were updated to return `decision.selection`, while `remoteLaunchModel.ts:150` was missed. (`translateModel` in `apps/server/src/fleet/remoteWorkerMatching.ts:285-295` already preserves `selection.options`.)

Fix: replace line 150 with `if (decision == null) return baseline; if (!decision.moved) return decision.selection;` and add a unit test in `apps/server/src/mcp/toolkits/project/remoteLaunchModel.test.ts`.

## [high] packages/shared/src/modelLanes.ts:582 unpicked composer draft leaks Daily row 1's `ultracode: true` onto Complex row 1 when both rows share the same model and Complex has Ultracode off
On a Tracks project, a new composer draft is seeded with `projectDraftModelSelection` = `firstDailyTrackEntry` (`packages/shared/src/modelTracks.ts:594-605`), which includes `{ id: "ultracode", value: true }` when Daily row 1 has Ultracode on, while leaving `modelSelectionExplicit` unset. When the user submits a Complex prompt without touching the composer picker or toggles, `apps/web/src/components/ChatView.tsx:13910-13918` sets `sendModelUnnamed = true` and `apps/server/src/ws.ts:1455-1462` passes that seeded `modelSelection` (still carrying Daily's `ultracode: true`) as `baseline` to `routeUnnamedLaunch`. If Complex row 1 is the same `(instanceId, model)` with Ultracode **off**, `resolveLaneRouting` (`modelLanes.ts:554`) computes `moved = false`, and `withTrackEntryUltracode(input.baseline, chosen, input.providers)` (`modelLanes.ts:582`, `modelTracks.ts:424`) returns `input.baseline` unchanged—leaking Daily row 1's `ultracode: true` onto a Complex thread whose row explicitly has Ultracode off. Because any manual trait edit in the composer sets `modelSelectionExplicit: true` (`apps/web/src/composerDraftStore.ts:3336`), an unpicked draft arriving at `routeUnnamedLaunch` never represents an explicit user Ultracode override.

Fix: distinguish an unpicked composer draft seed from an explicit or inherited selection (e.g., strip unpicked Daily seed options in `ws.ts:1455` before calling `routeUnnamedLaunch`, or let `routeUnnamedLaunch` apply the chosen row's options/Ultracode when routing an unpicked draft). Add a test in `apps/server/src/project/TracksLaunch.test.ts` covering Daily row 1 Ultracode on -> Complex row 1 same model Ultracode off.

## [medium] apps/web/src/components/settings/ModelTracksSettings.tsx:305 `TrackUltracodeToggle` hides the switch for saved built-in rows fitted to a newer family release or alternate source
After editing a built-in track, `savedBuiltInTrack` (`packages/shared/src/modelTrackRules.ts:375-380`) stores each row's canonical built-in `model` slug and `instanceId`. When a newer Claude release supersedes that slug (`newestOfFamily`) or settings sync to another machine with a different Claude `instanceId`, `describeTrack` (`modelTrackRules.ts:296-312`) still resolves the running source in `row.sources` and `fitSavedTrackEntry` (`modelTracks.ts:271,284`) still runs the row with its saved `ultracode: true`. Unlike `TrackEffortSelect` (`ModelTracksSettings.tsx:202-212`), which checks both `own` and `props.sources`, `TrackUltracodeToggle` (`ModelTracksSettings.tsx:305`) checks only exact `(selection.instanceId, selection.model)` via `trackEntryOffersUltracode(selection, props.providers)`. Consequently, the switch disappears—preventing users from enabling Ultracode or even seeing/turning off a saved `ultracode: true` that is still applied at launch.

Fix: pass `sources={row.sources}` to `TrackUltracodeToggle` (matching `TrackEffortSelect` at line 665), check `trackEntryOffersUltracode` against the resolved primary source `(source.provider.instanceId, source.slug)` when the exact saved pair is absent, and keep the switch rendered whenever `trackEntryUltracode(selection)` is already true so a saved toggle can always be turned off.

## [medium] packages/shared/src/modelTracks.ts:574-579 & apps/web/src/components/studio/shell/ProjectModelsPopover.tsx:255 `firstDailyTrackEntry` ignores `provider.enabled` and popover ignores `trackEntryOffersUltracode`
1. `firstDailyTrackEntry` (`modelTracks.ts:574-579`) checks only `provider.instanceId === entry.instanceId && provider.models.some((model) => model.slug === entry.model)` without checking `provider.enabled` (unlike `fitSavedTrackEntry` at line 268 and `laneEntryUnavailable`). If Daily row 1 is a saved entry on a disabled provider, `firstDailyTrackEntry` still returns it, so both new drafts and the Models popover display a disabled provider's model (and its Ultracode) even though `resolveLaneRouting` skips disabled providers and launches on row 2.
2. `ProjectModelsPopover.tsx:255` renders `· Ultracode` solely from `trackEntryUltracode(track)` without verifying `trackEntryOffersUltracode(track, props.providers)`, so a saved entry whose model no longer offers Ultracode still claims Ultracode is active in the popover (and seeds it into new drafts via `projectDraftModelSelection`).

Fix: require `provider.enabled` in `firstDailyTrackEntry` (`modelTracks.ts:575-579`), and strip unoffered `ultracode: true` from the returned entry (or gate `ProjectModelsPopover.tsx:255` on `trackEntryOffersUltracode`).
