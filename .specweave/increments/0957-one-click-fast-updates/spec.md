# One-click fast updates

## Problem

Updating SpecWithCode takes two presses and minutes of downtime. On 2026-10-20, updating M4 from 1.0.59 to 1.0.60 ran from the first press at 04:06:56 UTC to done at 04:14:03:
- Press 1 swapped and relaunched the Mac app. The relaunched app requested the service install 19 s later (04:07:30).
- The agent snapshotted at 04:07:39. update.py's preflight then failed with "Guarded prestate changed: rows", because the relaunched app had rewritten its own auth_sessions row (client_app_version 1.0.59 to 1.0.60) between the snapshot and the apply.
- The toast then sat on "Preparing to install", showing "Cancel update" and "Update now", until the user pressed again at 04:08:54.
- That second attempt took 5m09s. About 4m14s of it was service downtime (restart at 04:08:58, new process at 04:13:12), during which a 4.1 GB database backup was written (receipts and backups in ~/.specwithcode/m4/updates/receipts and ~/.specwithcode/backups).

The first attempt failed the same way on 1.0.49, 1.0.50, 1.0.53, 1.0.54 and 1.0.60. Update options are split between Settings and the toast. The toast and the sidebar both offer "Update now", and either one re-runs prepare. agent.log has no timestamps and receipts have no per-phase timings, so nobody can see where install time goes.

## Scope

In: one Update now press that installs the service and then the app, a visible clock and state while it runs, reload-proof follow-up, never downgrading a forced request, one download clock for app and service, the service catching up to the app's release, release-pipeline follow-ups found while shipping 1.0.60 to 1.0.62 (M4 held before forcing, the rollout cancelling only its own request, a stage-wide retry cap, waiting for ShipIt, setting a half-installed app aside), a faster service install, and releasing them (1.0.63 shipped the first version; the fixes ship in 1.0.67). Added 2026-10-28: the release rollout and check cover the desktop apps (on 2026-10-21 the M1 and M3 apps stayed on 1.0.48 and 1.0.65 while every service ran 1.0.68), and last week's unmerged r7 Update now race fixes are carried onto main. Out: the agent refusing an apply after the app relaunches (PR #466, its own thread), a main-process follow-up when every window is closed, and moving update options between Settings and the toast beyond routing both buttons through one flow.

## Acceptance Criteria

- [ ] AC-01: One Update now press installs the service and then the app, which restarts on its new version with no second press and no window reload in between.
- [ ] AC-02: While an update runs, the toast says what is happening with a running clock and offers only Cancel; a second press or a reloaded window follows the update already running instead of starting another, and the step that installs the app survives a reload.
- [ ] AC-03: A forced service request is never replaced by a normal one, and the service checks for a release as soon as the app finds one.
- [ ] AC-04: When the service runs an older release than the app, Update now brings the service to the app's release.
- [ ] AC-05: The release pipeline holds M4 before any forced request, cancels only its own request when it gives up, caps stage-1 retries across the whole stage, waits for the app's own ShipIt, and moves a half-installed app aside instead of keeping it.
- [ ] AC-06: The service install skips full database re-hash passes when nothing was committed since the last one and records per-phase timings in its receipt, with proof output byte-identical to today's on fixtures.
- [ ] AC-08: The app never activates a release ahead of the local service: a downloaded app release is staged for install-on-quit, or installed by a restart, only once the service runs that release or a newer one; until then the app keeps working on its version and the sidebar names both versions and the service's reason (operation-scoped, no blanket lockout). A service on a deleted database log is restarted for a held Update now by SIGTERM and a wait, never `kickstart -k` or SIGKILL.
- [ ] AC-07: SpecWithCode ships the review fixes and the faster install (1.0.67 and 1.0.68 did), and a one-press Update now to the release that carries AC-09 to AC-12 is checked on M4, M1 and M3. (1.0.63 shipped the first version; 1.0.64 to 1.0.66 shipped without these fixes.)
- [ ] AC-09: A studio release updates the desktop apps as well as the services: the fleet rollout updates the M1 and M3 apps after their services, and `release.sh verify studio` fails unless the app on each of M4, M1 and M3 is the released version, signed with the release's designated requirement and accepted by Gatekeeper.
- [ ] AC-10: Update now survives last week's (r7) races: a reload never installs the app for an install nobody asked for, a Cancel shows no failure and withdraws once, a refused stop lets go of its hold, asking again while the agent installs keeps the app's install, no request lapses while the agent installs, and neither a state written in the request's own millisecond nor a refusal from the pass that read the earlier request is taken as its answer.
- [ ] AC-11: A database restart late in a long Update now pass keeps the restarted service held for that request while the agent still works on it, and Update now for a newer release pressed during a pass for an older one installs the newer release instead of refusing it, and ends the older run as replaced instead of leaving it waiting.
- [ ] AC-12: An app update whose ssh session dropped still finishes and leaves no lock behind, a run with no room for the lock or its record stops with exit 5 and says so, a lock whose record is half written holds as a run that is starting, a folder a stopped run left aside is removed, a run stopped with Ctrl-C or kill opens the app it quit again, and only a folder counts as the lock.

- [ ] AC-13: Routine updates avoid serializing unchanged large history payloads while preserving schema, typed-cell, authentication, idle-work and rollback guarantees; corruption and concurrent-write fixtures still refuse unsafe updates.
- [ ] AC-14: A temporary startup transport timeout recovers automatically within a bounded window without being relabeled as an HTTP 500; actual authorization denials remain terminal.
- [ ] AC-15: Verified disposable installer/release artifacts are pruned with explicit ownership and rollback references; active, resumable, dirty, unknown and sole recovery material remains protected.
- [ ] AC-16: Focused regression checks and fresh review pass; delivery and local acceptance are recorded separately, pending PRs and protected worktrees are reconciled without disrupting other sessions.

- [ ] AC-17: A schema-compatible held update preserves history using an immutable stopped clone, authenticated page and changed-row validation, and an explicit versioned receipt, without decoding unchanged history; migration, unsupported-layout and uncertain proofs retain the full legacy validation fallback and rollback safety.

- [ ] AC-18: A service-owned relay launched from PATH or an override cannot stall an update when a versioned runtime ownership receipt and fresh kernel identity prove the exact child; missing, stale, ambiguous or mismatched proof still refuses, arbitrary user processes remain protected, and no startup download or live connector restart is introduced.

## Approach

Renderer first: `serviceUpdateFlow.ts` drives one press as service then app; it asks for a forced, version-bound service install held 15 minutes, follows the agent's progress, and calls the registered app installer once the agent reports the target installed. The desktop exposes the agent's pending request (`pendingInstall`) so any window can adopt it; a sessionStorage flag (45-minute TTL) keeps "then install the app" across reloads. `SidebarRestartToUpdate.logic.ts` holds the pure view: target = newer of the agent's release and the app's, Cancel-only while the forced request is live, the clock, and the copy. The desktop never downgrades a forced request, kicks the agent once after a refresh, and asks it to check when the app finds a release. Install timeout 25 minutes, matching the agent's APPLY_TIMEOUT (1500 s).

Release follow-ups ride in their own PR (#474). The install speedup (T-05) waits for #466, which owns update.py, update_agent.py and quiescence.py today; it records PRAGMA data_version and table watermarks at the first read and skips later full passes when nothing was committed, caches release_verified per apply, and hashes appended tables from one scan. Golden-equality tests guard the proof format.

Rejected: installing the app first (the relaunched app rewrote its auth_sessions row mid-apply and failed the guarded prestate), a second confirmation press, and moving the follow-up into the main process now (needs a new IPC contract; deferred).

Risks: the update to 1.0.63 itself still runs the old two-press flow once, because the renderer doing it is 1.0.62's. #466 should land before 1.0.63 so the relaunch no longer refuses the apply.

The app-update lock is owned by its directory's inode: a run removes only the lock it judged gone, takes one released meanwhile, and goes on only when its record still stands 2 s after writing it (closure reviews, 2026-10-28).
