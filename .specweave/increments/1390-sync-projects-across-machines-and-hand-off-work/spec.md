## The concept

A project lives on several machines as equals. Three verbs cover what happens between them:

| Verb | Moves | Used when |
|---|---|---|
| **Sync** | Files in Git. Each machine fetches from the remote and fast-forwards; what is missing is cloned. Nothing is pushed. Work Git does not carry is offered as extras, ticked by hand, and arrives as branches, not as files in a working folder. | The project is on both machines |
| **Add** | Files, first time. Download from GitHub, plus the same extras. | A machine does not have the project |
| **Hand off** | Work. Threads, unsaved work, the coordinator conversation and its routines continue on another machine. Unsaved project files are put into the working folder there when that is safe. | Closing the laptop, a usage limit, or simply working elsewhere |

One fact replaces the roles: **"Coordinator on {machine}"**. The coordinator is the project's one planning conversation. It is work, so it is handed off like a thread. A person never assigns a role to a machine.

### C. Sync and Add

- [ ] AC-10: "Sync…" opens "Sync {project}: {a} and {b}". It lists the project's root repository and every nested repository the existing manifest scan finds (`handoffGit.ts:762` to 803; a tree past the scan limits is listed as skipped), each with its branch and state on both machines and what Sync will do there. Thread folders and worktree sets are not part of Sync; they are work, and Hand off moves them. Each machine fetches from `origin` for its own repositories, always with a fetch rule Sync writes itself (remote branches into `refs/remotes/origin/`), never the repository's configured one: a configured `+refs/heads/*:refs/heads/*` would move local branches off commits that were never pushed (found in the Phase 2 code review, P2-01). Nothing is fetched from the other machine, and nothing is pushed. The scan is today's, made callable from outside `handoffGit.ts` without its `allowChanges` shortcut. Sync adds its own exclusion, because today's lives in that shortcut (`handoffGit.ts:774` to 784): a linked worktree inside the project folder (its Git directory differs from its common directory) is not listed and is never moved, whether or not its thread is running. The dialog's plan is a proposal: immediately before each fast-forward the server reads that repository's clean and in-use state again, and when either changed it downgrades the action to `fetch` and says why in the result.
- [ ] AC-11: Per repository and per machine, Sync does exactly one of the following and says which:

  | State on a machine | Action | Sync says |
  |---|---|---|
  | Clean, behind its upstream, no commits of its own | `fast-forward` (`git merge --ff-only`) | Moved forward {n} commits |
  | Up to date | `none` | Up to date |
  | Clean, has commits its upstream lacks, not behind | `none` | {n} commits not pushed (listed as an extra) |
  | Has commits of its own and is behind | `fetch` | Has {a} commits of its own and is {b} behind. Not moved |
  | Has uncommitted changes | `fetch` | Not moved forward: {n} uncommitted files |
  | A running thread works in this very checkout | `fetch` | In use by {thread} |
  | On a different branch than the other machine | `fetch` | On {branch}. The other machine's branch comes with the fetch when the remote has it; nothing is checked out |
  | Not on a branch | `fetch` | Not on a branch. Not moved |
  | Branch has no upstream | `none` | No upstream. Its commits are listed as an extra |
  | The fetch failed (offline, no access, remote gone) | `none` | Could not fetch: {Git's reason}. The other repositories continue |
  | Repository missing, has a remote | `clone` | Cloned from {remote} |
  | Repository missing, no remote, or a remote that is a local path | `none` | Not in Git on a remote. Use "Compare all files…" |
  | The repository's own fetch setting writes outside `refs/remotes/` (a mirror) | `none` | Not fetched: this repository mirrors its remote, and a fetch would move its branches |

  A checkout that is level with its upstream reports `none` ("Up to date", or the not-pushed row) even when it has uncommitted files or a running thread: the fetch has already happened and nothing would move. Its step still carries the uncommitted count and the thread's name, and the dialog never shows a bare "Up to date" for it (T-07). An unfinished merge, rebase, cherry-pick, revert or bisect counts as uncommitted changes.

  A thread running in its own worktree does not block the project's main checkout (today's `notInUse`, `handoffGit.ts:713`, blocks on any linked worktree; Sync gets its own check). The plan type has exactly four actions: `none`, `fetch`, `fast-forward`, `clone`. Sync never resets, rebases, merges with a merge commit, stashes, switches a branch, deletes, pushes or commits, and never calls the reconcile paths that stash or reset. A server test on real repositories covers each row and asserts that the working tree, index, stash list and branch list of every repository that was not fast-forwarded are identical before and after.

  - A "commits not pushed" or "branch only on {machine}" line lands as `swc/from-{machine}/{branch}`, with the machine's label made safe for a ref name (`refComponent`, `checkpointGit.ts:58`). If that branch exists there and the new head is a fast-forward of it, it moves forward; if not, the new one is `swc/from-{machine}/{branch}-{id}`. When that branch is checked out on the destination, in the project folder or in any worktree, the extra also lands as `swc/from-{machine}/{branch}-{id}` and the result says "{branch} is checked out on {machine}, so this arrived beside it as {name}" (`applyBundle` force-fetches into its target ref, `bundleGit.ts:131`, which Git refuses for a checked-out branch). The destination's own branches and its checked-out branch are never moved by an extra.
  - An "uncommitted files" line is one snapshot commit, built with a private index so the source's branch, index and working tree are unchanged, with the source's HEAD as its parent, on `swc/from-{machine}/uncommitted-{yyyymmdd-hhmmss}-{id}` ({id} is six characters of the operation id). When HEAD has commits the destination lacks, they travel in the same bundle: the line reads "Includes {n} commits not pushed on {branch}".
  - Every extra arrives as a branch. Sync puts no file into a working folder. The result names each branch and the next step in words: "On {machine} as branch {name}. To use it there, check it out or merge it." Only a hand off applies folder work to the working folder (AC-20).

- [ ] AC-21: A hand off runs in this order. The window drives steps 1 to 3, because the coordinator's move is a protocol only a window can run today. The source's server drives steps 4 to 6 and finishes them without the window. What ties the two together is a hand off session on the source's server, created when Hand off is pressed (step 2). It holds the operation id, the ticked items and their holds, the operation id of the coordinator's move, and how far each step got. The server starts step 4 itself when it records that the coordinator's move was acknowledged (the source writes that record, `MachineHandoff.ts:1008` to 1022), not on a call from the window. Any window on the source or the target reads the session (`handOff.session`) and can continue or release it; recovery reads the server's session, never one window's local storage. There is one open session per project, and a second start for that project is refused with "A hand off of {project} to {target} is not finished". A session records each item on its own, so "Bring back" works per thread (AC-23); the wide scope is one session per project it covers. The plan gains an item kind for project folder work.

  1. **Check.** Nothing moves. The source builds each ticked item's checkpoint on a scratch ref of this operation (`refs/specwithcode/check/{operation}/…`, deleted after measuring, never the thread's standby ref) and measures it (AC-34). No file and no commit is sent to the target: the scratch checkpoints stay on the source. The target is asked two things. First, whether it can take each thread, by a new check call (`peerCheck`): the grant, the project link, the provider and model the thread uses (named in the request) and the lease. Today's `peerPreflight` cannot be used here, because it answers from the target's copy of the thread and fails with "no checkpoint for this thread" when there is none (`handoffPreflight.ts:75`, `HandoffReceiver.ts:414`); it stays the check of the Hold step, after replication. Second, which of the commits the source proposes it already holds (`negotiate`, commit ids only), so that the size shown is the size of the bundle that will travel (AC-34). A scratch checkpoint has no sequence number; the real checkpoint with its sequence is written in the Hold step (`HandoffMode.checkpoint`). The coordinator's checks run now: the target's version and scopes, whether every repository on the target can fast-forward to the source's head (`checkExistingCopy`; the move itself does the fast-forward, so a hand off runs no separate Sync), and the idle check on both machines counting only threads that are not ticked. The button is enabled when the check is done, and each row shows its result. A target that cannot take the coordinator is named on the coordinator row with the fix for its cause: uncommitted files there ("Commit or discard them on {target}"), commits of its own there ("Push or remove them on {target}"), or behind and clean (nothing to do; the move fast-forwards it).
  2. **Hold**, after Hand off is pressed. Each ticked thread is marked handing-off and a running turn is interrupted; when the turn has ended the thread's checkpoint is written to its own hand off ref and replicated to the target. This uses the two halves of today's thread move in a new order: today every refusal comes before the hold (`HandoffMoves.ts:799`), here the hold comes first, so a refusal after it has its own outcome. A held thread runs nothing on the source until it is taken over or released. A thread whose checkpoint, replication or `peerPreflight` fails in this step (bundle too large, missing prerequisites, grant withdrawn) is released and resumes on the source, as the code already does for that failure (`HandoffMoves.ts:835` to 848), and its row moves to Stays with the reason; the hand off goes on with the rest. A turn that has not ended within the 45 second settle window is not checkpointed, because it could commit past the checkpoint: the hold is released and the row moves to Stays with "Its turn did not stop in 45 seconds". A ticked thread that has meanwhile asked a question drops to Stays.
  3. **Coordinator**, when ticked: the existing git-sync move with its conversation and `staleCopy: "refuse"`, run by the window as "Make main" runs it today, with the idle check unchanged (held threads are not running). It pushes each repository's head to origin under a hidden ref (D-03), so when the source has commits that are not on origin the coordinator row carries today's consent line and cannot be ticked without it. The window stops before the push and asks again only when one of these differs from what the check showed: a repository's head on either machine, the target's clean and ancestry result, the set of commits to be pushed, or the target. The hold's own effects (interrupted turns, new checkpoint sequences, the threads' changed state inside the coordinator's context) are expected and never cause a second question.
  4. **Project folder work** (AC-20), before anything starts on the target, so the coordinator there reads the same files. The gate is explicit: from the moment the coordinator arrives until this step has ended, the target holds that coordinator the way it is held on wake (`AwayWakeHold.ts`). A message typed on its page stays in the box under "Finishing the hand off from {source}: project folder work. Send unlocks when it is done.", and no routine is on there yet (step 5 comes after). The hold ends when the step ends, whatever its result, and after 10 minutes without word from the source; folder work that arrives later is checked again (AC-20) and stays a branch when the folder has changed.
  5. **Routines** of the coordinator, by the routine transfer (`ScheduledTaskTransfer`: staged off on the target, off here, on there with the run state), extended to routines the coordinator owns (`ownThread`, which the transfer leaves out today, `ScheduledTaskTransfer.ts:112`) and bound to the coordinator that arrived. The transfer has no operation id today, only the routine's id, so a blind replay would stage the routine off again on a target where it may already have run and then write the source's older run state over it. Each transfer in a hand off therefore carries the session's operation id; before any retry the source asks the target for the routine's state there (absent, staged, on, and its last run), never stages one that is on there, and the newer run state wins. A hand off by hand is permanent: the routine becomes the target's own, with no `grantedBy` pointing at the source, under the target's sign-ins and limits. A hand off on sleep is temporary and keeps today's `grantedBy`. From Phase 3 every coordinator move runs this step, including "Continue the coordinator here" on the old machine later, which is the way back.
  6. **Threads.** The takeover is sent for each held thread, one at a time, and it continues on the target.

  Every way this can stop is a named state with one next step:

  | What happened | State | Next step offered |
  |---|---|---|
  | A thread could not be held, checkpointed or copied in step 2 | It was released and runs on the source again. The rest goes on | Its row under Stays, with the reason |
  | The coordinator was refused in step 3 | Nothing was taken over. Copies of the ticked threads are on {target}, not running, and the threads are held | "Hand off the threads without the coordinator" or "Cancel", which releases the holds; each interrupted thread then shows "Continue here" |
  | The window closed during steps 1 to 3 | The move is finished or released as today's "Make main" does. Held threads stay held for 10 minutes, then the holds are released | The session card: "The hand off to {target} did not finish" with "Continue the hand off" and "Resume them here" |
  | The coordinator moved; folder work could not be put into the working folder | It is a branch on the target | The branch name and "check it out or merge it" |
  | The coordinator moved; a routine was refused or got no answer | That routine is on at most one machine, never on both | "Try the routines again", which first asks {target} what it has (step 5) |
  | The coordinator moved; {target} refused a thread's takeover | The thread stays on the source, held | "Try again", or "Continue it on {source}", which says its result will stay in its own thread and not reach the coordinator |
  | The coordinator moved; a thread's takeover got no answer | In doubt: {target} may have continued it (`pendingTakeover`, `HandoffMoves.ts:864` to 880). It stays paused on the source | "Try again" only. "Continue it on {source}" is offered once {target} has answered that it did not continue it, never before |
  | A thread that is not ticked keeps working or waiting on the source, or a worker the coordinator started on a third machine is still running | The coordinator row is greyed: "Stays while {n} threads keep working or waiting" | Tick them, wait, or hand off without the coordinator |

  Six things this order relies on are not proven by reading the code, and are proven on two machines, on a throwaway project, before the rest of Phase 3 is built (T-08): a held thread counts as idle for the coordinator's move on both machines (the idle check also counts open provider sessions, tool calls and pending effects, `folderCopyPreparation.ts:73` to 130); a held thread survives the coordinator's move and continues on the target; a thread the coordinator started reports to the coordinator on the target after both moved; a routine the coordinator owns runs once on the target and never on the source, also when it falls due between steps 3 and 5 and when the first answer to turning it on is lost; a thread handed off without its coordinator reports to the coordinator on the source; and the driving window can die, once after the hold and once after the move's fence is written but before its acknowledgement, after which a different window finds exactly one coordinator, can continue or release the holds, and needs nothing from the dead window's storage. The second proof also covers a turn that ignores its interrupt past the settle window. If one fails, Phase 3 stops and comes back to Anton with what was found.

## Approach

Four phases, each its own pull request and release, built from the tasks that carry its label (AC-32). No flag: the app has none. A name changes in the phase that makes it true (AC-01), so no release shows an entry that does not yet do what it says.

**Phase 1, the truth about where things are. Web, desktop, iOS and server strings, and web logic. No new call between machines and no server logic.**
- A new `apps/web/src/studio/machineRowState.ts` maps a member's `copyRoles` role (or `independent` from `orchestratorCopies`) plus the window's reach state to one row of AC-03. `OrchestratorSwitcher.tsx` renders rows from it, disables row 1, and replaces the per-machine "Make {machine} main" items with one "Continue the coordinator here".
- `composerMachines` (`routeToMain.ts`) stops substituting the coordinator's machine into the chip. Send loses its machine name. A new `coordinatorBoxState.ts` maps today's inputs (`canRouteToMain`, files, the silence clock of `makeMain.ts`) to the rows of AC-07 to AC-09, and `CoordinatorBlockedNotice.tsx` renders them. `useRouteToMain.ts` keeps its behaviour: send there, then open that page.
- The Fix dialog of AC-05 calls the unlink that project settings already has, moved into a shared hook. "Start a coordinator here" is removed (D-06).
- The role words go from every string (AC-01, Phase 1 row). "Send to another machine…", "Move running threads…" and "Leave this machine…" keep their names and their dialogs.

**Phase 2, Sync and Add.**
- New contract `packages/contracts/src/projectSync.ts`: `status`, `inventory`, `fetch`, `run`, `sendExtras`, with the scopes of AC-33. The plan type is the closed set of AC-11.
- New server module `apps/server/src/fleet/ProjectSync.ts`. It enumerates repositories with the scan of `handoffGit.ts` (exported for it), runs `git fetch origin` and `git merge --ff-only` on its own machine under the project's admission lock, and clones a missing repository through the Add-to-machine clone path. It does not use `git.materialize`, which needs a ref published to origin, and it does not use the reconcile planner, which can stash and reset.
- Extras in `apps/server/src/fleet/ProjectSyncExtras.ts`: one bundle per branch built with `bundleGit.ts`, negotiated and sent over a new peer path beside the thread hand off's (`handoffRoute.ts`, `handoffWire.ts`), received by a new `apps/server/src/handoff/ExtrasReceiver.ts`. The snapshot commit is built as `checkpointGit.ts` builds a checkpoint. The check of AC-14 goes into a new `apps/server/src/handoff/snapshotSecrets.ts` that `checkpointGit.ts` calls, so every checkpoint gets it.
- Web: a new `ProjectSyncDialog.tsx`, the sync fact on rows, and the entries "Sync…" and "Add to another machine…". The Add entry keeps `MachineHandoffDialog.tsx`; the measured copy stays behind "Compare all files…".

**Phase 3, Hand off.**
- It starts with the two-machine proof of AC-21 (T-08) and a review round of this section with its results.
- Worktree-set checkpoints in a new `apps/server/src/handoff/HandoffSetMoves.ts` (one checkpoint per member under one lease, all or nothing), with the wire and state changes that carries.
- `apps/server/src/away/AwayPlanner.ts` plans queued threads, idle threads with unsaved work, project folder work, usage facts (from the limit hand off's fleet probe), a project scope, and sizes measured on scratch refs.
- A new `apps/server/src/away/HandOffStages.ts` holds the stages the server runs: hold, folder work, routines, threads. `AwayRunner.ts` calls them in the order of AC-21 and saves the session after each item, as today. `ScheduledTaskTransfer.ts` learns to move a routine the coordinator owns.
- Web: one `HandOffDialog.tsx` replaces `HandOffMachineDialog.tsx` and `AwayDialog.tsx`. It runs the check, asks the server to hold, runs the coordinator's move with the code "Make main" uses today (moved into a hook, `useCoordinatorMove.ts`), then hands the rest to the server. The Away session, wake card and Bring back keep their engine. The entries and words of Hand off replace Move, Leave and Away.

**Phase 4, automatic.**
- `HandoffThreadModeSetting` (inherit, off, on) stays and is shown as "Hand off automatically". `sleepTarget`, `sleepTrigger` and `graceMinutes` stay and are shown as one row; the 2 minute floor is read into `away.ts` and the sleep notice. The limit rule keeps `providerLimitAction`, `providerLimitMachineTargets` and `providerLimitTargetOrder`; a thread set to Off is excluded in `limitHandoffTrigger`. The cut-off line of AC-26 is composed where the target continues a thread, in a new `apps/server/src/handoff/cutOffNote.ts`.

**File sizes.** Files already over the 1,500 line rule at the pin: `HandoffMoves.ts` (1,563), `MachineHandoff.ts` (1,727), `ProjectLink.ts` (1,523), `ProjectWorkspaceSurface.tsx` (2,633), `CommandPalette.tsx` (4,467) and `Sidebar.tsx` (5,797). A task may change strings in them. A task that needs logic there first moves that part into a new file, so the file ends smaller than it began (T-09 does this for the continue path of `HandoffMoves.ts`). `MachineHandoff.ts` and `ProjectLink.ts` get no logic in this increment. `handoffGit.ts` (1,468) gets only an export; `ProjectMachineHandoff.tsx` (1,344) loses its move code to the new hook.

**Single writer, unchanged.** One active coordinator per logical project at the highest epoch. "Continue here" is today's Make main. A takeover still waits 10 minutes and still claims the epoch on member machines. Plan claims and memory writes keep their current owner. The idle check is not relaxed anywhere. What changes is that a person sees where the coordinator is and continues it, instead of assigning a role.

**Rejected:**
- *Every machine runs its own coordinator, with a lock only on the plan.* Two conversations plan the same goal and split the context. Anton rejected it on November 16 (1372), and nothing he said on November 18 asks for it back.
- *Threads first, then the coordinator* (1389's order). The destination refuses to start a coordinator while the threads that just arrived work there.
- *The coordinator first while its threads keep running, with the idle check told to ignore them* (this spec after round 1). Running threads keep committing, so the move refuses with `source_changed`, and the check that was relaxed is the one that keeps the move still.
- *The server runs the coordinator's move.* It would need a new peer route with its own authentication, consent and replay rules. The window runs it, as today.
- *"Retire" an extra coordinator in place.* `supersede` (`ProjectLink.ts:1177`) needs the predecessor to be the caller and an epoch at or above the binding's, which m1's record cannot meet. Unlink, then link again, reaches the same end over existing calls.
- *Rename every entry in the first release.* For one release "Sync…" would open a folder copy that can overwrite, and "Hand off work…" a dialog that lists only threads set to move.
- *Push before every sync.* A push publishes work. Sync sends unpushed commits directly, and only when ticked.
- *Commit uncommitted work on the person's branch.* A snapshot branch on the target is reversible; a commit on his branch is not his choice.
- *Keep "Leave this machine" as a second entry.* It is the same dialog with a wider scope.
- *Copy a folder with broken Git data as plain files.* It needs its own discovery, route, size cap and secret rules. The folder is listed with its path and stays.
- *Continuous file sync.* It fights running threads for the working tree.

**Risks:**
- The hold step is the first half of a thread move used on its own. Whether a held thread survives the coordinator's move, and whether it then reports to the coordinator on the target, is not proven by reading. T-08 proves it or stops Phase 3.
- A window that closes during steps 1 to 3 leaves threads held. They are released after 10 minutes and nothing restarts on its own; the session card says what happened.
- The content check reads 64 KB per untracked file and 2,000 files per snapshot. A token further into a file, or in a tracked file, travels. The dialog says what was checked.
- The sync fact can be stale. It reads "Not checked yet" instead of guessing, and the dialog always fetches.
- A sent bundle is capped at 64 MB per repository. A larger item stays and points to "Compare all files…".
- Reordering the Away stages changes what an in-doubt session resumes. The saved stage is per item, so a resume reads both orders.
- Mixed versions: a machine without `projectSync` shows "Needs update" and offers the measured copy.
