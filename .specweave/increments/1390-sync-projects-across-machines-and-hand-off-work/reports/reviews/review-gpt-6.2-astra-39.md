## Blocking findings

1. **High · AC-35: two projects collide during startup migration.** `apps/server/src/project/EqualCoordinatorMigration.ts:150-152` derives the command ID from state, epoch and revision, without the project ID. Start with two transferred projects on one machine at the same epoch and settings revision. The first takes the receipt; `apps/server/src/orchestration-v2/EventSink.ts:996-999` returns that receipt without appending the second project’s event. `apps/server/src/project/ProjectService.ts:577-580` rejects it as another project’s command. The second project stays transferred; restarting with unchanged settings repeats the collision. Include project identity in the key and test two projects against the real receipt store.

2. **High · AC-35: an offline takeover can leave two machines running the same routine.** Suppose A went offline with B as standby. B took over, but A never received the superseding binding. Both have an enabled copy of the same due coordinator routine, with no settled runner or disarm record. On upgrade, A’s active binding with standby and B’s active binding with predecessor both produce `routineOwner: true` at `apps/server/src/project/EqualCoordinatorMigration.ts:98-100`. Migration removes the standby and clears the superseded mark at lines 189-195; the new server refuses to give way on reconnect. Both local owners pass `apps/server/src/scheduledTasks/ScheduledTaskRunner.ts:231-236,298-302` before they agree on a runner. Keep ambiguous legacy routines held until ownership is settled; test the same due occurrence on both schedulers, with the old takeover still outstanding.

3. **High · AC-35/48/49: linking a previous-release machine silently fences its coordinator.** `apps/web/src/components/studio/useLinkMachines.ts:43-49` checks `projectLink`, which `v1.0.386` already advertises. With a new kept machine and an old joining machine, `apps/web/src/components/studio/ProjectLinkDialog.tsx:358-379` calls the old accept and proceeds to commit without checking its binding. The actual `v1.0.386:apps/server/src/project/ProjectLink.ts:671-689` writes `transferred` and publishes `gave-way`. Instead of “Needs update” with both coordinators untouched, linking succeeds and the joining coordinator cannot take a local turn. Gate the changed operation before either endpoint mutates state. `apps/server/src/project/equalCoordinatorCompat.fixture.ts:14` pins the wrong release, and `apps/server/src/project/EqualCoordinatorMigration.test.ts:437-455` skips old accept altogether and asserts only the kept machine can type. Exercise the released behavior in both endpoint positions, including rejection without mutation.

4. **High · AC-35/01: a saved folder copy can still move the coordinator after upgrade.** Save a `copy-and-move` after the files were applied but before the coordinator transfer began. At startup the source is still active, so there is no transferring operation ID to retire. Reopening and retrying follows `apps/web/src/components/studio/HandoffFolderCopy.tsx:1007-1013` into `moveCoordinator`. The server writes `transferring` at `apps/server/src/fleet/MachineHandoff.ts:1004-1019`, then `transferred` on acknowledgement at line 888. Until another restart the source has no active local coordinator. Convert or retire the pending coordinator step without losing the copied files; refuse that project-role write server-side without weakening the per-thread fence.

5. **High · AC-35: Settings unlink leaves a third machine listing the departed member indefinitely.** With A, B and C linked, unlink B using A. `apps/web/src/components/studio/useUnlinkMember.ts:112-144` updates B and A only. In particular, `ScheduledTaskRunner.ts:216-221` still requires departed B’s acknowledgement on C for runner coverage. Propagate the explicit removal to remaining members rather than treating omission as deletion. Test C reconnecting after the unlink.
