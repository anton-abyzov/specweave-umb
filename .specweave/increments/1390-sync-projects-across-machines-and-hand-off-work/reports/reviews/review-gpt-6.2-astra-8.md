# Review: 1390 project sync server design, round 4
Verdict: fix the design first

Reviewed baseline: `5cacc4a2cf1943a1d7e54d29b5a57348c4044b2f`, `anton-abyzov/specwithcode#658`. This is a design verdict, not a verdict on a round-4 implementation. The gate is [AC-11, promises 1–6 and exclusions 1–4](/Users/antonabyzov/.specwithcode/m4/scratch/2026-11-18-1390-phase-2/spec-at-main.md). The [design](/Users/antonabyzov/.specwithcode/m4/scratch/2026-11-18-1390-phase-2/design-658-round-4.md), supplied trial scripts and outputs, prior reports and pinned Git source were read. No trial, build or test was run and the app checkout was not modified.

**Keep the prepared ref transaction.** On a stable checkout it solves the wrong-branch write that three rounds of pre-merge checking did not. It does not transact the files, index, upstream configuration or app's running-thread state. The largest remaining error is telling someone that nothing was written, or that someone else changed their files, when neither conclusion follows from Git's answer.

## D4-01 [high] A ref abort cannot undo a tree write, and a successful tree command does not prove every file changed

[Design: lines 85–99, 180–186](/Users/antonabyzov/.specwithcode/m4/scratch/2026-11-18-1390-phase-2/design-658-round-4.md). The order is **prepare refs → update files and publish index → commit refs**, not ref commit followed by a tree update. There is no ordinary crash window *between ref commit and a not-yet-started tree update*. There are these distinct outcomes:

| Interruption or failure | Possible checkout | Truthful result |
|---|---|---|
| Before the tree command starts | Old ref and old file contents. A prior explicit index refresh can already have changed index stat data. | No ref move. A refusal is not proof of byte-identical index storage. |
| During the tree command, including a later file failing to check out | Old ref; some files changed or removed; the new index need not have been published. | Ref not committed; files may have changed. Report what can be read. |
| Tree command succeeds; ref commit fails, times out or is never sent | Old ref with target index/files, possibly with subsequent edits. | Not a clean refusal. Do not retry or reverse the tree automatically. |
| Commit sent; acknowledgement lost, or process dies before readback | Ref may already be new. A dead server returns no result. | No attributed count without evidence. Next inspection reports present state, not who caused it. |

[Git's checkout loop](https://github.com/git/git/blob/v2.50.1/unpack-trees.c#L460-L507) removes paths before checking out the rest; [index publication](https://github.com/git/git/blob/v2.50.1/builtin/read-tree.c#L274-L293) comes later. There is a **new ref with old file contents** case even without another writer: if the target only deletes a file and the directory denies that unlink, [`unlink_entry` warns and returns `void`](https://github.com/git/git/blob/v2.50.1/entry.c#L595-L612). The checkout loop does not add that warning to its error count. The index and ref can advance with the old file still on disk, now untracked or ignored. A tracked-files-only diff, like the one in [the final trial: line 30](/Users/antonabyzov/.specwithcode/m4/scratch/2026-11-19-1390-guarded-ff/f_fix.py), can miss it. Separately, a ref commit can fail writing its reflog or renaming its lock after successful prepare ([files backend: lines 3165–3197](/Users/antonabyzov/.specwithcode/m4/scratch/2026-11-19-1390-guarded-ff/files-backend-v2.50.1.c)).

**Change:** Specify one owner for both subprocesses and a point after which cancellation is deferred. Do not let the independent timer at line 99 kill the ref transaction while the tree writer continues, or contradict the promised commit at line 92. Wait for the writer to finish before releasing a live guard. After any potentially mutating failure, inspect the **named ref**, index and affected worktree paths, including expected deletions; report observed differences or inability to read, not an inferred author. A verified ref move and an incomplete file update are two separate facts. Test a mid-tree failure, failed ref commit, lost acknowledgement and warning-only deletion. No automatic reset, rollback or lock-file deletion.

## D4-02 [high] The written obstruction guard permits deletion of an ignored directory

[Design: lines 37–49, 87–88](/Users/antonabyzov/.specwithcode/m4/scratch/2026-11-18-1390-phase-2/design-658-round-4.md). Suppose the target adds a **file** named `build`, and the checkout has an ignored directory `build/` containing local work. G1 as written accepts it because it is a folder. `read-tree -m -u` [does not preserve ignored entries](https://github.com/git/git/blob/v2.50.1/builtin/read-tree.c#L222-L229); Git [allows an excluded obstruction](https://github.com/git/git/blob/v2.50.1/unpack-trees.c#L2433-L2449) and can [remove the subtree](https://github.com/git/git/blob/v2.50.1/entry.c#L552-L578). The person's local file is gone even if ref readback is perfect.

**Change:** Adopt the stronger [trial rule: lines 16–24](/Users/antonabyzov/.specwithcode/m4/scratch/2026-11-19-1390-guarded-ff/f_fix.py): the added **leaf** must not exist, even as a directory or dangling symlink; existing **ancestors** must be real directories, not symlinks. Use literal, NUL-delimited paths, no trimming, and distinguish absence from a failed filesystem read. Test the ignored-directory-at-leaf case through the service and assert its contents survive. F3 tested a **file at a parent**, not this case.

## D4-03 [high] `read-tree` still obeys settings that can move a second checkout

[Design: lines 78, 88, 167–168, 188](/Users/antonabyzov/.specwithcode/m4/scratch/2026-11-18-1390-phase-2/design-658-round-4.md). Removing `merge` closes the `ours` strategy defect. It does not by itself satisfy “whatever the repository's or the person's Git settings say.” With `submodule.recurse=true`, a clean populated submodule and a changed gitlink, [`read-tree` reads the setting](https://github.com/git/git/blob/v2.50.1/builtin/read-tree.c#L101-L107). The checkout path [calls `submodule_move_head`](https://github.com/git/git/blob/v2.50.1/entry.c#L521-L536), which can [write the nested HEAD with `--no-deref`](https://github.com/git/git/blob/v2.50.1/submodule.c#L2252-L2267). That is a second checkout change with no approved row for it, even with no concurrent writer. An independent example for the ancestry check: [local replacement objects](https://github.com/git/git/blob/v2.50.1/Documentation/git-replace.adoc#L33-L56) or [grafts](https://github.com/git/git/blob/v2.50.1/Documentation/gitrepository-layout.adoc#L209-L216) can describe a parent that the fetched commit does not have.

**Change:** Force nonrecursive worktree updates or refuse affected gitlink changes before writing. Define one unmodified object graph for planning, counting, ancestor checks and materializing the tree; disable replacements and reject or neutralize grafts. Keep the existing no-lazy-fetch environment on local reads. Specify refusal before writing where a configured checkout filter cannot be supported safely. Acceptance cases: changed gitlink with recursion enabled and the child on a branch; divergent commits made to look related locally. Assert the child HEAD/index/files and the original branch tip, not just the parent result.

## D4-04 [high] Record expiry, upstream and occupancy are checked before the final admission to write

[Design: lines 55, 71–88](/Users/antonabyzov/.specwithcode/m4/scratch/2026-11-18-1390-phase-2/design-658-round-4.md). A row found at minute 59:59 can expire, or be evicted by the 32-entry limit, while local checks run. A thread can start using the checkout after step 7; the upstream can change after step 5 while the tree is still clean. The prepared section checks none of those three again. The ref locks prevent none of those events. This is a gap *before* the write, not just a simultaneous editor changing a file. G2 is likewise an observation of worktree registrations, not a Git lock against adding a forced holder elsewhere.

**Change:** Define a single admission point immediately before the tree write. After prepare and the slow probes, revalidate the exact cached row and lifetime, the actual upstream tuple and app occupancy; refuse expired/changed rows with “Sync again”, in-use rows with `fetch/in-use`, and unread state as unread. Define admission as consuming the decision for that one in-flight write; do not abort halfway because a row subsequently expires. An exact write-time guarantee about config or thread starts requires coordination with their writers; otherwise say explicitly that these are final observations, unlike the branch/OID comparison. Test expiry, eviction, upstream change and a thread start **within one checkout's run**, not only before the RPC or between batch items.

Dropping cross-fetch inode/URL identity is reasonable **if “checkout” means the project's canonical path plus the approved tuple**. Define that once. It does not follow that the ref child and later Git commands may rediscover different repositories during this one write. Use the same resolved worktree and Git directory throughout, or decline an unstable binding. This is not a request for endpoint history or an origin probe.

## D4-05 [medium] The server records a target that the window cannot identify

[Design: lines 57–75, 147–155](/Users/antonabyzov/.specwithcode/m4/scratch/2026-11-18-1390-phase-2/design-658-round-4.md). At this head the [fetch facts: lines 100–109, 145–167](/Users/antonabyzov/.specwithcode/m4/worktrees/specweave-umb/1390-phase-2-project-sync-server/repositories/anton-abyzov/specwithcode/packages/contracts/src/projectSync.ts) carry the **local** `head`, the upstream name and counts, not the fetched target OID. Two different upstream tips one commit ahead look identical. Keeping `target` only in the private record does not implement promise 2's “commit the person was shown.” Also, `otherBranch` currently travels as a short branch name; a literal comparison with the proposed full local ref rejects `main` against `refs/heads/main`.

**Change:** Return an optional fetched target OID on eligible rows. Derive the public facts and immutable private row from the same successful fetch output, and count `H...T` by those OIDs. Normalize wire branch names before comparing. Keep the [existing remote/source/destination check: lines 284–303](/Users/antonabyzov/.specwithcode/m4/worktrees/specweave-umb/1390-phase-2-project-sync-server/repositories/anton-abyzov/specwithcode/apps/server/src/fleet/projectSyncOrigin.ts): a porcelain line names a **destination**. If configured remote `release` tracks locally as `origin/stable`, Sync's fixed refspec writes *remote `stable`* there. Do not authorize it as `release`. `otherBranch` and the peer plan may veto, never create permission.

## D4-06 [medium] Failed reads still have paths to a definite reason or count

[Design: lines 74–80, 93, 103–122, 150–154](/Users/antonabyzov/.specwithcode/m4/scratch/2026-11-18-1390-phase-2/design-658-round-4.md). Step 6 handles a failed object read like a missing target or a proved non-descendant. A failed ancestor command is not its ordinary negative answer. “The fetched commit is no longer here” does not follow from a process failing to start. Returning an unread row's saved plan is safe only if that plan is *itself* unread, never `up-to-date` with an unread footnote. Inventory still has required numeric fields; an empty list plus a detail does not define whether its file and stash counts are known. The [existing extras counter: lines 68–75](/Users/antonabyzov/.specwithcode/m4/worktrees/specweave-umb/1390-phase-2-project-sync-server/repositories/anton-abyzov/specwithcode/apps/server/src/fleet/ProjectSyncExtras.ts) returns zero on failure.

**Change:** Carry value / documented absence or negative / unread through every decision, including operation markers, G1/G2 and final readback. For an unread row give the unread sentence priority, authorize nothing and mark affected counts unknown. If old required numbers stay on the wire, specify that consumers neither display nor aggregate placeholders. Check the recorded full branch's OID directly after commit; separate `symbolic-ref HEAD` and `rev-parse HEAD` reads can describe different branches. Attribute `moved: behind` only for confirmed old-OID prepare, confirmed commit and verified recorded branch at `T` with the expected checkout association. Lost acknowledgement or unread ref state: `movedUnverified: true`, no displayed count and no invented branch. A verified ref with unread files can report those two facts separately.

## D4-07 [medium] `fetchId` distinguishes the released old server, not the guarded protocol

[Design: lines 147–160](/Users/antonabyzov/.specwithcode/m4/scratch/2026-11-18-1390-phase-2/design-658-round-4.md). Tag `v1.0.374` has no fetch ID and can act on its own plan. Withholding **all fast-forward entries** from that server works. But the [reviewed baseline already returns a UUID: lines 696–710](/Users/antonabyzov/.specwithcode/m4/worktrees/specweave-umb/1390-phase-2-project-sync-server/repositories/anton-abyzov/specwithcode/apps/server/src/fleet/ProjectSync.ts) and uses the old merge. A new window talking to that intermediate server would enable precisely the path P3-02 rejected. This is a mixed-development-version case, not a claim that round 3 shipped.

**Change:** Require a positive guarded-protocol capability, or an equivalently unambiguous versioned fetch receipt, on that machine's answer. Missing capability means fetch-only and an update message. An old window sends no move request in the released case; an ID-less request to a new server must refuse every fast-forward without replanning. Clones remain a distinct request, not authorized by a move receipt. Keep additions optional and the existing action/reason literals. Cover legacy/no-ID, intermediate/ID-only, and guarded/guarded.

## D4-08 [medium] Inventory loses unpushed work on a branch with no configured upstream

[Design: lines 124–130](/Users/antonabyzov/.specwithcode/m4/scratch/2026-11-18-1390-phase-2/design-658-round-4.md). Local `work` has no configured upstream, origin has a branch named `work`, and local `work` has one unpushed commit. It is not “only here,” has no live upstream and did not lose a previously configured one. None of the three rules lists it. AC-11 says the no-upstream row's commits are listed as an extra; AC-12 requires the unpushed line. The [existing same-name fallback: lines 211–224](/Users/antonabyzov/.specwithcode/m4/worktrees/specweave-umb/1390-phase-2-project-sync-server/repositories/anton-abyzov/specwithcode/apps/server/src/fleet/ProjectSyncExtras.ts) should not be lost.

**Change:** With no configured upstream and a same-named branch in the named fetch, count against that recorded tip. Keep the branch-name test independent of ancestry; a name absent on origin is an extra even with zero unique commits. Label origin membership as of that fetch. Missing, expired, wrong-project/path or unread inventory proof gives unknown membership, not “only here.” A failed reachability count is not zero.

## What the trial establishes

The [pinned files backend: lines 702–788, 2481–2497, 2581–2587, 2629–2658](/Users/antonabyzov/.specwithcode/m4/scratch/2026-11-19-1390-guarded-ff/files-backend-v2.50.1.c) locks HEAD before resolving it, splits an indirect update and compares the old OID on the locked referent. The command itself does not name `main`. **It is the full `symbolic-ref` check after `prepare: ok`, in the same checkout, that makes the pair a branch-and-commit guard.**

| Case | What the supplied evidence actually says |
|---|---|
| Clean; prior switch, commit, detach or dirty file | [B1–B7 and B13](/Users/antonabyzov/.specwithcode/m4/scratch/2026-11-19-1390-guarded-ff/b_txn.out): clean moves; wrong branch and detach abort; a changed OID fails prepare; dirty tracked and ordinary untracked inputs remain intact. “Unchanged” is relative to the state after the competing action, not before it. |
| Concurrent checkout or commit | B8–B12: the competing ref write fails. A checkout or merge can already have rewritten files and index before it hits the ref lock. Sync detects that in the tested ordering. It does not lock arbitrary file/index writers or prove that every concurrent edit will be detected. [E3](/Users/antonabyzov/.specwithcode/m4/scratch/2026-11-19-1390-guarded-ff/e_more.out) supports the tested ref behavior on reftable. |
| Branch also held elsewhere | B7 declines on the primary checkout's wrong branch. **B20 moves** when both worktrees hold `main`, leaving the linked worktree's old files at the new branch tip. A [separate probe: line 5](/Users/antonabyzov/.specwithcode/m4/scratch/2026-11-19-1390-guarded-ff/c_ignored.out) finds two holders. Neither proves G2 aborts in the final helper. Require the integrated refusal, with both checkouts inspected. |
| Kill or failed rollback | B18/B19 signal **the ref child before tree mutation**: TERM cleans locks; KILL leaves two locks on the files backend. Parent death is different: EOF on an explicitly prepared transaction [aborts it](https://github.com/git/git/blob/v2.50.1/builtin/update-ref.c#L747-L760); a separate tree child can survive. | Edits after the tree update | B17 actually **aborts** under the earlier policy. The final script prints prepare/refresh results rather than enforcing all of them and does not run G2. These are component trials, not end-to-end proof. |
| Fetch provenance | [Porcelain output: lines 1–21](/Users/antonabyzov/.specwithcode/m4/scratch/2026-11-19-1390-guarded-ff/d_porcelain.out) distinguishes fetched, unchanged and force-updated heads; deleted `gone` is absent despite its surviving tracking ref. On Git older than 2.41, use the normal safe fetch without porcelain: `ok`/unread only if that fetch succeeded, otherwise `failed`. |

## What to keep in AC-10 through AC-16

The UUID scoped to this server and project, real path, readability, full branch, `H`, upstream tuple, fetched `T`, origin heads, counts, saved step, 60 minutes and newest 32 records are sufficient **data**. Publish immutable rows only after fetch/proof outcomes are known. Restart means unknown ID. Never substitute the newest record, cached tracking ref or a now-readable row. The problem is when and how those data are used, not a need for more history.

No AC here needs a second origin ask, batch network budget, offline permission or push-address binding. AC-10 still needs safe fetch and last clean/in-use checks; removing an authorization-time address check must not remove the ordinary safe clone address. AC-12 needs D4-08. AC-13/14 transfer, secret handling and AC-15 Add/link behavior need no redesign. AC-16 needs results that distinguish a verified ref move, a clean refusal and a checkout needing inspection. Windows, whole-batch latency and origin's current tip are not review gates.

**Spec edit before implementation:** Replace the literal `git merge --ff-only` example with the guarded fast-forward. Split exclusion 4: Git can guard the local ref and expected old tip; it cannot transact editor writes, index/worktree changes, config and worktree registrations together. Promise to report *differences observed*, not every transient edit or its author. Cover live I/O failure and loss of either process, not just a killed app. Scope the unchanged-on-refusal assertion to a refusal before content mutation and define index equality as staged entries if stat refresh is allowed. A dead server cannot send a result. None of those qualifications weakens the central rule: **never advance a different branch, choose a new target, or claim an unverified count.**
