## Answers to the six points

### 1. The sweep deletes folders by name pattern

Mostly contained, with the namespace caveat recorded as P2-23. The sweep is stricter than the filters: a path component must match the full `mkdtemp` shape `/^\.swc-clone-.+-[A-Za-z0-9]{6}$/` (line 170, enforced at line 196), so a real repository named `.swc-clone-tools`, a file named `.swc-clone-notes.txt`, and any folder without the six-character tail are never swept. The test at `ProjectSync.test.ts:1120` pins the file, the dashed-out name and a `../outside` path. Removal is recursive (`NodeFSP.rm` with `recursive: true`, line 205), runs only under the project lock, and stays inside the project: the folder is built from the project's real root and a path that passes `safeRelativePath` (lines 198 to 200), and line 203 requires the folder's real path to be the folder itself, so a staging symlink pointing outside, and a staging folder under a symlinked parent, are both skipped and never followed. As a second line, Node's `rm` on a symlink removes the link, not its target (verified in `/tmp`). A skipped symlink is also never reported as failed; it stays on disk, invisible to Sync. Named gaps: a folder the person named exactly like a staging folder is indistinguishable and would be removed silently (P2-23); a live staging folder of another server process on the same folder is not in this process's set and would be removed mid-clone, which costs that clone its work and nothing else, since clone contents come from `origin`; and an uncaught `lstat` at line 204 fails the whole `run` if the folder vanishes between lines 203 and 204, a retry then succeeds (unconfirmed, race-only).

### 2. The uncommitted filter

It can hide only untracked entries, and only under a `.swc-clone-` name. The filters test only `??` entries (`ProjectSync.ts:324`, `ProjectSyncExtras.ts:188`), so tracked modifications, staged files and renames under any name still count; the rename parse in `uncommittedCount` (lines 300 to 306) is untouched by the filter. The main count uses `-z`, so no quoting is involved and non-ASCII paths read as they are. The extras inventory reads porcelain without `-z` (`ProjectSyncExtras.ts:183` to 189), where Git quotes a non-ASCII path: a quoted staging entry still matches by its staging component and is dropped, while a quoted real file is kept, so quoting can only overcount, never hide. What can be hidden is real untracked work a person keeps in a folder or file whose name starts with `.swc-clone-`, because `inCloneStaging` (line 172) is a bare prefix test, wider than the sweep's full pattern (P2-23). The consequence is bounded: the checkout reads clean and may fast-forward, and the merge is `--ff-only --no-overwrite-ignore` (line 602), so untracked files in the way stop the merge instead of being replaced, and untracked files not in the way are left where they are by a fast-forward. The same prefix keeps those files out of the extras inventory and the left-out list, which is the more visible effect.

### 3. The snapshot

Safe while the staging folder has its `.git`, which is every staging folder that holds files, since `git clone` creates `.git` before writing any. `writeCheckpoint` in `apps/server/src/handoff/checkpointGit.ts` takes its untracked candidates from `ls-files -z --others --exclude-standard` (line 150). Reproduced in `/tmp`: a nested staging repository comes back as one entry ending in `/`, and any candidate ending in `/` is skipped as a submodule (lines 183 to 186), as is any candidate that is a directory on disk (lines 197 to 201). The private-index `add -A` (line 231) only ever receives the explicit file list, so the staging folder can travel neither as files nor as a gitlink; an attempt to add the folder itself also fails while it has no commit checked out. The one precondition is recorded as P2-24: `writeCheckpoint` has no staging filter of its own, and a staging folder whose `.git` is gone has its files listed one by one (reproduced), so those files would join a ticked uncommitted snapshot of the repository above.

### 4. P2-20's second ask

Bounded, prompt-free, and a real but small offline regression (P2-22). `branchOnOrigin` runs through the production runner (`apps/server/src/fleet/folderTransfer/git.ts:29` to 40 and 68 to 76): hooks off by `core.hooksPath=/dev/null`, `GIT_TERMINAL_PROMPT=0`, no lazy fetch. Its time limit is `FETCH_MS`, five minutes (`ProjectSync.ts:45`, 516). During `fetch` the caller's cancel signal reaches it (line 517, from `fetchAll`); during `run` the fast-forward context carries no signal by design (line 1100, "a merge is never cut short"), so a cancelled `run` waits out the ask under the lock, at most five minutes per repository, in series. Yes: a laptop that fetched, then went offline, now gets every fast-forward refused at `run` time, where round 1's code moved to the commit the fetch had already brought in. That is stricter than AC-11: its offline row covers a failed fetch, and AC-10's recheck before a fast-forward names only the local clean and in-use reads. It does not block, because nothing is lost, the step says why, and the normal dialog flow fetches in the same sitting. The smaller fix is in P2-22.

### 5. P2-21's exclusive folder

The target folder is made at move-in, not before the clone, so during a long clone there is still nothing at the target path: a concurrent `status` or hand off scan sees only the made parent folders, which are empty and not repositories, and Sync no longer lists the staging folder beside them. After a failed or cancelled clone nothing is left at the target: the target is never created on that path, `discard` removes the staging folder and `undo` removes the parent folders this call made (lines 666 to 668, 702 to 705, 731 to 735). After a successful clone that then loses the `mkdir`, the other folder stays and the staging folder is discarded (lines 759 to 762). A crash in the two calls between `mkdir` and `rename` leaves Sync's own empty folder at the target; the next clone refuses with "A folder is already there" naming the remedy, which is the pre-staging behaviour and visible to the person.

### 6. `upstreamGone` is additive

Yes, in the same sense round 1 found for `otherUpstream`, with one display difference. It is `Schema.optional(Schema.Boolean)` on `ProjectSyncRepositoryFacts` (`packages/contracts/src/projectSync.ts:117` to 123), read only to fill the pre-existing `detail` of the pre-existing `none`/`no-upstream` step; no new action, reason or field appears. A new window on an old server: the fact is absent, the plan says fast-forward, and the old server moves to the stale commit, which is round 1's P2-20 behaviour on an un-updated machine, not a wire break. An old window on a new server: decoding drops the unknown key, and unlike `otherUpstream` the old planner still plans a fast-forward, because `upstream` arrives set with `behind` greater than 0; the new server then refuses at move time (lines 574 to 585) and answers with the same step shape and the sentence in `detail`, so the plan and the result disagree for one click and nothing moves wrongly. Acceptable in both directions.

## New findings

### P2-22 low, does not block: when `origin` cannot be asked at `run` time, every fast-forward is refused, also to a commit this Sync already fetched

`fastForwardRepository` treats an unanswerable `branchOnOrigin` the same as a no for moving purposes (`ProjectSync.ts:574` to 585), and the recheck facts are read with `fetch: false` (line 563), so no fresh fetch rescues it. A machine that fetched and then lost its network gets `none`/`refused` for every repository, and a run with several repositories can spend up to five minutes per repository asking, under the project lock, not cancellable (lines 1100, 516). Round 1 rated moving to the stale fetched commit low precisely because nothing is lost by it; the proportional rule is to let only a definite no block the move, and to proceed to the already fetched commit when `origin` cannot be asked. As shipped it fails closed with a clear sentence and a retry online succeeds, so it does not block.

### P2-23 low, does not block: Sync claims the `.swc-clone-` namespace by name only, with no proof a folder is its own

There is no marker in a staging folder, no recorded list, and no check that its remote or contents came from a Sync clone. The sweep removes any real folder matching the full pattern (lines 170, 196), so a folder a person named `.swc-clone-{name}-{six letters or digits}` for their own clone would be deleted recursively and silently at the next `run`; a successful sweep produces no step. The read filters are wider still: any path component starting with `.swc-clone-` makes untracked files invisible to the uncommitted count, the extras inventory and the left-out list (line 172). The name is product-shaped and a person would have to adopt it deliberately, and round 1 already accepted that files placed inside a live staging folder go with it. Listed so the claim on the namespace is a decision on record, not an accident; a marker file written at `mkdtemp` time would close it if it ever matters.

### P2-24 low, does not block: the snapshot builder has no staging filter of its own, and a staging folder without `.git` would be snapshotted file by file

`writeCheckpoint` (`apps/server/src/handoff/checkpointGit.ts:149` to 170) builds its candidates without reference to `inCloneStaging`; it is protected only by Git listing a nested repository as one skipped folder entry (point 3). With the staging folder's `.git` removed, `ls-files --others` lists its files individually (reproduced in `/tmp`), they pass the candidate loop, are content-checked like any untracked file, and would travel inside a ticked "uncommitted files" extra of the repository above as part of the snapshot branch. Nothing is lost on the source, and the inventory that offers the extra does hide the folder, so it takes a real untracked file of the person's to make the line tickable. The realistic ways to reach it are narrow: a cleanup interrupted after `.git` went and before the rest did, or a person removing `.git` from a leftover. A one-line candidate filter next to the submodule skip would close it.
