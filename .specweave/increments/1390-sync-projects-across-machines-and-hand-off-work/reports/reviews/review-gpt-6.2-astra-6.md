## P3-01 [high] `apps/server/src/fleet/projectSyncRun.ts:193` The fetch ID authorizes any fetched branch, not the approved row

The record stores every remote head but no approved local branch, old HEAD, upstream, target tuple or indication that the returned row was readable (`apps/server/src/fleet/projectSyncOrigin.ts:43-56`; `apps/server/src/fleet/projectSyncFacts.ts:186-205`). The request carries only the path and the *other* machine's branch (`packages/contracts/src/projectSync.ts:437-444`). Run constructs a new plan from current facts and selects a target by the current upstream (`apps/server/src/fleet/projectSyncRun.ts:158-160,186-196`). Its last comparisons at `:248-256` are against the beginning of **run**, not the facts sent to the window.

For example, `main` was shown one commit behind `origin/main`. Before pressing Sync, its upstream changes to `origin/release`, at a different descendant of the old HEAD. The local and peer branch names are still `main`; the same fetch brought both remote tips. The checks pass and Sync moves `main` to the release tip. No race during `run`, outage or spoofed ID is necessary. A branch switch with `otherBranch: null`, a changed starting commit, or an unread row that becomes readable can likewise be repurposed. Bind authorization to the exact readable checkout row returned by fetch; revalidation may remove a proposed move, not choose a different one. Test changes **between** the two RPCs, including a same-local-branch upstream change.

## P3-02 [high] `apps/server/src/fleet/projectSyncRun.ts:271` The write still targets whichever branch is checked out

The branch and old tip are checked at `:248-250`. Upstream, tracking ref, options and occupancy are read afterward. Occupancy can itself do a database query, filesystem lookups and Git reads for multiple threads (`apps/server/src/fleet/ProjectSync.ts:651-672`). The merge receives only a target OID. The mutex is process-local and held by Sync fetch/move only (`apps/server/src/fleet/checkoutLock.ts:8-24`); clone, extras, other app Git operations and a terminal do not participate. It is not a Git precondition on the branch or old tip.

The real-Git test switches to `other` immediately before invoking Git, then expects `other` at the new tip, `main` at its old tip and `moved: 0` (`apps/server/src/fleet/ProjectSync.approved.test.ts:417-435,456-468`). Here Sync, not the other writer, advanced `other`. Reporting the resulting branch is useful but does not prevent or correctly attribute the mutation. Conversely, if another writer advances `main` and selects it again before readback, an old/new hash pair from a merge on `other` and a final read of `main` can satisfy the success test at `apps/server/src/fleet/projectSyncRun.ts:288-297`. The output contains no branch identity. A non-overlapping dirty change made after the last status can also survive an otherwise successful merge.

Require the expected checkout, full branch and old tip at mutation time, with index/worktree coordination; decline if that cannot be guaranteed. A second read or an app-only mutex does not suffice. The regression should require **both** branches to retain their tips after the switch. The separate test where a terminal fast-forwards first and Sync gets an ordinary no-op is correctly handled (`apps/server/src/fleet/ProjectSync.approved.test.ts:438-453`). A concurrent fetch cannot substitute its tracking ref for the OID argument; a concurrent commit or pull can still change the starting state or recipient branch.

## P3-03 [high] `apps/server/src/fleet/projectSyncRun.ts:74` Git's default two-head strategy can create a merge commit

`mergeOptionsSafe` reads only `branch.<name>.mergeoptions` (`:100-115`). `MERGE_ARGS` sets `--ff-only --commit` but does not select a strategy. With `pull.twohead=ours`, no branch-specific options, a configured commit identity and an ordinary clean, behind branch, Git can create a new two-parent commit instead of moving to the fetched OID. No concurrency is needed. The later observation at `:312-317` does not undo that commit.

This is not an inference from the setting's name. In [Git v2.50.1, builtin/merge.c](https://github.com/git/git/blob/v2.50.1/builtin/merge.c#L1536-L1549), a one-target `merge` selects `pull_twohead` if no strategy was specified; a strategy marked `NO_FAST_FORWARD` then changes `fast_forward` to `FF_NO`, **after** option parsing. [`ours` and `subtree` have that flag](https://github.com/git/git/blob/v2.50.1/builtin/merge.c#L99-L105); [a successful strategy with commit enabled finishes an automerge](https://github.com/git/git/blob/v2.50.1/builtin/merge.c#L1766-L1775). The installed Git reports 2.50.1; this is source verification, not a local execution. Neutralize or decline the effective default strategy and test that HEAD equals the target, no merge commit exists, and the index and tree match. The existing tests configure the branch key only.

## P3-04 [high] `apps/server/src/fleet/projectSyncOrigin.ts:348` A fetch deletes refs it did not create

Before fetching, Sync enumerates **all** `refs/specwithcode/sync/` refs, not this invocation's UUID, and deletes each listed ref at its observed OID (`:308-326`). A pre-existing user ref beneath the prefix is deleted even if origin is then unreachable. A live invocation in a different process or another worktree sharing the common ref database can lose its refs between fetch and enumeration. An empty successful enumeration is accepted as an empty remote, potentially reporting that a live upstream is gone (`:359-374`; `apps/server/src/fleet/projectSyncFacts.ts:256-261`). There is no ownership record or common-ref-store lock. Checking the old OID protects against some replacements, not against deleting a ref that was never Sync's.

The final cleanup also ignores nonzero exit status and exceptions (`apps/server/src/fleet/projectSyncOrigin.ts:321-326,375-376`), so success does not establish that temporary refs are gone. Delete only demonstrably owned refs for this operation at the OIDs actually written; separate recovery of abandoned operations from routine fetch and surface cleanup failures. The test at `apps/server/src/fleet/ProjectSync.approved.test.ts:149-172` starts with an empty namespace and does not inject a cleanup failure.

## P3-05 [high] `apps/server/src/fleet/ProjectSync.ts:722` A stale record can escape expiry, eviction or revocation before a later move

The service resolves `keptFetch` once, before cleanup and the serial repository loop, then keeps passing the object at `:751-759`. A long or queued run can start a later move after the hour, or after 32 newer fetches on other projects evict its ID. No lookup is made at that move. Eviction removes the object from `kept`, not from the running context. Later revocations visit only `kept` (`apps/server/src/fleet/projectSyncOrigin.ts:82-106,134-150`).

There is a second concrete gap at publication. Project A finishes fetching a shared checkout but is still fetching a slow sibling. Project B fetches that checkout after the upstream was deleted. A's record is not in `kept` yet, so B cannot invalidate it (`apps/server/src/fleet/projectSyncFacts.ts:195-199`; `apps/server/src/fleet/ProjectSync.ts:703-710`). A subsequently publishes. Fetch never prunes, so the old tracking tip still matches. If origin is now offline, A can move to a branch this server already learned was deleted. Separate project locks allow this order; the two Git fetches need not overlap. Keep ordered, checkout-generation-specific revocation facts independently of the cache, and check the named record's membership, freshness and revocation immediately before each move. Current tests expire a lookup or revoke two **already published** records (`apps/server/src/fleet/ProjectSync.origin.test.ts:328-344,359-381`).

## P3-06 [high] `apps/server/src/fleet/projectSyncFacts.ts:174` The recorded address and checkout identity can come from different fetches or folders

The server reads the effective URL before fetching, invokes Git against the mutable name `origin`, and obtains the filesystem identity only **after** the fetch and its ref readback (`:173-182`; `apps/server/src/fleet/projectSyncOrigin.ts:345-359,386-395`). If the config briefly changes between the URL read and the fetch, a fetch from B can be recorded as a fetch from A. Restore A and take it offline: the last address check matches A and offline permission is accepted for B's object. Conversely, replacing the folder after ref readback but before the identity read associates the old fetch with the replacement's identity. A replacement with the same address, tracking tip and compatible HEAD passes.

An ordinary re-clone **after** publication on a filesystem with a reliable generation is rejected. Without birth time the server deliberately accepts a matching device/inode **online** (`apps/server/src/fleet/projectSyncOrigin.ts:252-258`; `apps/server/src/fleet/projectSyncRun.ts:225-228`; `apps/server/src/fleet/ProjectSync.origin.test.ts:297-325`). Inode reuse is plausible, not reproduced. A live origin can confirm a tip, not that Sync fetched this checkout. Tie the fetch to its actual endpoint and checkout generation; do not authorize a replacement because its origin advertises the same SHA. Checking `pushurl` is not the fix: the fetch URL is the relevant one.

## P3-07 [medium] `apps/server/src/fleet/projectSyncOrigin.ts:195` An ask that never started can authorize an offline move

Budget exhaustion itself is handled correctly: `:191-192` returns `not-tried` without running Git. But **all** subprocess rejections and all nonzero exits become `unreachable` at `:199-202`; even malformed successful output takes that path at `:205-210`. A transient failure starting the local `ls-remote` process makes no request to origin. If subsequent local Git calls work, Sync uses offline permission and reports “origin could not be reached” (`apps/server/src/fleet/projectSyncRun.ts:225-228,294-298`). This matters if a real ask would have disclosed a deletion. Distinguish a local execution/parse failure from an attempted network failure; for the former, report the failed check and do not move. The timing tests inject rejections rather than demonstrating a remote was contacted.

## P3-08 [medium] `apps/server/src/fleet/projectSyncOrigin.ts:363` A successful fetch can still be reported as failed

Once `git fetch` returns zero at `:358`, the tracking refs are already updated. If the **local** private-ref listing fails, the function returns `ok: false`; a thrown listing error instead reaches the outer `fetchAll` catcher. Both produce `fetch: "failed"` (`apps/server/src/fleet/projectSyncFacts.ts:184-186`; `apps/server/src/fleet/ProjectSync.ts:421-438`). The reverse misclassification exists before the fetch: a rejected config read is reported as a failed fetch even though Git was never asked to fetch (`apps/server/src/fleet/ProjectSync.origin.test.ts:749-769`). Also, a null URL or stat after a successful fetch leaves no record, but can still produce move-ready facts from the tracking ref (`apps/server/src/fleet/projectSyncFacts.ts:184-204,251-279`).

Record command completion independently of proof collection and checkout reads. After a successful fetch without usable proof, report fetched/unread and withhold the move. Before a fetch starts, report not run. The new red test interrupts `symbolic-ref`, **after** private-ref enumeration, so it misses this boundary.

## P3-09 [high] `apps/server/src/fleet/ProjectSync.ts:409` An unread nested checkout can be returned as clean, inventoried, or used for extras

`syncRepositories` now sets `unread: true` when the worktree probe fails (`:157-164`); fetch and move honor it. `statusOf` ignores it and calls `readRepositoryStatus`, which returns `clean: uncommitted === 0` (`apps/server/src/fleet/projectSyncFacts.ts:103-112`). The new service fixture has exactly the necessary state: only the common-dir probe fails and the nested working tree is clean. The status assertion checks **only path names** (`apps/server/src/fleet/ProjectSync.approved.test.ts:599-615`). A subsequent rejected branch read can instead reject the whole status batch. Inventory and `sendExtras` also accept the unread entry without checking the flag (`apps/server/src/fleet/ProjectSyncExtras.ts:581-589,598-606,624-628`), even though Sync did not establish that this is not a thread worktree.

Propagate the skip to all consumers. Return a conservative status with no positive clean claim and an optional unread indicator; do not touch an unread path for extras. Assert the status and the absence of per-path work, not just that the path is present. The earlier discovery fallback for an entire limited scan is distinct and sets `scanLimited` (`apps/server/src/fleet/ProjectSync.ts:603-629`).

## P3-10 [medium] `apps/server/src/fleet/projectSyncGit.ts:103` Read errors can become definite branch or movement claims

`branchAndHead` conflates the normal detached exit of `symbolic-ref` with **every** nonzero exit. If that one read fails but the commit read succeeds after a genuine move, readback does not retry and emits “on no branch” with `moved: 0` (`apps/server/src/fleet/projectSyncRun.ts:283-292,312-317`; `packages/contracts/src/projectSync.ts:273-278`). It can do so on an attached branch. The two concurrent reads can also describe different instants. During planning, a nonzero upstream/ref/count read is collapsed into `no-upstream`, and a failed address read can become `no-remote` (`apps/server/src/fleet/projectSyncFacts.ts:121-125,248-279`; `apps/server/src/fleet/projectSyncOrigin.ts:293-305`). Those are not equivalent to “could not read.”

**Unknown final state does send zero.** `apps/server/src/fleet/ProjectSync.origin.test.ts:663-676` expects `moved: 0` and separately verifies that the real checkout **did move**. Its unknown-outcome sentence is honest; the numeric field documented as “Commits a fast-forward moved the checkout by” is not a verified count (`packages/contracts/src/projectSync.ts:451-456`). Preserve the wire shape, but add an optional structured verification/known-count field, document zero as a compatibility placeholder for unverified outcomes, and distinguish absent/detached from unread in the Git helpers. Do not retain the pre-merge branch as an observed final branch on an unknown result. A new UI is not required for the server to make the distinction.

## P3-11 [medium] `apps/server/src/fleet/ProjectSyncExtras.ts:199` “Only here” can describe a branch that exists on origin

`onOrigin` identifies the configured **upstream source** when one exists (`:187-198`). Suppose local `work` tracks `origin/release`, and origin contains both `work` and `release`. After `release` alone is deleted, `listed.has(onOrigin)` is false and `work` goes into `onlyHere`, although `refs/heads/work` is in the same fetched map. Conversely, the local-only name of a branch level with a differently named live upstream is omitted. Test branch-name membership separately from commit reachability and tracking configuration.

Inventory also regresses checkout binding: `latestHeads` selects solely by project, path and record creation time. No expiry, Git-directory generation, effective URL or revocations are checked (`apps/server/src/fleet/projectSyncOrigin.ts:113-125`; `apps/server/src/fleet/ProjectSyncExtras.ts:584-588`). After replacing the checkout or changing origin, inventory can apply the previous repository's branch list to the new one. Reuse only the applicable inventory and represent an unavailable membership or count as unknown, not as evidence of absence. Neither issue gives inventory permission to merge.

## Contract, limits and evidence

- **ID scope.** UUIDv4 is generated on this server (`apps/server/src/fleet/projectSyncOrigin.ts:67-74`); lookup checks project, repository lookup checks real path, and the RPCs require source-control write scope (`packages/contracts/src/clientRpcPermissions.ts:77-78`). A random guess is not a meaningful way around that guard. IDs do not work on a different server or after restart. A batch ID intentionally covers all its successfully recorded paths, not just one; it is not proof of a user's selection or of the local branch they saw. An ordinary moved checkout misses the path key. An ordinary re-clone misses the identity, with the qualifications in P3-06. The simple 32-entry/60-minute lookup does not substitute another record. Eviction by another project can force a harmless retry; continued use of an already retained object is P3-05.
- **Wire.** Against the full base, no new `action`, `reason`, `stays` or `landed` literal (`packages/contracts/src/projectSync.ts:32-73,542-560`). `fetchId` is optional both ways (`:171-184,429-444`); `unreadDetail`, `upstreamUnusual` and `stateUnread` are optional (`:131-152`). On ordinary struct decoding, old peers ignore extra fields and new peers accept their absence. This is a schema inspection, not a mixed-version RPC run. Decodability is not safety: a new caller must not send a move to an **old server** that never supplied an ID on the assumption it enforces this protocol. A clone on this server needs no ID.
- **Level plus unread.** `packages/contracts/src/projectSync.ts:377-389` cannot plan a move on `stateUnread`. At level it emits `none/up-to-date` or `none/not-pushed` **with unread detail**; a reason-only count is not evidence of “in sync.” `apps/server/src/fleet/ProjectSync.results.test.ts:364-397` covers this, including a scratch repo and a failed status read. The plan step has no structured `stateUnread` field (`packages/contracts/src/projectSync.ts:197-210`); the facts do. This head has no final dialog aggregate proving what it counts. Gate that consumer in its own PR. The positive clean status for an unread discovery path is already a server defect, P3-09.
- **Time.** Fetch uses four workers and nominal five-minute network commands, not a five-minute batch (`apps/server/src/fleet/ProjectSync.ts:85-86,384-402`; `apps/server/src/fleet/projectSyncOrigin.ts:349-353`). Thirty silent repositories can cost eight waves, about 40 minutes **before local work**; the schema permits 128. Run charges elapsed time per ask. A positive remainder still grants a full 10 seconds, so the 60-second allowance can approach 70 seconds under ordinary timeout behavior. The final budget-exhausted path never claims offline. There is no hard end-to-end deadline for filesystem reads, lock queues, occupancy reads, serial merges or clones. The merge timeout is five minutes per checkout and clone timeout is 30 minutes per target. Local reads and lock waits cannot be bounded by quoting the network budget. Accept a tighter latency bound as follow-up, not the admission/revocation gap in P3-05.
- **Scope of other unproven items.** Keeping offline knowledge separate across different physical checkouts of the same origin is acceptable for this approval contract; do not confuse that with losing known facts about the *same* checkout. A push-only URL control, Windows execution and a real two-machine exercise remain useful follow-ups, not reasons by themselves to block this head. A terminal not sharing an app lock is normal; using that lock to promise no wrong-branch write is not. Lack of birth time was only injected, not exercised on such a filesystem. Cleanup is a real additional write, not a harmless untested assumption.
