# Review: specwithcode#718 folder copy over the local network (runtime attack read)
Verdict: ship
Reviewed commit: 645f98573a708178c15420924a2f1b73e7e9859b (base cb2963143; diffs read: cb2963143..0381d80c1 and 0381d80c1..645f98573)
Reviewer: claude-sonnet-5-5 (author claude-opus-5-5). Read-only, Git objects only, no test run. 0 high, 2 medium, 1 low, 1 nit. The gate is closed on every OS (`implementationReview`, `relayRecords`, `osEvidence` are false), so none of this runs in a release.

## [medium] apps/server/src/fleet/folderTransfer/lanSource.ts:178 a Connect pull spawns an interface probe every time
`pulled()` returns early only for live, declined or running copies. `run()` returns false without adding the copy to `declined` when there is no eligible interface (:234-237), the live cap is full (:238-245) or the hourly budget is spent (:247-248). `SourceTransfers.authorize` calls `pulled()` on every manifest and chunk request (sourceService.ts:755). Each call reaches `policy.eligible()`, which runs `networksetup` (macOS) or `powershell.exe -Command Get-NetAdapter` (Windows) with a 3 s timeout (lanInterfaces.ts:41-49, 144).
Scenario: setting on, Wi-Fi only behind a VPN, so no eligible interface. A 122k-file copy over Connect makes thousands of chunk requests and spawns one child process for each. A paired destination can force the same by hammering `chunks`.
Fix: record a cooldown (or add to `declined`) for every non-retryable reason in `run()`, not only for a destination "no".

## [medium] apps/server/src/fleet/folderTransfer/lanListener.ts:64-66, 104-113 failure and block tables never shrink
`failures` and `blockedUntil` are keyed by remote address. `blocked()` deletes an entry only when the same address comes back. `failed()` only trims its own address. `LanSourceBudgets` lives as long as the `LanSource` (lanSource.ts:140), which is the process.
Scenario: a hostile Linux host on the LAN adds many IP aliases inside the interface prefix and does one bad handshake from each. Every address leaves a permanent entry (10.0.0.0/8 allows millions). Memory grows until the app restarts. It is slow and needs a live listener, so medium, not high.
Fix: drop `failures` entries older than 60 s and expired `blockedUntil` entries on each `failed()` or from the 250 ms tick, and cap both maps.

## [low] apps/server/src/fleet/folderTransfer/lanSource.ts:341 listener is registered after an await, so an end signal in the gap is lost
`LanGenerationListener.open` binds first. `this.live.set(...)` runs only after `await identityOf(state.folder)`. In that gap `ended()`, `endAll()` (`network_changed`, `woke`, `setting_off`, `shutdown` via `close()`) and `deny()` find nothing in `live`. The listener stays bound, and a stale entry counts against the 4-generation cap, until the 15 minute idle end (lanListener.ts:549-550). Per-request `denial()` (lanListener.ts:450) and the re-check at lanSource.ts:363 still refuse service after a denial, so no data is exposed. The listener can outlive a network change or shutdown by up to 15 minutes.
Fix: `live.set` right after `open`, fill `rootIdentity` afterwards, and re-check `closed` and `enabled` before sending the offer.

## [nit] apps/server/src/fleet/folderTransfer/destinationService.ts:1686 `withoutLan` also drops `updatedAt`
The author's claim is "compare without `lan`". It also removes `updatedAt`. `lanSave` never touches `updatedAt`, so removing `lan` alone is enough. No exploit; approve can no longer notice a touch-only update.

## Control-channel authorization (paired machine without a grant)
`studio_folder_copy_receive` (mcp/toolkits/project/handlers.ts:1208-1231) refuses with no work grant, an agent-origin call, a revoked grant, or `projects.kind !== "all"`, before any action runs, `lanCheck` and `lanOffer` included. Past that, `LanDestination.check` and `offer` require the operation's recorded source to equal the caller (lanDestination.ts:201, 267). Unknown operation, wrong source and setting off all give the same `lan: null` / `false`, so there is no oracle. No state is written before those checks.

## The destination approve race (author's claim: confirmed)
`approve` reads `saved = (await this.require(operationId)).lan` inside `this.locked(...)` (destinationService.ts:689-692). `lanSave` (:291) and every `update` use the same per-operation promise chain (`locked`, :325), so a concurrent `lanCheck`, `lanOffer`, `latch`, `count` or `end` runs either wholly before the approve's critical section (and is read as `saved`) or wholly after (and is applied on top of the approved record). The stale `record.lan` captured at the start is overwritten by `saved`. No other site writes a whole record from a stale read: lines 483 and 503 read `existing` inside the lock, 1531 reads `current` inside it. What a hostile source can do through `lanCheck` is raise its own generation (monotonic, up to 2^31) and reset `accepted`. A latch that lands between `check`'s read and its save is kept (`...current`), and `offer` re-reads and also finds the generation entry deleted by `latch`, so a latched copy cannot get a connector.

## Tool results and outbound proxy spans
No code path traced puts the LAN token, addresses or hashes in a log, span, error or record.
- Outbound: `LanSource.peer.check/offer` calls `SecretsPeer.lan` (sealedSecretsPeer.ts:93-123), which calls `remote.proxy` and maps every failure to the literal `"refused"`. The `RemoteMcpError.cause` (SDK error text, which can quote a rejected value) is dropped there. On success only `lan` and `lanAccepted` are decoded.
- `RemoteStudioMcpClient.call` (:422) hands `input.arguments` to the MCP SDK `callTool` and nothing else. There is no log, span annotation or argument capture in that file. `Effect.fn("fleet.agentCopy.receive")` records no arguments. The tool wrapper logs only tool name, error tag and failure count (mcp/McpHttpServer.ts:888). No telemetry exporter or fetch instrumentation exists in apps/server.
- The control call is made by the server, not by an agent thread, so no thread tool-result record is written. The browser gets only `transport` byte counts.
- Not traced: the Connect relay itself. The `lanOffer` body carries `lanToken` and addresses through it. This is the S-10 requirement the `relayRecords` gate flag stands for, and it stays unproven until a test relay shows it.
- Residual: on the destination, an MCP parameter decode failure for a malformed `lanOffer` returns text that can quote the value to the caller. The caller is the source, which already holds the block.

## Checked and sound
- Listener, no cert / wrong cert / old-generation cert / copied cert without key: TLS 1.3 only, ALPN pinned, `requestCert`, then SHA-256 of the DER bytes in `timingSafeEqual` (lanListener.ts:337-351). No HTTP parser sees the socket before that, and a failure writes no response.
- Restarts: source restart drops listener and token (nothing rebinds); the destination gets refused or reset and latches once. Destination restart loses the key; `connector()` latches (lanDestination.ts:345-352), and `offer` after a restart fails because `mine` is missing.
- Resumption and 0-RTT: `SSL_OP_NO_TICKET`, `isSessionReused()` refused on both ends, no `session` option on the client, no early data enabled. Version fixed at 1.3 on both sides.
- Slow or huge input: 8 KiB headers with its own 2 s timer (Node's header check never runs because the http server never listens), 5 s handshake timeout, 128 KiB streamed body cap with a 10 s timer, chunked bodies counted, `?` in the URL refused, three allow-listed routes, operation id compared, all before any body read. 2 handshakes per address, 16 total, 10 failures/min then a 60 s block, 4 authenticated sockets, 4 chunk reads per operation and 8 total.
- Chunk requests: hashes only (no index, no path). Each must match `SHA256`, be unique, and at most `MAX_BATCH_CHUNKS_LARGE`. The source looks them up in this operation's own index; any other hash gets the "unknown" frame with no bytes (sourceService.ts:1157-1191). `usable` indexes from the destination (negative, huge, repeated) fall out through `interfaces[index]` and a `Set`.
- Fallback: the LAN token exists only in `LanRoute` inside the connector. `LanFirstSourceClient` never sees it and Connect uses the record's transfer token and address, which a LAN answer never changes. A latch is saved before the first Connect request (`fell`). A denial is an authenticated 401/403 from a pinned peer and stops the copy; everything else latches once and never returns to LAN. Connect authorizes by itself, so a switch cannot revive a revoked copy.
- Connector: pin compared in constant time before any HTTP byte; `hello` binds environment, operation, generation and binding hash; redirects and any non-200/202 are errors; no proxy (custom agent over a pre-made socket); one pool of at most 4 sockets per generation, destroyed on latch, rotation and terminal state; wire and expanded limits streamed; `decodeFrames` caps inflation (`maxOutputLength`); every frame is hash-checked against the request.
- Secrets in text: `LanFailure` messages are the class only; `lanSource` catches swallow causes; no logging calls in any lan*.ts file; keys, token and addresses are in memory only; the destination record keeps generation, latch and byte counts.
- Addresses: `admitLanHost` accepts canonical RFC 1918 or fc00::/7 literals only. `routeOf` (including the PowerShell string) runs only on an admitted literal. Directly-attached check needs on-link prefix plus the route out of the same interface; the source also checks the remote is inside the listening prefix at accept.
- Gate: `folderCopyLanGateOpen` is evaluated at runtime in `lanSettingInEffect`, the only writer of `link.enabled` (MachineHandoff.ts:486). A stored `true` in settings is ignored while the gate is closed. No environment variable and no peer message reads or sets it; no production code imports the testkit or fixtures; `lanLink` is local to `MachineHandoff`. `lanCheck` and `lanOffer` return nothing when disabled. (`FOLDER_COPY_LAN_GATE` is `as const` but not `Object.freeze`d. Nothing mutates it; freezing it would be a cheap hardening.)
- Cleanup: `end()` closes the listeners, destroys authenticated and raw sockets, clears the watchdog and header timers, drops the token hash and calls `closeAllConnections`. Stall timers clear on response close. `readBody` timers clear on every path. The destination `destroy()` wakes waiters and destroys sockets and agents. A half-finished copy keeps its hash-verified staged chunks and continues on Connect; an unverified manifest is thrown away, and `recheck` re-reads it after a wrong pin or identity.
