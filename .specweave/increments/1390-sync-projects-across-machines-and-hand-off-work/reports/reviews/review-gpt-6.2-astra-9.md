# Review: 1390 equal coordinators and hand off proposal, round 2
Verdict: fix first

Keep the equal coordinators, the two starts, local fallback first and the common progress view. Do not accept the release sequence yet. The first release is feasible without changing the receiver, but as specified it can tell the launcher that an idle worker finished. Later releases can mistake an older peer for one that enforces a reviewer lock, or start a second copy of work after a partition.

## EC2-01 [high] T-19 can lose the real completion or send a false one

The old peer is readable. Its read and wait handlers check the project grant, not who created the continuation (`apps/server/src/mcp/toolkits/orchestrator/handlers.ts:47-60,236-246,306-319`; `apps/server/src/mcp/workGrantAccess.ts:226-236`). The sender knows the ID before sending (`apps/server/src/handoff/HandoffReceiver.ts:192-202`; `apps/server/src/handoff/HandoffMoves.ts:823-825,855-864`). Neither a new receiver nor wider access is needed for proof 5.

The gap is the interval between registering the follow and observing a **real run** (`spec.md:35,880-882`; `reports/equal-coordinators-handoff.md:59-65`). A follower polled before creation stops on `thread_not_found`. A continuation installed idle returns `runId: null`, `status: "idle"`; the follower treats it as terminal, sends a completion keyed by `no-run`, and leaves the row idle. On restart it resumes following rows, not stopped rows; redelivering an idle row is not following its later run. This matters for proof 5's idle-then-run case as well as a lost reply. See `apps/server/src/orchestration-v2/ThreadManagementService.ts:696-711`; `apps/server/src/mcp/OrchestratorMcpService.ts:4666-4685`; `apps/server/src/fleet/remoteWorkerMatching.ts:350-351,362-368`; `apps/server/src/fleet/RemoteWorkerFollower.ts:435-458,543-593,595-613,868-886`; `reports/phase-3-proof.md:64-75`.

**Change:** Keep T-19 first. Give a handoff follow row a durable *awaiting continuation/first run* state. An early not-found is not terminal; idle with no run produces no completion. Retire the row on a definitive refusal, recover it on restart or a lost reply, then deliver the actual terminal run with a stable row/run wake key. Test a poll before creation, a refusal, an idle arrival followed by a message on the target, and a running arrival that finishes while the source is offline. Against the previous receiver, assert zero early wakes and exactly one wake for the real result after reconnect and replay.

## EC2-02 [high] “Continue here” can bypass the single execution owner

The design keeps manual pull but says only the current owner can offer a revision and the old turn must have stopped (`reports/equal-coordinators-handoff.md:16-30,93-100`; `spec.md:27,33-34,884-886`). The deployed pull deliberately uses a stale lease and a failed reachability probe, then invokes the receiver **locally**, with the replica epoch plus one (`apps/server/src/handoff/HandoffMoves.ts:1118-1153,1177-1218`). Neither observation proves the source turn stopped. During a partition a live source and a replica can each have network access without reaching each other. Two replicas can also claim locally; the receiver lock is on each machine, not shared between them (`apps/server/src/handoff/HandoffReceiver.ts:895-902`). A later heartbeat that interrupts the source is too late (`apps/server/src/handoff/HandoffMoves.ts:1359-1378`).

**Change:** Make manual pull use the same exclusive transfer as a push: obtain a source-issued, target-specific fence, or use an independently enforceable ownership grant which the old executor must lose before another starts. Without proof, leave the replica readable and the pull waiting; a click is not proof of fencing. In T-20, test a running source partitioned from two replicas, concurrent pulls, and reconnect. Count executions, not just distinct continuation IDs.

## EC2-03 [high] A legacy stuck hold cannot be classified as “never sent”

T-20 claims to fix proof 6 and offers “Resume here” for a never-sent hold (`spec.md:34,884-886`; `reports/equal-coordinators-handoff.md:24-30`). The previous release writes `handing-off` with `pendingTakeover: null` **before** sending; it stores the pending request only on the uncertain-error path, and fences on success. A crash before dispatch and a crash after the destination launched but before the source recorded the answer can leave the same local fields. The legacy retry needs a non-null request (`apps/server/src/handoff/HandoffMoves.ts:684-691,809-823,855-881`). Proof 6 observed the first case; its local row is not evidence that every such row is safe to release (`reports/phase-3-proof.md:79-89`).

**Change:** Define an upgrade state for legacy ambiguous holds, distinct from a new, provably unsent hold. Reconcile against possible targets and the expected epoch; keep the thread held if acceptance cannot be excluded. For new operations persist `sent` before dispatch, make cancellation and dispatch mutually exclusive, and make “not accepted” final for that operation even if a delayed packet arrives. Seed both legacy crash states in the runner test and check that only a proven non-acceptance enables local execution. Also exercise the stated 45-second rule, not just an interrupt request (`apps/server/src/handoff/HandoffMoves.ts:498-519`; `reports/phase-3-proof.md:30-36`).

## EC2-04 [high] The first `handoff.v2` peer cannot certify features released later

T-20 advertises `handoff.v2` before T-24 adds reviewer locks, T-10 adds receiver quota confirmation and T-09 adds worktree sets (`spec.md:29-31,39-40,800-812,841-847,900-902`). For example, the T-22 receiver already advertises v2 when a T-24 source wants to send a review. Acceptance of an ordinary transfer is not acceptance of its review restrictions. Likewise a successful single-repository preflight cannot mean every member of a set was staged. The current wire already has a separate numeric protocol version **2**; its preflight returns failures, not an attestation of any of these features (`apps/server/src/handoff/handoffWire.ts:39-65,159-185`). Missing routing makes the fallback rule unrestricted (`packages/shared/src/reviewPolicy.ts:447-475`).

**Change:** Reserve `handoff.v2` for the T-20 base operation; do not infer it from numeric version 2. Specify a per-operation version, feature bit or affirmative capability response for each later wire feature. Require it at both ends before holding work or exposing partial files. An absent or unknown requirement means “Needs update” or a specific Stayed reason, never a successful downgrade. Add the actual sender, stored replica metadata and peer schemas to the appropriate tasks: T-24 currently lists neither the producer in `apps/server/src/handoff/HandoffMoves.ts:334-351` nor the retention path in `apps/server/src/handoff/handoffState.ts:577-592`; T-10's confirmation needs the peer call/response as well as its planner (`apps/server/src/handoff/HandoffMoves.ts:436-460`; `apps/server/src/handoff/handoffPeers.ts:180-183,286`). Test T-24 against T-22, T-10 against T-24, and T-09 against T-13. A compatible review test must force a *second* model pick and preserve the family, any pinned model and the effort; the first pick alone does not prove AC-40.

## EC2-05 [high] T-23 cannot revoke a silent start by changing only the upgraded machine

Retiring `auto-takeover` is correct. The mixed-version case is a previously armed receiver: the old source announces a delay in its heartbeat, the receiver saves it, and the receiver's own timer can continue a resumable replica without contacting the source. An old peer drops the designation only on a clearing heartbeat; the sender already tracks which announcements were acknowledged (`apps/server/src/handoff/HandoffMoves.ts:1263-1313,1331-1341`; `apps/server/src/handoff/handoffState.ts:786-801`; `apps/server/src/handoff/HandoffAutoContinue.ts:115-145,276-305,371-399`). If the source updates to T-23 and sleeps while disconnected, removing its local trigger cannot retract the old receiver's stored permission. Removing the old source fence at the same time also risks two executions. An old sleep intent already acted upon must not be answered “not accepted” either (`spec.md:27,896-898`; `reports/equal-coordinators-handoff.md:89-100`).

**Change:** Stop new designations and sleep intents; drain and acknowledge previously armed peers and outstanding intents. Distinguish pending, already acted upon and unknown. Keep protective holds until the peer reports its state or confirms disarm; show a pending upgrade when it is unreachable rather than promising zero starts. Include sender heartbeat/disarm call sites in T-23. Test an armed **previous-release** receiver, offline during the upgrade and lid close, plus an old receiver that already acted before its acknowledgement was lost.

## EC2-06 [high] T-21 changes who fires a routine before the old standby loses that power

T-21 replaces the coordinator gate; project standby takeover survives until the *next* release, T-22 (`spec.md:36,803-806,888-894`; `reports/equal-coordinators-handoff.md:67-74,82-87`). The previous standby holds a copy with the same ID and enabled state, and fires it if it becomes coordinator. A new runner continuing independently while the old standby takes over can therefore execute the same due slot twice. An explicit runner move is a second compatibility boundary: the previous routine endpoint has `stage`, `enable` and `release`, but no operation ID or status query; its `enable` switches on **before** writing the supplied run state (`apps/server/src/scheduledTasks/ScheduledTaskCopies.ts:19-25,79-96`; `apps/server/src/scheduledTasks/ScheduledTaskCoordinatorGate.ts:14-31,81-94`; `apps/server/src/scheduledTasks/ScheduledTaskTransfer.ts:64-86,457-465`).

**Change:** Seed the actual runner, but retain the legacy exclusion until every old enabled replica has acknowledged disarm or can no longer fire. A peer that cannot confirm runner revision and idempotent enable must not receive an explicit move; leave the original runner intact. Check the existing Away caller, which explicitly transfers a moved worker's routines (`apps/server/src/away/AwayRunner.ts:362-365,429-451,516`), and assign the “Move the routine too” action to a UI task. Test a due slot on an armed old standby during a partition, plus lost enable acknowledgement. Count actual fires across both machines.

## EC2-07 [high] T-22 misses an installed coordinator state: `transferring`

The migration names `active`, `transferred` and `standby`; the actual binding states are `active`, `transferring` and `transferred`. Standby is a separate field (`spec.md:26,876-878,892-894`; `reports/equal-coordinators-handoff.md:80-87`; `packages/contracts/src/logicalProject.ts:94-113`). The old server writes `transferring` durably before destination execution, and proof 6 observed that state even *after* destination activation (`apps/server/src/fleet/MachineHandoff.ts:994-1022`; `reports/phase-3-proof.md:79-85`). Ignoring it leaves an inactive coordinator after T-18 removes the recovery UI. Blindly flipping it to active leaves a late legacy operation free to rewrite ownership. There is also a persisted supersession hold outside the binding: peer sync marks it before calling give-way, and the wake gate reads it (`apps/server/src/project/LinkedPeerSync.ts:491-518`; `apps/server/src/project/CoordinatorWakeGate.ts:248-279`).

**Change:** Specify a disposition for every persisted binding and outstanding operation ID. Reconcile or retire the old role operation at both ends; preserve both conversations and the independently fenced workers. Disable late legacy role writes and clear obsolete coordinator-only holds without clearing thread holds. Extend T-22's Files to cover the fleet move and peer-sync/admission paths. Test upgrade before target activation, after activation with lost acknowledgement, and with an old peer retrying. Type on the upgraded member after restart, not just immediately after migration.

## EC2-08 [high] The automatic start loses its disposition before the batch sees it

T-13 ships before T-11; T-11 promises one batch for both starts (`spec.md:32,807-812,845-859`). The automatic caller constructs `resume`, `reason` and `idempotencyKey` and passes all three to its port. The production adapter forwards only thread, destination and model to `handOff`. The receiver independently infers resume from the checkpoint (`apps/server/src/orchestration-v2/MachineLimitHandoff.ts:581-599`; `apps/server/src/orchestration-v2/LimitHandoffAdapter.ts:168-185,216-226`; `apps/server/src/handoff/HandoffReceiver.ts:697-700,769-793`). A manual call and a threshold call on the same idle thread can reach the same API with identical inputs. The eventual progress view cannot reconstruct “you asked” versus “track out” from those inputs. A test of the planner or batch alone misses the loss. Neither task owns the adapter.

**Change:** Before T-13 activates the rule, wire the production port into a one-thread T-20 operation carrying the trigger key, reason, intended run and disposition. Alternatively release the common batch before activating the trigger. Keep the final local-track/Stop/opt-out check before dispatch. Include the adapter and its integration test; assert real launch counts for limit-stop, threshold-idle and user Stop and assert the stored reason for both starts. In T-11 also list the window RPC definition/group and client binding for any new calls, or name the existing calls being reused: the permission map does not register a callable method (`packages/contracts/src/awayRpc.ts:30-41,64`; `packages/contracts/src/rpc.ts:2480-2485`; `apps/server/src/away/AwayRpc.ts:17-39`).

## EC2-09 [high] The acceptance gate passes an inconclusive proof

AC-49 requires **each release** to work against the previous release, but its task is closure, after every deployment. T-08 tests only that its report is nonempty and lacks the literal `Verdict: fails`; T-15 tests only that its report is nonempty (`spec.md:39-40,800-813,836-839,861-868`). The T-08 condition accepts the historical proof ending `Verdict: cannot be shown with today's released code.` (`reports/phase-3-proof.md:30-36`). This was checked against the actual condition. An inconclusive proof or one that omits five of six cases can therefore pass. A same-version run at the end cannot establish the intervening mixed-version behavior.

**Change:** Put a version-pinned compatibility case in each shipping task's Test, before release, with both directions and the expected outcome per operation: success, safe refusal, or recovery of an existing transfer. Record both builds, the operation, source and destination effects, and the observed result. Give T-08 a positive check for every required case and explicit pass evidence; missing, skipped or inconclusive is not a pass. T-16 should aggregate those receipts. Repoint T-14's old Fix-dialog/AC-21 fixture and T-15's old coordinator/lid-close script to the surviving scenarios (`spec.md:309-310,861-868`). No second owner decision is needed.
