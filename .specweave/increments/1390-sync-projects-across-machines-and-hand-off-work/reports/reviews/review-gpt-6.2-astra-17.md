## Blocking findings

### T19R2-01 [high] An accepted hop can leave the original launcher with no result

`/Users/antonabyzov/Projects/github/specweave-umb/repositories/anton-abyzov/specwithcode/apps/server/src/fleet/RemoteWorkerFollower.ts:734-747,1258-1276`; `/Users/antonabyzov/Projects/github/specweave-umb/repositories/anton-abyzov/specwithcode/apps/server/src/fleet/handoffFollower.test.ts:549-562`.

**Scenario:** A launches the worker, A hands it to B, and B has permission to hand it to C. A has no direct fleet entry for C. B accepts the move, C finishes, and A writes `stopped` and exits. The test asserts an empty launcher inbox; startup does not restart this row. B handing the worker back to A has the same outcome on a normal fleet that lists peers, not self. The returned continuation is created as `system`/`server`, so it is not independently recognized as a locally launched worker. Even a **temporary** failure to read A's fleet file is converted into the same permanent stop for a *configured* C.

**Fix:** Keep the delivery obligation on an authorized route: follow a hand-back locally; relay the result through B for a non-direct hop, or decline the onward move before execution ownership changes if it cannot retain a route. Retry a fleet read failure rather than treating it as proof of absence. Do not grant A direct access to C. Test all three paths and require one wake on A after an accepted move.

### T19R2-02 [high] Revisiting a reachable machine can pin a continuation that never existed

`/Users/antonabyzov/Projects/github/specweave-umb/repositories/anton-abyzov/specwithcode/apps/server/src/fleet/handoffDelivery.ts:173-185`; `/Users/antonabyzov/Projects/github/specweave-umb/repositories/anton-abyzov/specwithcode/apps/server/src/handoff/handoffFence.ts:163-184,187-210`; `/Users/antonabyzov/Projects/github/specweave-umb/repositories/anton-abyzov/specwithcode/apps/server/src/fleet/RemoteWorkerFollower.ts:743-755,932-942`.

**Scenario:** A follows B (epoch 2), then C (3). C hands the work back to **B** (4); both are directly reachable from A. C publishes its move link before it appends the new execution-history entry. Between those writes its thread correctly reads “fenced, now on B,” but history still ends on C, with an earlier entry for B at 2. At this head `movedOn` returned B/2 on precisely that snapshot and B/4 once the second write was visible. The follower has already repointed its only row to the ID derived from C's thread and epoch **2**. B created the ID for epoch **4**. Polls of the nonexistent ID retry indefinitely without consulting C again.

**Fix:** Prefer the continuation ID from the accepted move receipt. If using the released read format, accept only the new, current history stretch for the destination, not any historical visit; keep the prior route and retry an inconsistent snapshot. Test a read between the two writes on A → B → C → B.

### T19R2-03 [high] The paged scan changes which run counts as the result

`/Users/antonabyzov/Projects/github/specweave-umb/repositories/anton-abyzov/specwithcode/apps/server/src/fleet/RemoteWorkerFollower.ts:630-660,685-698,712-720`; `/Users/antonabyzov/Projects/github/specweave-umb/repositories/anton-abyzov/specwithcode/apps/server/src/fleet/handoffDelivery.ts:81-92,157-164`.

**Scenario:** On an idle-arrival thread, two messages are queued; the second is moved ahead and completes first. The first-queued message runs later and also completes. On reconnect, 49 subsequent queued messages leave the actual first result just inside the 50-run window and the later result just outside it. Run ordinals do not change when the queue is reordered. The explicit wait for the omitted run returns status but no start time; `olderRuns` supplies `startedAt: ""`. That sorts before every actual timestamp. I ran the head selector in memory: with the two real start times it reported `job`; with the production off-page encoding for the later run it reported `later`. The wrong wake closes the row, so the launcher's job result never follows. This does not depend on the missing cancel-sequence red.

**Fix:** Preserve an authoritative run-start order or an authoritative identity for the outstanding job across the page boundary. Do not use page membership as evidence of execution order. Add the straddling, reordered case with distinct result IDs and assert the original launcher's message, not just its count.

### T19R2-04 [high] Restart can send two completion wakes for the same delivery

`/Users/antonabyzov/Projects/github/specweave-umb/repositories/anton-abyzov/specwithcode/apps/server/src/fleet/RemoteWorkerFollower.ts:325-326,760-772,1028-1064,1271-1276`; `/Users/antonabyzov/Projects/github/specweave-umb/repositories/anton-abyzov/specwithcode/apps/server/src/fleet/handoffFollower.test.ts:406-433`.

**Scenario:** The handed-off job fails, the grace period expires, and its failure is sent. The target later starts a genuine server fallback for that failed run and completes. When the source restarts within the failed-run recheck window, it reopens the *delivered* obligation and sends another completion under the fallback run ID. The new green test explicitly waits for **two kept messages** and asserts two different command IDs. This is not a replay of the same notification, or a separately requested job. Recognizing the relationship is correct; treating it as a new delivery is not.

**Fix:** Keep fallback tracking separate from whether the launcher is still owed a notification. Follow a replacement before the final wake, or update the card after delivery without another completion wake. Persist a delivery-level wake identity across replacement runs. Test the late fallback with and without a source restart: the final outcome is available, and at most one completion message reaches the launcher.
