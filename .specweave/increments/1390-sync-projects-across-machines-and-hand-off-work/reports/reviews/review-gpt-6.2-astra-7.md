# Review: 1390 equal coordinators and hand off proposal
Verdict: fix first

Keep the equal coordinators and the two agreed ways to start. Do not accept the transfer protocol yet. In the existing two-machine proof, a worker resumed and finished without notifying its launcher; another thread was held with no continuation and no working retry. A reply of “done or failed” cannot distinguish either case from a successful handoff.

## EC-01 [high] The shipped default can leave while a local model has room

With `switch`, a configured M5 target and a usable local fallback, the shipped default is `other-machine-first`. The sweep considers M5 before committing the local switch. Changing only the default would leave explicitly saved remote-first projects doing the same thing. The proposal describes the desired order but supplies no precedence or migration rule. Evidence: `reports/equal-coordinators-handoff.md:35-38`; `packages/contracts/src/settings.ts:1702-1707,2136-2149`; `apps/server/src/orchestration-v2/MachineLimitHandoff.ts:200-206`; `apps/server/src/orchestration-v2/ProviderFallbackWorker.ts:1847-1871,1875-1904`.

**Fix:** For track-routed work, make exhaustion of the effective local track a prerequisite for *any* remote attempt, including the final admission check. Explain in Settings what happens to a saved remote-first order; do not silently change unrelated non-track projects. Use the user's saved routes, source permissions and track order, not a hard-coded list. The proposal correctly names the built-ins: Daily = Opus 5.5 → Sonnet 5.5 → GPT-6.1 Sol → GPT-6 Luna; Complex = Fable 5.2 → GPT-6 Astra; Review = Muse Wonder Full (Extra High) → GPT-6.1 Sol → Gemini 4 Carbon. Test both order values with a second local source, then a later local model. Each gets its own chance; one instance's failure must not hold its siblings. A provider with `supportsProviderSwitchingViaHandoff=false` must not be forced across providers. Preserve `ask`, `wait`, no targets, near-reset waits and source-consent requirements. See `spec.md:17-18`; project memory `decision_model_tracks.md` rev. 12, lines 5-11; `decision_handoff_mode.md` rev. 3, “Limits”.

## EC-02 [high] A configured target is not proof of capacity on the same track

A saved target is a **machine plus a particular model selection**, not a track. The current judge can accept an otherwise eligible Daily-only model for a Complex thread. Conversely, it rejects a known matching account fingerprint on the same driver *before* checking percent used, even if a stale display suggests room. Unknown identity, unknown usage or stale usage can qualify under a separate opt-in. The proposal notices the same-account and fleet-wide exhaustion cases, but “an account that is also out” and “when the limit resets” do not specify which evidence admits a move or which reset to show. Evidence: `reports/equal-coordinators-handoff.md:36-38`; `packages/contracts/src/settings.ts:1684-1699,2151-2154`; `apps/server/src/orchestration-v2/MachineLimitHandoff.ts:422-430,452-483,678-693`; `packages/shared/src/machineFallback.ts:30-34,95-104,138-146,160-192`; `spec.md:275,284`.

**Fix:** Intersect the permitted machines and sign-ins with the moving thread's effective track; have the receiver confirm the actual model, account and usable quota before accepting. A matching depleted quota pool adds nothing; try another eligible sign-in on that machine, not a different track. Unknown is not evidence of room for an automatic track move. For a manual move, show the same-account or unknown warning without pretending it buys quota. If all allowed machines are out, **leave the thread where it is**, name the track and earliest known eligible reset, then recheck; if no reset is reported, say so. No move, retry loop or out-of-track substitution. Test shared fingerprints, stale readings, an off-track target and two different reset times.

## EC-03 [high] Review cannot move without its reviewer lock

The proposal includes Review in the remote path. Today a marked review delegation has **no machine candidates**, deliberately: its reviewer-family lock does not travel. The shipped test expects zero requests even with two targets. Removing just that guard can let a review continue on the author's family; leaving it alone makes the new Review promise false. Evidence: `reports/equal-coordinators-handoff.md:36`; `apps/server/src/orchestration-v2/MachineLimitHandoff.ts:417-422`; `apps/server/src/orchestration-v2/MachineLimitHandoff.test.ts:295-323`; `spec.md:284`.

**Fix:** Carry the review routing marker, family restrictions, review policy and effort with the thread. Apply those constraints to both the receiver's first selection and every fallback. Cover older prefix-only reviews as well as marked ones (`decision_model_tracks.md` rev. 12, “Review work falls back along the Review track”). Until the receiver can prove compatibility, show “Review stays here” with the reason and wait. Test a receiver with only the author's family and one with a permitted reviewer.

## EC-04 [high] A 99% reading is not permission to start a turn

The proposal says the receiver resumes each thread. The threshold is **percent used**, defaults to 99 and can be disabled with `null`. A recent completed idle thread can be positioned once per usage window **without** resuming; a resumable limit stop has a different key and resumes. An active run, blocking request or settled thread is not admitted by this trigger. Sending one blanket “resume” for the whole track can start work the user did not request. Evidence: `reports/equal-coordinators-handoff.md:19,26-29,36`; `packages/contracts/src/settings.ts:1589-1595,2102-2108`; `apps/server/src/orchestration-v2/MachineLimitHandoff.ts:181-186,201-228`; `apps/server/src/handoff/HandoffReceiver.ts:751-777,792-794`.

**Fix:** Carry a per-thread disposition: resume a specific interrupted or limit-stopped run, install idle for the next turn, or stay with a reason. Evaluate each thread independently; never sweep in a healthy sibling simply because its track matches. Require `switch` and configured targets for automatic movement. Keep user Stop, pending approval and settled states intact. Test a real stop, a recent idle thread at 99%, one outside ten minutes and `null`; distinguish “Ready on M5” from “Resumed on M5”.

## EC-05 [high] Two equal coordinators need one execution owner per thread

“Create or update” does not say how to recognize the same logical thread, whose update wins, or who may start its next turn. If both coordinators act on the same snapshot, a manual and automatic send can create two continuations, overwrite a newer turn, or send a just-arrived thread straight back on the same limit signal. The shipped receiver already derives a stable continuation ID for a particular source and epoch, journals side effects and uses a stable launch command. A project name and the latest context are not substitutes. Evidence: `reports/equal-coordinators-handoff.md:17-30`; `apps/server/src/handoff/HandoffReceiver.ts:192-202,751-777`; `apps/server/src/handoff/HandoffTurnGate.ts:51-63`.

**Fix:** Address the linked project by ID and the work by stable thread lineage, expected owner/epoch and checkpoint sequence. Only the current holder may offer that revision. Atomically claim it at the receiver; replay the same receipt for duplicate operations, reject stale or divergent revisions without overwriting either history, and suppress a reverse automatic move for the same run/window. Different threads may cross in opposite directions. Test crossed sends, duplicate creation, reordered packets and two starts for the same thread. Neither coordinator wins a *project* role.

## EC-06 [high] Loss of the reply is neither failure nor permission to resume locally

Two cuts matter. Before takeover, the recorded proof left a thread `handing-off`, with `pendingTakeover: null`, no target continuation and no working retry. After M5 accepts, losing its reply looks identical to failure from m4 but M5 may already be running. Today an uncertain send stays paused; a definite refusal can release. The proposal gives the sender only done/failed. Evidence: `reports/equal-coordinators-handoff.md:19,27-30,46`; `reports/phase-3-proof.md:79-89`; `apps/server/src/handoff/HandoffMoves.ts:782-789,809-815,855-881`; `apps/server/src/orchestration-v2/MachineLimitHandoff.ts:595-619`.

**Fix:** Before the first hold, persist the batch, per-thread operation ID, target, checkpoint and intended disposition. Persist the target's acceptance before launching. On reconnect or restart of either machine, query or replay that same operation; do not pick another target or start locally while acceptance is unknown. A definitely unaccepted item may be released, not an ambiguous one. Require the previous active turn to have stopped before starting another. Prove interruption before send, after receipt and after resume but before acknowledgement, with a fresh window and a partially successful batch. Sleep can pause an existing operation; it must not start a new one.

## EC-07 [high] A transfer receipt does not deliver the worker's eventual result

On both m4→M5 and m4→M1, the worker finished on the target and the launching coordinator never got its completion. Today's receiver creates a system/server continuation; the normal launcher wake selects agent-launched threads. “Done” when the handoff succeeds does not fix that broken return path. Evidence: `reports/equal-coordinators-handoff.md:19,28-30`; `reports/phase-3-proof.md:64-75`; `apps/server/src/handoff/HandoffReceiver.ts:775-795`; `apps/server/src/project/LaunchedWorkerWake.ts:119-129,169-173`.

**Fix:** Preserve the launcher/parent address separately from the execution owner, register the continuation before acknowledging transfer, and route its eventual result once to the coordinator or parent that is waiting. Persist undelivered results while the launcher is offline. Prove one remote completion wakes the original launcher once after reconnect, with no second wake on receipt replay.

## EC-08 [high] Equal coordinators remove the scheduler's single-runner test

Multiple machines can hold copies of the same coordinator-owned routine. Today's scheduler uses the coordinator binding to decide which copy fires or accepts an edit. Making both coordinators active makes both copies eligible if that is the only gate; retaining the old gate can leave neither running. The old move proof observed the latter outcome, not a double run. Evidence: `reports/equal-coordinators-handoff.md:17-19`; `apps/server/src/scheduledTasks/ScheduledTaskCoordinatorGate.ts:14-31,45-50,65-85`; `reports/phase-3-proof.md:50-58`.

**Fix:** Give each routine one durable runner and revision independent of the project coordinator. Leave existing coordinator-owned routines with their actual runner by default; a thread handoff must not silently copy or activate schedules. Route changes to that runner, reject conflicting stale edits, and keep webhook URLs local. Define the disposition of a routine bound to a moving worker. For any explicit runner move, stage disabled, confirm source disabled, transfer the due slot, then enable once. Test a due fire, concurrent edits and a lost enable reply.

## EC-09 [medium] “Latest context” does not resolve conflicting project memory

If both coordinators edit the same note offline, an arriving thread's older context must not replace the receiving project's note or be treated as a new project instruction. The proposal does not distinguish a thread snapshot from authority to write shared memory. The existing memory path already detects concurrent edits, merges where possible, and preserves a conflict copy before replacement. Evidence: `reports/equal-coordinators-handoff.md:17-19,27-28`; `apps/server/src/project/linkedMemoryMerge.ts:9-16,284-321`; `apps/server/src/project/LinkedMemorySync.ts:332-357`.

**Fix:** State that handoff changes only thread ownership. Carry context at a named revision; leave coordinator conversations local and reconcile shared memory through its existing revision-checked sync. Surface unresolved conflicts without using packet arrival time as precedence. Test two offline edits to the same note while a thread moves: neither edit disappears and neither machine gains authority over the other.

## EC-10 [high] Removing the Phase 1 labels alone leaves a coordinator that cannot run

Version 1.0.368 shipped a real behavior, not just “Extra coordinator” and “Fix…”. Link acceptance writes `transferred` on the joining machine; the role service treats only `active` as active. T-18 lists UI files. Removing those labels and leaving Add's link behavior unchanged would make a newly added M5 *look* equal while local typing still routes away or cannot start. A returning old peer can also advertise a superseding binding. Evidence: `spec.md:9-11,20,838-841`; `reports/equal-coordinators-handoff.md:9-19,50`; `apps/server/src/project/ProjectLink.ts:115-119,671-677,1233-1239`; `apps/server/src/project/CoordinatorRole.ts:93-105`; `apps/web/src/studio/coordinatorBoxState.ts:73-94,116-131`.

**Fix:** After acceptance, migrate existing active/transferred/standby members and change new link acceptance. Preserve both coordinator histories, local worker ownership, project identity and genuine Settings unlink; retire project-level give-way, standby takeover and remote composer routing, **not** the per-thread execution fence. Require peer capability agreement for the new handoff and show “Needs update” for an incompatible peer; do not use a build flag or silently revert to moving the coordinator. Prove local typing on both a formerly transferred member and a freshly added one, including an old peer reconnecting.

## EC-11 [high] A saved sleep trigger still starts a move

“Sleep handoff stays off” is correct for the revised design but not for every installed configuration. A saved Away target with `sleepTrigger: "always"` fires on suspend; `"on-battery"` does so on battery. The desktop also has a renderer fallback when Away declines. Leaving the default off or hiding the setting does not stop either path for existing users. Evidence: `reports/equal-coordinators-handoff.md:35`; `spec.md:17,283,820-821`; `apps/server/src/away/awaySleepRoute.ts:105-114`; `apps/desktop/src/app/DesktopHandoffSleep.ts:158-169,179-205`.

**Fix:** Retire sleep as a *start* event for these handoffs at both sender and receiver, including legacy preferences and outstanding sleep intents. Keep harmless sleep/checkpoint notices distinct from a request to move. Test lid-close with both legacy settings and no window open: zero new handoffs, while a previously authorized handoff remains recoverable under EC-06.

## EC-12 [medium] The progress bar counts outcomes but labels them as arrivals

The mockup says “2 of 4 threads on M5”. Its rows show one resumed, one received, one sending and one failed. Under the proposal's own definition two outcomes are terminal, only one is confirmed resumed, and the rendered bar is 46%, not 50%. There is no row for an unknown acknowledgement or a thread installed idle. Evidence: `reports/equal-coordinators-handoff.md:40-46`; `reports/handoff-progress-mockup.html:71,95-116,120`.

**Fix:** Use “2 of 4 finished: 1 resumed, 1 failed” and derive 50% from those same terminal rows. Give pending, held, ready-but-idle, waiting for confirmation, stayed/skipped, and failed distinct meanings and safe next actions. A waiting row does not count as failed; all failed must never read “all on M5”. Show the earliest reset or “reset unknown” when no destination qualifies. Keep the existing quoted project name/icon and use this same view for manual and automatic starts; only their reason changes.
