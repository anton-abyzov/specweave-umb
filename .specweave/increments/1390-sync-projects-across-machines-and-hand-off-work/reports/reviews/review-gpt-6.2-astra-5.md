## E-01 [high, blocks] A successful source reply can report an unconfirmed destination write as “Stays on {source}”

`apps/web/src/components/studio/projectSyncDialog.logic.ts:1114` treats an `unreachable` item as definitively staying. There are **two replies**, not one. The receiver can write the branch and then lose its reply to the source. The transport explicitly marks a failure after the replicate POST, a proxy 5xx, or an undecodable success as uncertain (`apps/server/src/handoff/handoffPeers.ts:465–475,509–524`). The source drops that flag (`apps/server/src/fleet/ProjectSyncExtras.ts:470–492`) and returns a normal item with `status: "stays"` (`:407–417`). The window receives a perfectly decodable batch, prints “Stays on {source},” and a retry gets a fresh operation ID (`apps/web/src/components/studio/ProjectSyncDialog.tsx:772–777`). Showing the peer detail once does not correct the headline.

Preserve uncertainty through the two hops, or conservatively treat an indistinguishable `unreachable` item as unknown in the window. Keep confirmed siblings. The regression should give the window a **successful batch** containing that item and require “may have arrived; check the destination,” not “Stays.” This does not require adding a literal to the shared contract.

## E-02 [high, blocks] A send can start after its dialog and plan are gone

`apps/web/src/components/studio/ProjectSyncDialog.tsx:770–778` checks only `gate.current` before each extras call. The generation and mounted checks are outside the entire loop (`:745,792`). If the first batch is outstanding when the dialog unmounts, cleanup sets `alive.current = false` (`:607–612`); resolving that batch still dispatches the next one using the old pair and ticks. Only afterwards does the dead dialog discard the result. Losing operate access on the shown machine provides a production route: the parent removes `onCopy` (`apps/web/src/components/studio/ProjectWorkspaceSurface.tsx:2253`), and the hook removes the dialog instead of passing a new block (`apps/web/src/components/studio/useProjectSyncMenu.ts:263–269`). The bug is dispatching more work; whether it lands depends on the permissions still in force on that route.

A temporary denial while still mounted also matters: `planning.current` excludes `running` (`apps/web/src/components/studio/ProjectSyncDialog.tsx:630–633,702–709`). If access returns before the pending call resolves, the old run can continue without another check or fresh consent. A superseded fetch likewise starts inventory before checking its generation (`:652–659`). The two initial Git calls run concurrently (`:726–743`); this is not evidence that a call already submitted can be recalled.

Make invalidation permanent **for that run**. Check the execution identity, lifetime and pair permission before each new dispatch; keep confirmed receipts and mark unattempted items separately. Test unmount and deny-then-regrant while batch one is outstanding and assert no further dispatch, including on the other side.

## E-03 [high, blocks] Add still restores a measured folder move, including its old target

`apps/web/src/components/studio/ProjectMachineHandoff.tsx:1043–1053` bypasses the saved **Git handoff** for Add, but still consults the folder-copy pointer. The child receives `machineRequested=true` (`:1240–1245`), which does not suppress unfinished pointers. `apps/web/src/components/studio/useCopyDraft.ts:88–105` resumes one without checking its mode or target. `apps/web/src/components/studio/HandoffFolderCopy.tsx:602–615` then installs the saved machine, folder and `copy-and-move` mode. The callback restores move intent in the parent. An applied move can enter transfer recovery (`:691–699`), whose continuation calls `moveCoordinator` (`:1009–1011`). No assumption that simply opening every saved move transfers the coordinator is needed.

With an unfinished measured move to B, choosing Add for a project missing on C must not open the move to B. Preserve its pointer and give it a separate recovery action; if both operations cannot coexist, explain that without adopting the pointer in Add. Exercise the real child, not only the parent props.

## E-04 [high, blocks] “In sync” is possible without fresh evidence for every displayed repository

`apps/web/src/components/studio/ProjectSyncDialog.tsx:793–815` does request both statuses after the run. But `apps/web/src/components/studio/projectSyncDialog.logic.ts:500–518` compares the two lists **only to each other**. Plan a root and a level nested repository, move the root, and let both post-run scans omit the nested path, for example because those checkouts were removed or replaced by excluded worktrees. Both complete status replies can report just the same clean root. The result table still uses the original rows (`apps/web/src/components/studio/ProjectSyncDialog.tsx:809`), yet the title can say “in sync” without a read of the nested row on either side.

There is a second, decodable case: `[root, root]` on A and `[root, nested]` on B can satisfy the equal-length, one-sided map check. The status schema does not enforce unique paths (`packages/contracts/src/projectSync.ts:88–96`). Require unique path sets covering the displayed repositories and matching on both sides; keep “Sync finished” if that proof is missing. Test the ordinary omitted-on-both case, not just malformed input.

## E-05 [medium, follow-up] The whole-call classifier mistakes a known non-send for uncertainty, and arbitrary message text for a refusal

`packages/client-runtime/src/rpc/client.ts:143–155,210–220` can return `EnvironmentRpcUnavailableError` because there is **no session**, before the method is invoked. The production adapter passes the failure to the window (`apps/web/src/studio/projectSync.ts:94–103,120–128`), which says “may have arrived” (`apps/web/src/components/studio/projectSyncDialog.logic.ts:922–936`). Its test explicitly expects that at `apps/web/src/components/studio/projectSyncDialog.logic.test.ts:829`. Starting a batch in the window is not proof that it left the window.

In the other direction, the test for an unknown method searches an unanchored `Unknown request tag` substring in any `reason` or `message` **before** checking the typed failure (`apps/web/src/components/studio/projectSyncDialog.logic.ts:70–86,925–929`). A `SchemaError` containing those words would be called “Not sent” even though it provides no such evidence. This is a classifier counterexample, not a claim that the fixture or an actual peer produced that message. Use the actual unsupported-method shape for this method; distinguish proven pre-dispatch failure from transport loss. The source's typed `invalid`, `not_found` and `personal` exits inspected do precede the item loop (`apps/server/src/fleet/ProjectSyncExtras.ts:541–552`; `apps/server/src/fleet/ProjectSync.ts:958–978`). Treating `failed` and an unproven `busy` as uncertain is appropriate.

## E-08 [medium, follow-up] The “finish or cancel” toast also matches a finished move

Completion sets `phase="complete"` and clears the saved pointer, but not the in-memory snapshot (`:529–534,562–574`). Closing a completed result skips discard (`:452–455`). While that same surface stays mounted, a subsequent Add can say to finish or cancel a move that has already finished, with no pending pointer for recovery. A remount can clear this state; this is not a permanent server lock.

For an actual interrupted published **linked** handoff, the separate “Finish handoff” control is real (`apps/web/src/components/studio/ProjectWorkspaceSurface.tsx:2027`; `apps/web/src/components/studio/ProjectHandoffRecovery.tsx:42–58,95–106,219–226`). The toast alone is not a recovery action. Base the guard on recoverable unfinished work, offer the supported recovery from the refusal, and test completed-then-Add without remount. Do not remove a pending pointer to make the toast disappear.
