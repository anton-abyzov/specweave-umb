## Round 1 findings revisited

### P2-01 fixed: Sync's fetch names its own destinations; a fetched tag cannot replace a local one

`apps/server/src/fleet/ProjectSync.ts:80` to 89 fixes the fetch as `fetch --quiet --no-prune --no-prune-tags --no-recurse-submodules --refmap= origin +refs/heads/*:refs/remotes/origin/*`, and `ProjectSync.ts:96` to 116 refuses to fetch at all (state `unusual-config`, planned as `fetch-config` at `packages/contracts/src/projectSync.ts:182`) when `remote.origin.mirror` is set or a configured fetch line writes outside `refs/remotes/`.

Direct answer to the round 2 question. I reproduced the exact fetch in `/tmp` against a repository carrying an extra configured line `+refs/heads/*:refs/heads/stolen/*`, `fetch.prune=true` and `remote.origin.tagOpt=--tags`, with the remote's tag `shared` force-moved: no `refs/heads/stolen/*` appeared, only `refs/remotes/origin/main` moved, the local tag `shared` stayed at its old commit, a genuinely new tag was created, and the fetch exited 1 on the tag it would have had to replace, which `ProjectSync.ts:283` maps to `fetch: "failed"`, so no merge follows. So: no repository setting I could construct (extra or mirror fetch lines, prune and pruneTags settings, `tagOpt`, `url.insteadOf` rewrites, a rewound remote) lets this fetch create, move or delete anything outside `refs/remotes/origin/*` and newly created tags, because the command line refspec and `--refmap=` override the configured ones and there is no `--force` for tags. A fetched tag can be created but never replaces or deletes a local tag. Two literal exceptions outside those refs: Git writes `FETCH_HEAD` on fetch and `ORIG_HEAD` on the fast-forward merge, both pseudo-refs, neither a branch or tag. The fast-forward itself moves the checked-out branch, which is its purpose; where it may move it to is P2-10 below. The server's own environment is trusted as before (`apps/server/src/fleet/folderTransfer/git.ts:68` spreads `process.env`); a repository cannot set it, so `GIT_DIR` or `GIT_CONFIG_*` injection is not a repository escape.

### P2-02 fixed: the in-use list is read live, and again immediately before the merge

`ProjectSync.ts:750` to 752 runs the running-threads query on every `inUse` call and fails closed when it cannot be read. Facts read it last (`ProjectSync.ts:319`, after status at line 308), and `fastForwardRepository` re-reads all facts at line 365, resolves the target, then asks `inUse` once more at line 379 with only the merge left to run. The named tests match this reading (`ProjectSync.test.ts` "does not move a checkout a thread started working in after the recheck's reads"; `ProjectSync.service.test.ts` "holds back a checkout a running thread works in, and only that one"). The residual window between line 379 and the merge is inherent and was the accepted shape of the round 1 fix. One fail-open corner remains and is filed as P2-18.

### P2-03 partly fixed: a checked-out branch can no longer be moved; the compare-and-swap gap stays

Arrival moves now go through `git branch --no-track -f` at `apps/server/src/handoff/ExtrasReceiver.ts:112`, which Git refuses atomically for a branch checked out in any worktree, closing the round 1 window; the named test at `ExtrasReceiver.test.ts:172` covers the late-checkout case. The worker's disclosed gap is real and is filed as P2-13: `moveBranchForward` re-reads the ref at line 107 and ancestor-checks at line 108, then the `branch -f` at line 112 carries no old value, so a non-Git-interface writer (a user's own `git update-ref` plumbing) moving that `swc/from-` branch in between is overwritten. Creating or committing on the branch normally requires checking it out, which is now refused, so what remains is plumbing-level interference with an arrival branch in a sub-second window. Low.

### P2-04 fixed: binary and UTF-16 heads are scanned; an unreadable file is not checked, never fine

`apps/server/src/handoff/snapshotSecrets.ts:35` to 39 re-runs the token patterns with NUL bytes removed, which makes ASCII tokens in UTF-16LE and BE, with or without a BOM, contiguous; the named test at `snapshotSecrets.test.ts:82` covers binary, LE-BOM, BE (via `swap16`) and LE without BOM. Unreadable files map to not-checked and are left out in the Sync path (`snapshotSecrets.ts:69` to 75, 117), as AC-14 requires; the named test at line 104 asserts both modes but early-returns where `chmod 000` does not block the process. Two small remainders: NUL-stripping can also join a split token into a false positive (fail-closed, the file is left out, acceptable), and a FIFO swapped in for a listed file can hang the pre-check read (P2-17, fail-closed).

### P2-05 partly fixed: what is staged is what is judged, with one capped corner

`apps/server/src/handoff/checkpointGit.ts:235` to 271 writes the private-index tree, judges the staged blobs with `checkStagedContent`, force-removes flagged and secret-named paths and re-writes the tree before `commit-tree`, so a rewrite between the worktree check and staging is judged as staged. Both named tests cover the rewrite and the directory swap (`snapshotSecrets.test.ts:229` and 264). The corner filed as P2-12: the staged content read is capped at 2,000 files by a silent slice at `snapshotSecrets.ts:209`, and files past it in a swapped-in folder are neither judged nor reported as not checked. A file that replaces a tracked symlink (diff status `T`) is also not content-checked (`snapshotSecrets.ts:177` treats only `A` as added); that sits inside AC-14's accepted boundary for tracked changes, which are name-checked only, and is noted here rather than filed.

### P2-06 fixed: an unfinished operation counts as uncommitted, including a multi-commit cherry-pick part way through

`ProjectSync.ts:139` extends the shared mark list (`apps/server/src/handoff/bundleGit.ts:320`: `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `BISECT_LOG`, `rebase-merge`, `rebase-apply`) with `sequencer`, for Sync only, and `ProjectSync.ts:217` to 226 treats an unfound Git directory as unfinished. The named tests at `ProjectSync.test.ts:809` and 827 cover `CHERRY_PICK_HEAD` with an empty status and the lone-`sequencer` state. On the other marks the brief asked about: `rebase-merge`, `rebase-apply`, a revert sequence (`REVERT_HEAD`, plus `sequencer` between commits) and `BISECT_LOG` are all in the list; `MERGE_MSG` and `AUTO_MERGE` are rightly left out, because while an operation is genuinely unfinished one of the listed head marks is present alongside them, and both files can also exist without one. A stale empty mark left by a crash blocks the fast-forward forever, which is the safe direction.

### P2-07 partly fixed: local paths and plain loopback no longer cross; loopback spellings still do

`ProjectSync.ts:327` to 330 returns no clone address unless `canonicalOrigin` accepts the address and `isLocalAddress` (`ProjectSync.ts:122` to 132) clears it, and the clone itself re-checks at line 445. Folder and `file://` origins, `localhost`, `*.localhost`, `127.x.x.x`, `::1` and `0.0.0.0` are refused, as the named tests assert. The spellings that still pass are filed as P2-11.

### P2-08 fixed for one server: dead sends and arrivals are swept; cancelled sends finish and clean up

The sender registers its operation before sweeping (`apps/server/src/fleet/ProjectSyncExtras.ts:560` to 564 with the refcounted active set), and `sweepStaleExtraRefs` at line 126 deletes only refs whose operation is not active; the receiver sweeps all incoming refs but the current one at the start of a landing (`ExtrasReceiver.ts:136` to 147), sound because arrivals per repository are serialised. The named tests cover the dead-ref cases and the cancelled send (`ProjectSyncExtras.test.ts:375`, `ExtrasReceiver.test.ts:229`, `ProjectSync.service.test.ts:573`). What remains is filed as P2-14: the active set is snapshotted before the async listing, so a second send that registers and creates its hidden ref in between can have that live ref swept, failing that send without losing anything; and two concurrent sends reusing one operation id share hidden refs and each other's cleanup. Both need two overlapping `sendExtras` calls, which nothing issues yet.

### P2-09 fixed: a cancelled clone stops, its folders go, and the lock is held until Git has ended

The clone receives the call's `AbortSignal` (`ProjectSync.ts:493` to 497`), failure or cancellation removes the target and undoes the parents this call made (lines 504 to 510; the parent undo is `rmdir`-only over folders recorded after a successful `mkdir`, lines 453 to 466, so a folder this call did not make, or one that gained files meanwhile, is never deleted). Merges stay uninterruptible by design, and the admission lock is released only after the stopped work settles (`ProjectSync.ts:660` to 684), matching the named service tests at `ProjectSync.service.test.ts:309`, 356 and 392 and the clone test at `ProjectSync.test.ts:579`. One remainder is filed as P2-15.

## New findings in the round 2 delta

### P2-10 medium, does not block this dark merge, fix before T-07 wires `run`: the fast-forward target is `@{upstream}`, never pinned to origin

`ProjectSync.ts:287` to 303 records whatever `@{upstream}` resolves to, `packages/contracts/src/projectSync.ts:188` only null-checks it, and `ProjectSync.ts:368` to 392 merges `@{upstream}^{commit}`. With `branch.main.remote=.` and `branch.main.merge=refs/heads/other` (a stacked-branch setup), upstream is a purely local branch, and a clean, unused checkout behind it is planned and executed as a fast-forward to that local branch, which this Sync never fetched; I confirmed in `/tmp` that `git rev-parse --abbrev-ref --symbolic-full-name @{upstream}` returns the local branch name there, so the code path runs exactly as traced. An upstream on a second remote behaves the same way, fast-forwarding to that remote's stale tracking ref while Sync fetched only origin. Nothing is lost (the move is `--ff-only` on a clean checkout), but the checkout is moved to commits the person did not ask Sync to bring in, and the result will say "Moved forward {n} commits" about a move origin had nothing to do with. Fix: treat an upstream outside `refs/remotes/origin/` as no upstream for planning, or fetch and name that remote explicitly.

### P2-11 low, can follow: loopback spellings pass `isLocalAddress` and reach `git clone` on the destination

`canonicalOrigin` (`apps/server/src/fleet/handoffGitTypes.ts:95` to 122) keeps the host literal for the non-special schemes `git:` and `ssh:` and for scp form, and `isLocalAddress` (`ProjectSync.ts:122` to 132) matches only `localhost`, `*.localhost`, `::1`, `0.0.0.0` and dotted `127.a.b.c`. Verified with Node's own `URL` and DNS lookup on this machine: `git://127.1/…`, `git://2130706433/…` and `git://0x7f000001/…` keep those literal hosts (the https forms are normalised to `127.0.0.1` by `URL` and are correctly refused), `127.1` resolves to `127.0.0.1`, `https://localhost./…` and `git://localhost./…` keep the trailing dot and `localhost.` resolves to `::1`, and `[::ffff:127.0.0.1]` serialises to `::ffff:7f00:1`, which matches nothing. The octal form `0177.0.0.1` is resolver-dependent and was not proven loopback here. So an origin written in one of those spellings on the source is offered, and cloned from the destination's own loopback service: wrong content or a failed clone, never an overwrite, since the target folder must not exist. A host name that merely resolves to loopback, and a destination-side `url.insteadOf` rewrite (deliberately honoured, `ProjectSync.ts:253`), stay possible by the same token; both are the destination owner's own configuration, and refusing resolved private addresses would break legitimate LAN remotes, so those two are accepted-risk notes, not findings.

### P2-12 low, can follow: staged files past the 2,000-file read cap in a swapped-in folder are content-checked by nobody and reported by nobody

`snapshotSecrets.ts:201` to 209 slices the added files to read at 2,000 and records nothing about the remainder. In the normal flow the pre-check already left files past its cap out (or counted them), so this bites only where `abde444bd` aimed: files that appear between the pre-check and staging, past the first 2,000 in diff order, travel with their first 64 KB unread and no not-checked entry, where AC-14 promises files past the cap are listed as "Not checked" and left out in a dialog. Secret names are still caught for every added file (line 180), so this needs a token in an innocuously named file, a mid-send swap, and more than 2,000 staged additions. Fix: count the unread remainder as not-checked findings, as the pre-check does.

### P2-13 low, can follow: arrival has no compare-and-swap between the re-read and `branch -f`

See P2-03. `ExtrasReceiver.ts:107` to 112. The worker disclosed this; judged non-blocking because the ordinary way to move that branch (check it out and commit) is refused atomically by `branch -f`, and the branch is an arrival branch under `swc/from-`, never one of the destination's own.

### P2-14 low, can follow: a sender sweep can delete the live hidden ref of a send that registered after the sweep's snapshot

`ProjectSyncExtras.ts:562` snapshots `activeOperations` into a fresh set, then `sweepStaleExtraRefs` (line 126) lists and deletes asynchronously. A concurrent `sendExtras` that registers and creates its hidden ref in between is swept as if dead; its send then fails its bundle check and reports a refusal, and its snapshot commit is merely unpinned, so the cost is a failed send, not lost work. The receiver sweep (`ExtrasReceiver.ts:136`) has the same shape and rests entirely on the per-repository, per-process arrival lock. The named sweep tests call the sweep directly with a hand-made set and never race two sends, which matches the worker's "never reproduced" note; the reading above is from the code, not a reproduction.

### P2-15 low, can follow: a failed or cancelled clone recursively deletes whatever is in the target folder Sync created

`ProjectSync.ts:506` runs `rm(recursive, force)` on the target on the strength of the exclusive `mkdir` at line 474. A clone may run for up to 30 minutes, and files another process or the person places inside that Sync-created folder during it are deleted with the clone's remains. The parent undo beside it is `rmdir`-only and safe. Fix: delete only what the clone made, or empty-check before the recursive delete and keep the folder with a refusal when it holds foreign files.

### P2-16 low, can follow: `remote.origin.mirror` values `2` and a valueless key are not recognised

`ProjectSync.ts:100` accepts only `true|yes|on|1|fetch|push`; Git also treats any non-zero integer and a valueless key as true, and `--get-all` prints an empty string for the latter, so such a repository is fetched instead of reported `fetch-config`. The fetch itself is safe regardless (P2-01), and a real mirror clone also carries fetch lines that the same function catches, so only the reported state is wrong. Fix: read the value with `--bool`.

### P2-17 low, can follow: a FIFO swapped in for a listed untracked file hangs the snapshot pre-check

`snapshotSecrets.ts:55` to 60 opens the file before checking it is a regular file, without `O_NONBLOCK`, so opening a FIFO blocks; the failure direction is closed (nothing is sent), but the send hangs until an outer timeout. Git itself stages nothing for an untracked FIFO, so this is the pre-check's own exposure. Fix: `lstat` first, or open non-blocking.

### P2-18 low, can follow: a running thread in a subfolder is missed when its `rev-parse --show-toplevel` fails

`ProjectSync.ts:763` to 768 yields `threadCheckout: null` on that failure, and `threadUsesCheckout` (line 546) then returns false for a thread folder inside the checkout, unlike the fail-closed query path at line 752. A thread whose folder is the checkout or above it still blocks (lines 544 to 545). Fix: treat a failed read for a folder inside the checkout as in use.

## Ships dark

The claim holds for local behaviour. In `checkpointGit.ts` both new checks run only when `contentCheck` is passed (lines 215 and 236), and its only production callers today, `HandoffMode.ts` and `keepFencedChanges` in the same file, pass none; the sole caller passing it is `ProjectSyncExtras.ts:314`. The rest of that diff is additive return fields existing consumers ignore. `bundleGit.ts` only exports its mark list and adds `measureCommitRange`, whose only caller is the extras sender; `ProjectSync.ts:139` layers `sequencer` onto its own copy, so thread hand off and in-place landing see the same six marks as on `origin/main`. `handoffGit.ts` gains only the `discover` export; `MachineHandoff.ts` and `ProjectLink.ts` are untouched by the diff, and `HandoffMoves.ts` behaviour is unchanged because the checkpoint it rides on is unchanged. `server.ts` and the contract files add registrations only, the two new services do no work at construction (no timers, forks or filesystem access; the running-threads query is a prepared value run only inside `inUse`), and the scopes remain exactly the AC-33 table, enforced as in round 1. One honest qualification: the receiver is armed at boot, so a paired machine that initiates `sendExtras` can land `swc/from-` branches on a machine whose owner never opens Sync. That is the intended Phase 2 receiver rather than a behaviour change to existing features: it sits behind the same peer authentication and work grant as a thread hand off (401 unauthenticated and 403 on a revoked grant are both test-asserted), and it can only create or fast-forward branches under `swc/from-`, never touch a working tree. Existing checkpoint arrivals already have the same property.

## Plausible, not proven

- `refs/replace/*` is honoured on these paths (`folderTransfer/git.ts` does not set `GIT_NO_REPLACE_OBJECTS`), so a replacement the owner created can change the tree a fast-forward installs while the head SHA stays the upstream's. Replacements are the owner's own deliberate Git state, and every Git command in the app honours them; listed here because it bounds the P2-01 answer, not as a defect of this PR.
- Hooks are disabled, but repository-configured filter drivers (`filter.*.smudge`) still run during a fast-forward checkout, as they do for any merge the app performs today. The spec promises hooks off, and that promise holds; "hooks off" should not be read as "no repository-configured code runs".
- The extras receiver and the thread hand off receiver hold separate per-process locks, so an extra and a checkpoint can land in one repository concurrently. Ref updates are individually atomic and the arrival re-reads its branch head, so the expected cost is a beside-branch fallback; no concurrent-arrival test exists to confirm or refute harm.
- An orphan checkout of the exact arrival branch name in the window between the receiver's worktree snapshot and its create would have that branch materialise under the new worktree. It needs the person to race their own machine with the exact `swc/from-` name.
