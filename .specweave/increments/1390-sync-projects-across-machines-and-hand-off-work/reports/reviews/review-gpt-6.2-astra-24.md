## Blocking findings

### T19R3-01 [high] A configured peer without a read grant is advertised as reachable

`apps/server/src/handoff/HandoffMoves.ts:772-790` passes `peers.targets` into `launcherFor`. That list is the configured roster, not the granted roster (`apps/server/src/handoff/handoffPeers.ts:309-312,535-545`). `apps/server/src/handoff/handoffFollow.ts:140-150` copies all of its non-self IDs; `apps/server/src/handoff/handoffFollow.ts:108-119` admits an onward move on ID membership alone.

**Scenario:** A lists B and C. A has a grant on B, B has a grant on C, and C has **never** granted A access. All three are online and on this head. A hands the worker to B; B hands it to C. With those roster entries, the exact-head functions produced `reachable: ["B","C"]` and returned `null` (no decline) for B moving to C. B can complete its takeover under its own grant. A cannot read the result: the client requires A's credential for C (`apps/server/src/fleet/RemoteStudioMcpClient.ts:234-239,366-370`), and the follower enters `paused_auth` (`apps/server/src/fleet/RemoteWorkerFollower.ts:1047-1051`). With the permissions unchanged, C can finish and A gets no completion. This is an incorrect snapshot **when taken**, not a stale snapshot.

**Minimal fix:** Build the same handoff-time snapshot from evidence that the launcher can read this project on the destination. Exclude absent or out-of-scope grants; if access cannot be established, do not allow that onward route. No new access is needed. Add a configured-but-ungranted C to the test: B must decline before holding the worker, and A must receive B's eventual result once.

### T19R3-02 [high] A run that finished before the pinned run stopped can close the handoff

`apps/server/src/fleet/handoffDelivery.ts:150-160,173-182` chooses the earliest started, non-stopped run in the **entire** list. It does not compare the candidate's start with the end of the pinned run. `apps/server/src/fleet/RemoteWorkerFollower.ts:824-835` delivers that selection; `apps/server/src/fleet/RemoteWorkerFollower.ts:503-507,537-561` closes the row.

**Scenario:** On an idle-arrival continuation, message 2 is moved ahead of message 1. Run 2 starts and completes. Pinned run 1 then starts and is interrupted. All timestamps are on the page. I ran the exact-head selector with run 2 at times 1–2 and run 1 at 3–4. Before any replacement existed it returned `{"kind":"report","runId":"r2","status":"completed"}`. Adding run 3, the actual replacement, started at 5 and failed at 6, produced the **same** answer, even with the input order reversed. The launcher gets the old success, never the replacement's failure. The reorder is the same setup exercised at `apps/server/src/fleet/handoffFollowerRoute.test.ts:223-235`; that test ends the pin successfully instead of interrupting it.

**Minimal fix:** Pass the stopped run's end boundary to the successor selector. Exclude candidates that started before the stop; wait when none started after it. Use the existing uncertain-result behavior when ordering cannot be established. Test the sequence in two reads: zero completions after run 1 stops, then exactly one for run 3. Keep the agreed ordinal-1 pin.

### T19R3-03 [high] A replacement thread on the same machine is invisible to the launcher

`apps/server/src/handoff/handoffFollow.ts:108-119` permits `destination === self`. `apps/server/src/fleet/handoffDelivery.ts:225-236` ignores that same destination even when the thread is fenced. The individual `handoffMode.handOff` RPC (`apps/server/src/handoff/HandoffMode.ts:875`) accepts a self destination with another model and calls the local receiver (`apps/server/src/handoff/HandoffMoves.ts:547-553,706-717`). This is not the batch or MCP migrate path.

**Scenario:** A hands its worker to B. While the continuation on B is running, B hands that thread to another model on B. The local receiver derives a new thread ID at the next epoch (`apps/server/src/handoff/HandoffReceiver.ts:692-699`); its run finishes. A reads the old, fenced thread, where the only run was interrupted. In memory, the exact-head selectors on that read, including the open history entry for B, returned `{"route":null,"step":{"kind":"nothing"}}`. The follower retries the old thread ID indefinitely (`apps/server/src/fleet/RemoteWorkerFollower.ts:803-806,851-855,922-932`). A receives zero completion wakes.

**Minimal fix:** Decline this self-targeted move before the hold when a remote launcher is waiting, or follow the fenced thread's actual successor ID on the same machine. Add an A → B → replacement-on-B regression that checks either an unchanged running worker on refusal or exactly one wake on A after acceptance.

## Follow-up (non-blocking)

The launcher already received its one failure notification, so this does not block AC-44.
