# 1481 MCP servers can ask the person for input in Claude threads (form-mode elicitation)

## Problem

Claude threads never pass the Agent SDK's `onElicitation` option (`apps/server/src/orchestration-v2/Adapters/ClaudeAdapterV2.ts:1231-1293` on `origin/main` `8dea0b339`). SDK 0.3.276 declines every elicitation it cannot hand to a callback or hook (`sdk.d.ts:1660-1679`). So when any MCP server a Claude thread loads (the user's own servers, through `settingSources` user, project and local) asks the person for input, for example GitHub's `delete_repository` typed confirmation, the request is declined silently and the tool fails with no sign why. Codex threads show the request as a generic "App access approval" with no fields (`ComposerPendingApprovalPanel.tsx:24-36`).

Evidence: research notes `03-specwithcode-gaps.md` gap 1 and `05-brainstorm-opus.md` section A, both under `~/.specwithcode/m4/scratch/2026-11-24-mcp-video/research/` (November 24, 2026).

## Scope

In: form-mode elicitation from any MCP server in a Claude thread reaches the person as a typed form card; URL mode is declined visibly; only the person answers a Claude form (Full access, agents and automatic responders never do, even for a form without fields); answers are checked against the form before the request resolves and stay out of durable records; forms that ask for a secret are refused; unattended threads cancel an unanswered form after 30 minutes; a measured probe of long studio-code calls in Claude threads (not a merge gate).

Changes from the lead's adversarial plan critique (GPT-6.2 Sol, November 25, 2026) override the matching parts of 05 section A: AC-03 no longer exempts confirm-only Claude forms, and AC-04, AC-06, AC-09 and AC-10 carry the rest.

Out: opening URL-mode links (owner decision, needs approval), Codex and ACP moving onto the new card (next increment), in-app OAuth for MCP servers, the phone apps' card (they keep today's generic approval card, which offers Decline and Cancel for a field form), any Agent SDK or Effect version bump.

## Acceptance Criteria

- [ ] AC-01: The `approval_request` turn item of an `mcp-elicitation` request gains one optional `elicitation` object with `serverName`, `mode`, `message` and `requestedSchema`. Codex requests that do not fill it keep today's panel unchanged. In a Claude thread, an `elicitation/create` in form mode from any MCP server the thread loads reaches the person as a card titled "<server> asks for input", showing the message and the fields of `requestedSchema`: string (with the `email`, `uri`, `date` and `date-time` formats and min and max length), number and integer (with minimum and maximum), boolean, single-select (`enum`, `enum` with `enumNames`, or `oneOf` of `const` and `title`) and multi-select arrays (`items.enum` or `items.anyOf`, with min and max items). Defaults are pre-filled and required fields are enforced. **Submit**, **Decline** and **Cancel** answer `accept` with `content`, `decline` and `cancel`. The server re-validates submitted content against the schema; a schema the card cannot show (unknown type, nested object, over the size limit) answers `cancel` and the thread notes "<server> asked for input in a form SpecWithCode can't show yet; it was cancelled."
- [ ] AC-02: The handler is the SDK's `onElicitation` option, built in the new `apps/server/src/provider/ClaudeMcpElicitation.ts`. `ClaudeAdapterV2.ts` gains only the option wiring and the response hook (at most 15 lines). When the SDK `signal` aborts (turn interrupted, thread stopped), the card closes as cancelled and the call answers `cancel`; nothing waits forever.
- [ ] AC-03: Every Claude MCP form needs the person, including a form with no fields. Its card advertises no `accept` option (Submit lives on the form), and `isConfirmOnlyElicitation` (`FullAccessApprovals.ts:86-90`, which treats any `accept` option as confirm-only) returns false for any item that carries `elicitation`. The orchestrator's `runtime-request.respond`, which every route passes through (the person's client over the WebSocket, the agent tool, Full access, relays and internal cancels), refuses an accept on a Claude form that carries `answeredByThreadId` ("Only the user can answer this form. Wait for their answer.") or carries no `answers` ("Submit this form from its card in the thread."). Decline and Cancel stay open to every route, so Stop, settle and dismiss still close a card. Codex confirm-only elicitations keep 0936 AC-03.
- [ ] AC-04: No agent can answer an elicitation card: `studio_pending_request_respond` (`apps/server/src/mcp/toolkits/thread/handlers.ts:412-420`) refuses it with "Only the user can answer an approval card. Wait for their answer.", as it refuses a Gmail send, and the orchestrator refuses it again (AC-03). `studio_thread_send` `answersRequestIds` does not close it. One terminal response only: when two machines answer the same card at once, the first wins and the second is told "This form was already answered."; a card closed by Stop or the timeout answers "This form was closed.". While the card is open the thread's pending request is a person-answered `mcp-elicitation`, so it reads "Waiting on you" and is listed under Needs you through the existing mapping (`packages/client-runtime/src/state/models.ts`, `AWAITING_PERSON_BY_REQUEST_KIND`); the Blocked row and the alert placement of `decision_alert_on_both_machines` follow from that pending request with no new code. An app update that interrupts a stale card (0936 AC-05) cancels the tool call; the form is not shown again after the restart.
- [ ] AC-05: A URL-mode request answers `decline`, visibly: the thread notes "<server> wanted to open a link in your browser. SpecWithCode doesn't open MCP sign-in links yet; finish it from the tool's own terminal." The URL is neither shown as a link nor opened, and no card appears.
- [ ] AC-06: A probe recorded in the increment's `reports/` runs an HTTP MCP tool call held for 3 minutes and for 7 minutes through the Agent SDK with the exact server entry and environment a Claude thread gives studio-code (`type: "http"`, `timeout` 65 minutes, the thread's `env`; studio-code attaches over HTTP, `ClaudeAdapterV2.ts:1395-1402`), on the installed CLI 2.1.331 and on the SDK's bundled CLI. The held calls send no progress (a quiet call), and a cancellation run aborts a held call mid-way. Each held call returns inline, not moved to a background task and not cut by an idle timeout; the cancelled call ends promptly. This check is independent of the form card and does not block its merge. If one fails, the studio-code session environment sets `CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS=0` and a `CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT` above `CLAUDE_STUDIO_MCP_TOOL_TIMEOUT_MS`, the probe passes, and the report states that these variables also apply to the user's own MCP servers in Claude threads.
- [ ] AC-07: The new `apps/web/src/components/chat/McpElicitationForm.tsx` renders the card. `ComposerPendingApprovalPanel.tsx` routes an approval that carries `elicitation.requestedSchema` in form mode to it. Requests without it (today's Codex cards) keep the current panel and actions. `ChatComposer.tsx` and `ChatView.tsx` gain hook lines only (at most 15 each).
- [ ] AC-09: Answers are checked and kept private. On an accept, the orchestrator validates `answers` against the card's bounded schema (D-04) with the shared validator before the request resolves; answers that do not fit are refused with the first field's reason ("<field title>: Required.") and the card stays open. The resolved request in events and projections, and the effect that carries the answer, store only a redacted summary (each answered field's key with "[redacted]"), never the values (`Orchestrator.ts` copied answers into the resolved request, `Orchestrator.ts:9054-9060` on the base). The raw answers reach the Claude adapter through an in-process hand-off that is dropped when the card closes. The server's message is shown as plain text (no Markdown, no links) under the server's name. A form whose field key or title asks for a password, passcode, token, API key, private key, PIN, one-time code or similar is never shown: it answers `decline` and the thread notes "<server> asked for a password or secret ("<field>"). SpecWithCode doesn't send those through forms, so it was declined." Tests cover Stop, the 30-minute timeout and two answers at once.
- [ ] AC-10: Hooks: the SDK runs `Elicitation` hooks before `onElicitation`, and a hook that answers wins. The app installs no `Elicitation` or `ElicitationResult` hook (a test pins the hook events in the options the adapter opens the query with). A hook in the user's or project's own Claude settings (`settingSources` user, project and local) can still answer first; that is the user's configuration and is noted here and in the module header.
- [ ] AC-08: Unattended threads: when the thread was not created by the person (a delegated worker, a routine's thread) or the turn is a routine run, the card still appears under Needs you; if nobody answers within 30 minutes it closes as cancelled, the tool call gets `cancel`, and the thread notes "No one answered <server>'s question in 30 minutes; it was cancelled." The 30 minutes is one named constant, `UNATTENDED_MCP_ELICITATION_TIMEOUT_MS`.

## Approach

1. Contracts (`packages/contracts/src/mcpElicitation.ts`, new): `OrchestrationV2McpElicitation` schema, added as an optional field to both `approval_request` structs in `orchestrationV2.ts` (hook lines only, the file is 4,540 lines). `providerPolicy.ts` needs nothing: `mcp-elicitation` already exists.
2. Shared schema module (`packages/shared/src/mcpElicitationForm.ts`, new): parse `requestedSchema` into typed fields (or a reason it cannot be shown), and validate and coerce submitted values. Used by the server handler (re-validation) and the web form (rendering and client validation), so both agree.
3. Server handler (`apps/server/src/provider/ClaudeMcpElicitation.ts`, new): `makeClaudeMcpElicitations(deps)` returns `onElicitation` and `respond`. It keeps its own pending map, builds the request with the adapter's `buildApprovalRequestArtifacts`, adds `appName`, `options` and `elicitation` to the turn item, emits the three events, and races the person's answer against the SDK signal and, for unattended turns, the 30-minute timer. When it closes a card itself it emits the request, node and turn item as cancelled (the `dismissNativeUserInputs` pattern in `ProviderEventIngestor.ts`) plus a `system_notice`. `ClaudeAdapterV2.ts` gets the option in `makeClaudeQueryOptions`, the handler's construction, and one `respond` delegation at the top of `respondToRuntimeRequest`.
4. Every Claude form advertises Decline and Cancel only; `isConfirmOnlyElicitation` also checks `item.elicitation === undefined`, so Full access and the composer's "switch to Full access" shortcut never accept one.
5. Agent refusal in `apps/server/src/mcp/toolkits/thread/handlers.ts`: before `readQuestion`, a pending `mcp-elicitation` request with that id is refused with the Gmail-send message. `answersRequestIds` already only closes `user_input` cards; a test pins it.
5a. Response rules (`apps/server/src/orchestration-v2/ClaudeFormResponses.ts`, new): `checkFormResponse(item, status, command)` returns a refusal, the redacted answers to store and the content to hand off. `Orchestrator.ts` (14,380 lines) gets hook lines only: the call and refusal before the pending check, `storedAnswers` in the resolved request and the effect, and the hand-off before the effect. `ClaudeMcpElicitation.respond` takes the raw answers from the hand-off; a restart loses the hand-off but also ends the Claude process waiting on it.
6. Web: `ThreadPendingApproval` gains `elicitation` (`packages/client-runtime/src/state/threadRequests.ts`); `respondToThreadApproval` passes optional `answers` (`packages/client-runtime/src/operations/commands.ts`); `ComposerPendingApprovalPanel` routes to `McpElicitationForm`, which owns its three buttons; `ChatComposer` hides the generic actions for a form card and passes the responder; `ChatView`'s responder takes optional content.
7. Probe (AC-06) and live check (screenshot) run from a scratch folder against the verification copy, never the shared checkout.

Rejected: a new runtime request kind (the kind exists and Codex, phones and Full access already know it); answering through the hook events (`Elicitation` hooks are config files, not per-thread code); an app-side timeout for attended threads (a person may leave a card open on purpose; the turn's Stop closes it).

Risks: an MCP server's own request timeout (the TypeScript MCP SDK defaults to 60 s) can end the request before the person answers; the CLI's behaviour then is unverified and recorded as a proof limit. The secret check reads field keys and titles only, so a server can still ask for a secret under a neutral name; the card's note tells the person never to enter one. The web client's own command (the person's answers in a WebSocket request) is not persisted by the server, but browser extensions or devtools on that machine can see it.

## Decisions

### Asked
- D-01 Unattended threads cancel after 30 minutes (owner, in the brief, November 24, 2026).
### Defaulted (change any before sw-do)
- D-02 "Unattended" is read from the thread, not the turn's message: the thread was not created by the person (`appThread.createdBy` is `agent` or `system`: delegated workers, routine threads), or the turn's message carries a routine's `scheduledTaskId`. Wake, compaction and recovery turns in a person's own thread carry `createdBy: "system"` messages, so a message-level rule would cancel a watched card. A person's own thread waits until answered or stopped.
- D-03 Display data lives on the `approval_request` turn item as one optional `elicitation` object; the runtime request shape is unchanged.
- D-04 Limits: a `requestedSchema` over 64 KB of JSON or with more than 50 properties is cancelled with the notice in AC-01.
- D-05 The AC-06 probe uses a local HTTP stand-in server with the same entry and environment as studio-code, not the live studio-code, so no live app or database is touched.
- D-06 The phone apps and the coordinator's native-controls strip keep today's generic approval actions (Decline and Cancel for a field form) until the Codex and ACP follow-on.
- D-07 New card text is English only for now; other languages fall back to English (the i18n catalog allows it).
- D-08 The raw answers travel in process from the orchestrator to the Claude adapter, not through the effect outbox (which keeps settled effects for 7 days). Rejected: scrubbing outbox rows after delivery (touches every effect kind).
- D-09 "Already answered" is decided by the orchestrator's single writer: the second of two answers finds the request resolved.
- D-10 Review round 2 (GPT-6 Sol, NO-SHIP on `6e2061f87`) found two real gaps, both fixed:
  - The adapter records a form's request a moment before its card. A request whose native id the Claude adapter gave it (`mcp-elicitation:` from driver `claudeAgent`) is a form even before its card lands. Until then an accept is refused with "This form is still opening. Try again in a moment.", and Decline or Cancel go through without keeping any answers.
  - A field named `__proto__`, `constructor` or `prototype` makes the form one the card can't show, so it is cancelled with a note. The validator reads only the answers object's own values.
