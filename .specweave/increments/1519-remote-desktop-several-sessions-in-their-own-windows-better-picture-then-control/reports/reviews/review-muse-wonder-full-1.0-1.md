## Must-fix

1. **must-fix: an unexpected helper exit loses every key from a still-unanswered release; the session hand-off does not cover them.** The exit handler now rescues only after its own `stop()` (`apps/desktop/src/screenShare/ScreenControlHelper.ts:148`, `apps/desktop/src/screenShare/ScreenControlHelper.ts:151`) and otherwise just calls `onExit` (`apps/desktop/src/screenShare/ScreenControlHelper.ts:166`). The session path is real for keys it still holds: `onExit` is wired at `apps/desktop/src/screenShare/screenShareSession.logic.ts:1126`, `helperGone` deletes the link and ends control (`apps/desktop/src/screenShare/screenShareSession.logic.ts:1202`), and `endControl` then orphan-releases what `held.take()` returns (`apps/desktop/src/screenShare/screenShareSession.logic.ts:1240`, `apps/desktop/src/screenShare/screenShareSession.logic.ts:1246`, wired to a fresh helper at `apps/desktop/src/screenShare/ScreenControlDeps.ts:59`). But a live release (silence timer at `apps/desktop/src/screenShare/screenShareSession.logic.ts:1175`, display switch at `apps/desktop/src/screenShare/screenShareSession.logic.ts:715`, lock at `apps/desktop/src/screenShare/screenShareSession.logic.ts:827`) first empties that tracker: `releaseHeld` sends `control.held.take()` (`apps/desktop/src/screenShare/screenShareSession.logic.ts:1186`), and `take()` clears both sets (`apps/desktop/src/screenShare/screenControl.logic.ts:200`). From then on, those keys exist only in the link's unreleased sets (`apps/desktop/src/screenShare/ScreenControlHelper.ts:100`), and the release promise still resolves after 500 ms with no answer (`apps/desktop/src/screenShare/ScreenControlHelper.ts:25`, `apps/desktop/src/screenShare/ScreenControlHelper.ts:93`), so the session cannot tell. If the helper is then killed or crashes on its own (the SIGKILL case the old code rescued from its last-held snapshot), the link drops the sets and the session's `take()` returns only keys pressed since, so the unanswered release's keys — a stuck `MetaLeft`, say — are let go by nobody. Probe A (below) confirms the link starts no rescue and reports only `onExit` in this state. Fix direction: carry the unreleased sets out on the unexpected-exit path (for example through `onExit`, merged into the session's single orphan release), or rescue them in the exit handler when non-empty regardless of who stopped the helper; the sets are disjoint from the session's currently-held keys by construction, and a duplicate key-up is harmless.

2. **must-fix: one `released` reply clears later, still-unanswered releases.** Any `released` line clears both whole sets and resolves every waiter (`apps/desktop/src/screenShare/ScreenControlHelper.ts:133`). Swift answers releases one at a time, in queue order: lines append and drain FIFO (`native/screen-control/main.swift:316`, `native/screen-control/main.swift:333`), and each `release` case inserts the named keys, releases all, then replies (`native/screen-control/main.swift:267`). So a reply proves only the earliest outstanding release. Session-reachable loss: release R1 is queued; the viewer presses KeyA (its down line is queued after R1, so R1's `releaseAll` cannot cover it); a second release R2 names KeyA and adds it to the sets (`apps/desktop/src/screenShare/ScreenControlHelper.ts:100`); if R1's reply is read after that `release()` call, it wipes KeyA and resolves R2's waiter early. If the helper then stalls before R2 and `stop()`'s SIGKILL lands (`apps/desktop/src/screenShare/ScreenControlHelper.ts:75`), the exit handler sees empty sets and starts no rescue (`apps/desktop/src/screenShare/ScreenControlHelper.ts:151`), and the session does not backstop an expected exit (`apps/desktop/src/screenShare/ScreenControlHelper.ts:166`) after `endControl` already took its held set (`apps/desktop/src/screenShare/screenShareSession.logic.ts:1241`). Probe B (below) demonstrates exactly this against the real module: the second release resolves on the first reply and no rescue helper is spawned. This is the same lost-unanswered-release class as the round-3 must-fix, so fix 1 is incomplete. Fix direction: keep a FIFO of per-release snapshots (with their waiters); on `released`, drop only the earliest snapshot, removing a key only when no later snapshot still names it. The new test cannot catch this: its first helper never replies at all (`apps/desktop/src/screenShare/ScreenControlHelper.test.ts:79`), so no `released` line is ever interleaved.

## Confirmed in this commit

- **Round-3 finding 1, in the tested path: fixed.** Releases add to union sets instead of overwriting (`apps/desktop/src/screenShare/ScreenControlHelper.ts:100`), and the rescue after `stop()` sends the whole union (`apps/desktop/src/screenShare/ScreenControlHelper.ts:157`). Sequential timed-out releases (`MetaLeft`, then `KeyA` + `left`) rescue as one union; see finding 2 for the reply interleaving that still breaks the "not yet answered" invariant stated at `apps/desktop/src/screenShare/ScreenControlHelper.ts:56`.
- **Round-3 finding 2, in part: fixed.** An answered release with nothing else outstanding leaves empty sets, so a later kill starts no stale rescue (`apps/desktop/src/screenShare/ScreenControlHelper.ts:155`), and an unexpected exit no longer races the session's orphan release for keys the session still holds (chain cited in finding 1). The unanswered-release case in finding 1 is the part that is not fixed.
- **Round-3 finding 3: fixed.** Let-go input lines (`"down":false`) are admitted only while the total queue is under `letGoLimit` = 1,024, other input under 256 (`native/screen-control/main.swift:302`, `native/screen-control/main.swift:311`). Release and config lines remain uncapped, as before; only the app writes those. Stale let-go events still run (`native/screen-control/main.swift:228`, `native/screen-control/main.swift:246`), and `release` is never stale-checked (`native/screen-control/main.swift:267`).
- **Swift ordering: sound.** One FIFO queue for input, release and config (`native/screen-control/main.swift:316`, `native/screen-control/main.swift:333`), drained serially on the main queue (`native/screen-control/main.swift:324`); no line overtakes an earlier one, which is what makes reply-per-release accounting possible.
